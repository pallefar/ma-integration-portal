<objective>
Finish the steering-committee pack and put it in the Integration Lead's hands: the three data
sections, the route that assembles a clearance-filtered model and returns the file, and the single
accent-coloured button that generates it.

This is where the pack becomes a real MNPI egress surface, so it inherits the tracer's guarantees
rather than restating them: it reads the same filtered lanes the raw exports read (D-08), it has no
org or talent surface at all (D-09), and it writes the same audit event on real deals and none in
demo (D-10/D-11).

Purpose: RPT-02 delivered end to end, with RPT-03's no-double-counting and RPT-04's stale-versus-
current rules visible in the document a steering committee reads.
Output: three pack sections, GET /api/reports/pack, and the pack card on the Reports tab.
</objective>

  <action>
    Register the three remaining sections with the paginator, in D-04's fixed order after the executive
    summary: workstreams and tasks, then risks and decisions, then synergies. Each is a measuring
    composer in pass one and a body-callback renderer in pass two, exactly as the frame requires; none
    of them draws a header or footer band.

    Workstreams and tasks. First a horizontal bar per workstream: a light track, a fill coloured by the
    band the server-side workstream rollup already computed, the label on the left and the percentage on
    the right — the document-scale equivalent of the screen's own workstream progress bars, drawn with
    the canvas the repository already vendors and no chart library (D-06). Below the bars, a task table
    with columns for title, workstream, phase, status, owner and due date, one row per task, separated by
    a hairline rule and with no zebra striping, because the app's own lists do not stripe and the pack
    should not invent a new visual habit.

    Risks and decisions. One table with columns for type, severity, title, owner and status, grouped by
    type in the same fixed order the screen's own filter buttons use, so the live filter interface and
    the pack's static grouping agree. Severity renders as coloured text in the existing four-level
    palette, not as a filled pill — at this density a filled chip per row competes with the table and
    costs ink for no added clarity. Rows this caller is not cleared for are already absent from the model
    before this renderer runs; the section must never draw a placeholder row or a count implying that
    further entries exist, because that would disclose the existence of restricted content, which is
    exactly the absence-not-disabled principle this project established in Phase 6, now extended to a
    generated document.

    Synergies. A small recap caption at the top of the section repeating page one's headline figures at
    the small type size, read from the SAME rollup object page one read — never re-summed from the rows
    printed below it, which is the drift RPT-03 names and D-02 forbids. Then the per-initiative table:
    title, category as coloured text, stage as coloured text in the four-stage palette, **stage at last
    baseline** (same four-value vocabulary as plain text, an em-dash when the initiative has no baseline
    history — sourced from Phase 5's baseline records, resolved server-side into the pack model alongside
    the current stage, never re-derived in the renderer; this column IS RPT-03's "confidence-stage
    movement" — UI-SPEC §5 Section 4 amended 2026-08-09 per the planner's RPT-03 PARTIAL, option (a)),
    target, realized, cost incurred, net benefit, and a small horizontal realized-versus-target bar drawn
    as a two-stop linear gradient using the same two colours the screen's own synergy bar uses. Test
    assertion (add to this task's verification): a fixture initiative whose baseline stage differs from
    its current stage renders BOTH values in its row, and an initiative with no baseline history renders
    the em-dash — proving movement is visible, not merely current state.

    Stale rows (D-12): an entire row's text renders in the dim text colour instead of the primary text
    colour, and a small filled rounded tag reading the stale label followed by the day count from Plan
    07-04's field is drawn after the initiative title, using the screen's existing stale-badge palette.
    Stale initiatives stay in their normal position in this same table — not sorted to the bottom, not
    moved to their own page, and with no appendix anywhere in the document.

    Pagination for all three sections: when a table exceeds the remaining content height, it continues
    onto further pages, and the column-header row REPEATS at the top of every continuation page while the
    section title does not — a reader distinguishes a continuation from a new section by the footer's page
    counter. Enforce a page ceiling in the measuring pass and, if a deal's data would exceed it, truncate
    the final table with a plain last line stating how many further rows exist in that dataset and naming
    the CSV export as the complete source. That truncation notice is about volume, not clearance, and must
    never be conditioned on or worded in terms of what the caller may see.

    Every label resolves through the language resolver, and every column width is measured from the
    resolved string, never from the English one.

    Extend test/reports-pack.test.js: assert a task set large enough to overflow produces more pages and
    that each continuation page's descriptor carries the repeat-header state; assert the synergies recap
    numbers equal the supplied rollup exactly on a rounding-edge fixture; assert a stale initiative's row
    carries the dim colour and a tag whose day count matches the supplied field, and that its index in
    the rendered row order is unchanged from the input order; assert the RAID rows render grouped in the
    fixed type order; assert no drawn string anywhere in a pack rendered from a model containing withheld
    rows mentions a hidden, restricted or remaining count; and assert an oversized deal truncates with the
    stated notice rather than producing an unbounded document.
  </action>
