  <action>
    Collect every translation key this phase introduced across Plans 07-01 through 07-06: the Reports
    and Exports tab label, the four dataset labels, the two format labels, the raw-data-export and
    steering-committee-pack section labels, the pack card intro sentence, the generate button label, its
    generating-in-flight label, the pack failure message, the empty-deal message, the unphased rollup
    tile label added in Plan 07-04, and every label the pack renderer resolves — its section titles,
    column headings, stat tile labels, stale tag and stale-count sentence. Derive the list from the
    source rather than from memory, by scanning the interface files for translation-key attributes in the
    reports namespace and the pack renderer for its resolver calls.

    Write scripts/seed-reports-i18n.js on the org seed's shape. For each key, write an English value and
    a value in the other three shipped languages. Follow the convention this project settled: where a
    phrase's meaning is genuinely unchanged from an existing translated string, carry that translation
    verbatim; otherwise ship English and rely on the documented fall-back-to-English contract, and say in
    the script's header comment which keys took which route and why. Do not machine-invent a translation
    for a compliance-bearing string: the confidentiality line's leading word stays as it is in every
    language, because it is a handling instruction, not interface copy.

    The script is ADD-ONLY per language: if a key already carries a value in a language, leave that value
    untouched. Overwriting is the documented trap here — an existing translation silently overrides the
    inline English text of any element carrying that key, so re-pointing an existing key at new copy
    produces a page that reads correctly in English and wrongly in every other language, or the reverse.
    Every key this phase adds is new, so any collision is a signal to stop and investigate rather than to
    overwrite.

    Make the script idempotent by deleting exactly its own key list before re-inserting, and print a
    summary line naming the count of keys written per language, matching the org seed's own reporting
    style.

    End the script with a truncating write-ahead-log checkpoint before closing the connection, then
    verify the effect by diffing the tracked database file against the committed revision. A clean
    working tree is not evidence: a write to a committed write-ahead-log database can land only in the
    ignored sidecar, leaving the tracked file byte-unchanged while the write appears to have succeeded.
    This has fired in every prior phase of this milestone that touched a committed database file.

    Create test/reports-i18n.test.js: enumerate the translation-key attributes present in the reports
    pane of the execution page and every key the pack renderer resolves, and assert each one resolves to
    a non-empty value in each of the four languages through the same lookup order the application uses.
    Assert no key in the reports namespace resolves to its own key name, which is what a missing entry
    would surface as on screen.
  </action>
