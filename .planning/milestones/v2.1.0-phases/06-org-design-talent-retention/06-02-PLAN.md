<objective>
Complete ORG-01's organisation view against UI-SPEC §Surface Contracts 2 and 3 and §Design Tensions
1, 2, 4 and 6: a collapsible indented tree that stays legible at 200+ nodes and at 375px, a
client-side search that force-expands ancestors of a match, an unassigned-employees bucket below the
tree, and the current/target switch that is structurally absent for an uncleared session rather than
disabled.

Purpose: the tracer proved one card renders; this makes the surface the thing an Integration Lead
actually works in, and closes the Tension-4 disclosure hole where a disabled control would itself
announce that a target design exists.
Output: a production-quality org workspace page plus three server additions — a capability probe, a
current-to-target copy action, and a delete route that refuses to orphan direct reports.

**Planner judgment call, surfaced.** UI-SPEC §Design Tension 3 requires the client to construct a
target-state request only when "a `restricted` capability flag from an initial `GET /api/org/summary`
or equivalent probe is present". `GET /api/org/summary` does not exist until Plan 07 and cannot exist
earlier, because its restricted tier tallies decisions and flight-risk entries that Plans 04 and 05
create. This plan therefore builds the "equivalent probe" the UI-SPEC explicitly allows for —
`GET /api/org/capabilities` — using the same `hr` grant check and the same absent-key-not-false
response shape the summary route will use in Plan 07. This is defence in depth only: the server
refusal built in Plan 01 remains the actual control.

**Planner judgment call, surfaced.** UI-SPEC §Surface Contract 3's target empty state reads
"Positions copied from current state, or added new, will appear here", which names a copy action the
spec never otherwise specifies. Rather than ship copy that describes a capability that does not exist,
this plan builds it: `POST /api/org/positions/copy-to-target`. Per this phase's identity model
(Plan 01's objective), the copy produces NEW ids and remaps `reportsToId` through an old-to-new id
map — it never re-points or shares a current-state row.

**Sibling ordering is a backstop, not an invented rule.** Nothing in 06-CONTEXT.md, the ROADMAP or the
UI-SPEC locks how siblings under one parent are ordered. This plan does not invent a sort rule; it
records the stability property as a `verification: backstop` must-have so an unevidenced claim routes
to human review at verify time instead of silently passing.
</objective>
