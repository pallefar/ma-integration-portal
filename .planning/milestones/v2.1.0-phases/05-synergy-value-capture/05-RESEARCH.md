## User Constraints (from CONTEXT.md)

### Locked Decisions

**Phasing model**
- **D-01:** Monthly periods are the phasing granularity. User chose monthly over the recommended quarterly. The consequence was surfaced before the choice — 36 rows per initiative over a 3-year horizon — and accepted, mitigated by D-05 auto-fill.
- **D-02:** Run-rate (steady-state annual) is tracked separately from in-year realized value. An initiative can be at 100% run-rate while in-year banked value is far lower; practitioners treat this distinction as essential.
- **D-03:** The phasing horizon is 3 years, configurable per deal — covers the standard cost-synergy ramp to full run-rate without forcing a small acquisition into a full 3-year grid.
- **D-04:** The existing `targetM` / `realizedM` fields become **derived totals** (rollup of the phased rows) — not removed, not independently editable. Chosen for demo-showcase safety: every existing consumer (demo showcase, PMO console, dashboards) keeps working untouched. — **Reversibility:** costly per CONTEXT.md's framing — see this document's "Verified Ground-Truth Findings #13" for a correction: the actual blast radius is narrower than stated.
- **D-05:** Monthly rows are generated by ramp-template auto-fill: the IL enters run-rate + start month + curve shape (cost 30/70/100, revenue 10/40/70, or linear); rows generate automatically and remain individually editable. This is what makes monthly granularity workable.
- **D-06:** Realized value is editable **only for months that have arrived** — no forward-booking into future months. Forward-booked value is the main way synergy tracking loses trust.

**Stage vocabulary + migration**
- **D-07:** **Replace** the 5 execution statuses with exactly the 4 SYN-03 confidence stages: `idea → validated → committed → captured`. One canonical field, one axis. Mapping applied once: `identified→idea`, `validated→validated`, `planned`+`executing`→`committed`, `realized→captured`. Rejected: a 5-gate rename keeping `executing`, and a second independent `confidenceStage` field alongside `status`.
- **D-08:** Stage advancement carries **minimal hard gates, enforced server-side** with a stated rejection reason: `committed` requires an owner AND a phased target (run-rate + start month, per D-05); `captured` requires realized value recorded in at least one arrived month (per D-06).
- **D-09:** Backward stage movement (de-scoping) is **allowed but requires a non-empty reason**, recorded in the initiative's baseline history alongside the stage change.
- **D-10:** The 5 demo seed initiatives are **hand-tuned** to spread across all four stages and carry believable phasing rows, rather than taking the mechanical map verbatim.
- **D-11:** **Hard cutover — no read-time compatibility shim.** The 4 stages become the only accepted values in all three duplicated copies (`server.js:3043`, `validators/workstream.js:114`, `public/js/execution.js:28-30` including `SYN_LABELS`/`SYN_COLORS`); legacy values are rejected by the validator. Verified safe during discussion: `data/deals/` is empty. Migration surface is 5 seed rows in `demo.db` plus the legacy `ma-portal.db` copy.

**Baseline history**
- **D-12:** Baseline history is an **explicit snapshot model**: a `baselines[]` array on the initiative, each entry pinning the full prior target curve + run-rate + stage with who/when/why. **Not** a keystroke-level change log.
- **D-13:** A new baseline version is created by an **explicit re-baseline act** at any time, AND is **forced** (with a required reason) for any run-rate or curve-shape change once the initiative has reached `committed`.
- **D-14:** **Baseline v1 is pinned as the "deal case"** and is never superseded. Variance reports against **both** the deal case and the current baseline.
- **D-15:** **AUTHZ (explicit):** re-baselining is restricted to the Integration Lead and admin, **enforced server-side**. Baseline history is readable by any authenticated member of that deal. Rejected owner-can-also-re-baseline and any-member-writes.

**Staleness rule**
- **D-16:** Staleness is driven by an explicit `lastConfirmedAt` stamp, set by a deliberate **"confirm current"** action or by a real value/stage change — but **not** by editing a note or title.
- **D-17:** The staleness threshold is **30 days, configurable per deal**, applied uniformly to every stage.
- **D-18:** Stale initiatives are **visibly badged AND the headline rollup splits the figure**: "realized $XM, of which $YM unconfirmed".
- **D-19:** Stale initiatives **nudge their owner by reusing the Phase 4 deal-home in-app owner-nudge pattern** (DD-02), not a new notification surface. See "Verified Ground-Truth Findings #7" — this document corrects the exact code location.

**Cost-to-achieve (SYN-02)**
- **D-20:** Cost-to-achieve is modelled as a **single planned figure (with an expected spend month) plus dated actual-cost entries** — a list, not a fixed monthly grid.
- **D-21:** The headline synergy rollup reports **gross realized, cost incurred, and net benefit**, alongside the stale split from D-18.

**Task linkage (SYN-04)**
- **D-22:** Linkage is stored as **`taskIds[]` on the initiative** — a task may serve several initiatives. Rejected `source: 'synergy:<id>'` on the task (verified collision with the existing dedupe use of `source`, `server.js:3006`) and rejected denormalizing both directions.
- **D-23:** Completing linked tasks **does not** affect realized value or stage. The link shows a delivery-progress indicator ("4 of 6 tasks done").

## Summary

This phase has **no new external dependency** — it is a data-model extension (new fields + arrays on an existing collection), five to seven new/extended Express routes reusing the existing zod validation pipeline, and a vanilla-JS rewrite of one render function (`renderSynergy()` in `public/js/execution.js`). The UI-SPEC (already checker-approved, 4 PASS/2 non-blocking FLAG) is the binding visual contract; this document focuses on the parts a UI spec cannot cover — exact current code shape, exact migration surface, and where each of the 23 decisions attaches to that code.

Every one of the 12 specific verification targets in this phase's brief was checked directly against source and the live committed `.db` files this session (not re-stated from CONTEXT.md). All twelve came back **confirmed as stated**, with two corrections worth flagging up front because they change what the planner should write in the plan text:

1. **D-19's nudge surface does not exist yet where CONTEXT.md implies it does.** `renderOwnerNudge()` lives in `public/js/due-diligence.js:526-570` and fires on the DD workspace page itself. `public/js/deal-home.js` (the actual "deal-home" surface, rendered into dashboard.html's `#deal-home` div) has **three panels and zero nudge/banner code** — Setup checklist, Readiness assessments, Diligence progress, nothing else. D-19 must be read as "reuse the *pattern*" (badge + `page-banner--warning` + `window.makeBannerDismissible` + session-scoped dismissal), not "extend an existing nudge on that page" — because there isn't one there to extend. The planner should scope a task to *author* a new `renderStaleSynergyNudge()`-shaped function inside `deal-home.js`, modelled on (not literally calling) `due-diligence.js`'s function.
2. **D-04's stated blast radius is wider than the code shows.** `targetM`/`realizedM` are read by exactly **one** file: `public/js/execution.js` (lines 218-219, 232, 241, 243). Neither `public/js/pmo.js` nor `public/js/dashboard.js` reads `targetM`/`realizedM`/`synergyInitiatives`/`/api/synergies` at all — `pmo.js`'s "synergy" gauge (`pmo-synergy-fill`) is a workstream task-completion metric, unrelated data. This does not change D-04's decision (deriving the two fields as rollup totals is still correct and low-risk) but it means the "reversibility: costly" framing overstates the real cost — a future revert touches one file, not three.

**Primary recommendation:** extend the existing collection in place (no new SQLite table — `synergyInitiatives`/`customSynergyInitiatives` stay the storage unit, per `db/collections.js:34,55`), add 5-6 new dedicated sub-routes under `/api/synergies/:id/*` for the distinct-authz / distinct-audit-shape actions (stage change, re-baseline, confirm-current, generate-phasing, cost-entries) rather than further overloading the single upsert handler, and follow the exact WAL-checkpoint + direct-SQL-UPDATE script pattern `scripts/seed-dd-request-templates.js` already established for the one-off demo-seed migration.

### 6. Role model — `ROLE_WRITE_POLICY` confirmed, no existing "admin-or-IL-only" inline helper exists

```js
}
```

### Pattern 1: Dedicated sub-routes for distinct-authz / distinct-audit actions

**What:** Rather than continuing to overload `POST /api/synergies`' single upsert handler with every new capability, give each action with its own authz rule or its own required-field shape a dedicated route.

**When to use:** Any action where (a) the authz rule differs from the base upsert (re-baseline, D-15), or (b) the payload shape and required fields are fundamentally different from a partial-field upsert (stage change with a gate + optional reason; confirm-current touching exactly one field; cost-entry add/delete being list operations, not object-merge).

**Why (precedent in this exact codebase):** `POST /api/deals/:id/members` (`server.js:796`), `POST /api/dd/request-items/instantiate` (`server.js:100-108` region via validator + its own server.js route), and `POST /api/dd/findings/:id/convert` (DD-03's conversion route) are all existing examples of a capability that could theoretically have been crammed into a base upsert route but was instead given its own path, specifically because its authz rule or required-shape differed. This phase has MORE such actions than any prior phase's single lane (5 distinct sub-actions on one resource), making the case for dedicated routes stronger here than anywhere else in the codebase so far.

**Example (re-baseline route, D-13/D-15):**
```js
// server.js — new, near the existing synergy section
```

### Pattern 2: Server-computed rollup totals, never client-writable once phasing exists

**What:** D-04 requires `targetM`/`realizedM` to become derived totals. Compute them server-side on every read (`GET /api/synergies` and inside the create/update response), from `(item.phasing || []).reduce(...)`, rather than storing them as independently-writable fields once an initiative has any `phasing[]` rows.

**When to use:** Any initiative that has generated phasing rows (post-D-05). An initiative with zero phasing rows (brand new, pre-ramp-generation) should fall back to the pre-existing raw `targetM`/`realizedM` behavior so the UI-SPEC's stated empty-state ("No phasing rows yet") doesn't also need a zeroed rollup card.

**Example:**
```js
function synergyRollupFields(item) {
  const rows = item.phasing || [];
  if (!rows.length) return { targetM: item.targetM || 0, realizedM: item.realizedM || 0 };
  const targetM = rows.reduce((a, r) => a + (r.targetM || 0), 0);
  const realizedM = rows.reduce((a, r) => a + (r.realizedM || 0), 0);
  return { targetM: Math.round(targetM * 10) / 10, realizedM: Math.round(realizedM * 10) / 10 };
}
```

### Anti-Patterns to Avoid
- **Adding a 4th independent copy of the stage vocabulary:** any new stage-aware code (e.g. a stage-gate-check helper) must reference the SAME three arrays (`server.js:3043`, `validators/workstream.js:114`, `public/js/execution.js:28-30`) being renamed in place — never introduce a 4th literal array anywhere, including inside a new sub-route file.
- **Computing "arrived" months against `timeTravelDay`:** see Finding #12 — this would be new, untested complexity contradicting the established `computeOverdue()` precedent.
- **Storing `baselines[]` snapshots as references, not copies:** D-12 requires the FULL prior target curve pinned — a shallow reference to the live `phasing[]` array would silently "time-travel" the pinned baseline forward as the live array is edited. Always deep-copy (`.map(p => ({...p}))`) when snapshotting.
- **Skipping `wal_checkpoint(TRUNCATE)` after the demo-seed migration script:** confirmed live risk — `git status` currently reports clean, but any unchecked-in write to `data/demo.db` will land only in the gitignored `-wal` sidecar, leaving the tracked file byte-identical and the migration invisible to `git diff`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Audit trail for new fields | A custom before/after diff for `phasing[]`/`baselines[]`/`costEntries[]` | The existing `db/store.js` `writeDb()` hook (Finding #8) | It already whole-row-serializes; a custom per-array diff would duplicate working infrastructure and risk missing a field |
| Request validation | Ad hoc `if (!b.foo) return 400` checks in the route handler | `validators/workstream.js`'s `registerSchema()` pipeline | This is VAL-01's established, test-gated (`test/write-validation-coverage.test.js`) requirement — a route with no registered schema fails closed with a 500, so skipping this is not a silent option |
| Month/date parsing for the phasing grid | A date library, or hand-rolled `Date` object math for month arithmetic | Zero-padded `YYYY-MM` string comparison (`<`, `>`, `===`) — lexicographic sort is chronological sort for this exact format | `validators/dd.js`'s existing calendar-date precedent proves regex+string-compare is this codebase's established pattern for date-shaped fields; no library has ever been introduced for this class of problem |
| Ramp-curve percentage tables | A generic curve-fitting/interpolation library | Three named, fixed lookup tables (cost 30/70/100, revenue 10/40/70, linear) per D-05 — these are literal percentages applied to elapsed months since `startMonth`, not a mathematical curve-fit problem | D-05 names exactly three shapes; a general-purpose interpolation library would be solving a problem one order of magnitude more general than what's asked |

**Key insight:** every "don't hand-roll" item in this phase resolves to "reuse infrastructure this exact codebase already built in Phases 1-4," not "reach for an external library." This phase's entire technical risk is in getting the DATA MODEL and the AUTHZ/GATE placement right, not in algorithm or library selection.

## Common Pitfalls

### Pitfall 1: Overloading `POST /api/synergies` past the point of correctness
**What goes wrong:** Continuing to add `if (b.foo !== undefined) item.foo = ...` branches to the existing upsert handler for stage changes, re-baseline, and confirm-current makes it impossible to enforce D-08's gate or D-15's authz correctly, because a single PATCH-shaped body could carry a stage change AND a title edit AND a re-baseline reason in one request, with no clean way to say "this part needs admin/hrbp, that part needs the gate check, this other part needs neither."
**Why it happens:** The existing handler already does this for `title`/`owner`/`category`/`targetM`/`realizedM`/`status` — it's the path of least resistance to keep adding to it.
**How to avoid:** Follow Pattern 1 above — dedicated routes for stage/rebaseline/confirm-current/cost-entries/generate-phasing; keep the base `POST /api/synergies` for the fields it already correctly handles (title/owner/category/notes/workstream) plus the NEW read-only-until-generated `targetM`/`realizedM` (Pattern 2).
**Warning signs:** A single route handler exceeding ~150 lines with more than 3 distinct `if (b.X !== undefined)` authz-sensitive branches.

### Pitfall 2: Missing the D-19 nudge surface's actual location
**What goes wrong:** A plan task that says "extend `due-diligence.js`'s `renderOwnerNudge()` to also cover stale synergies" will fail at execution time, because that function is scoped to DOM selectors (`.dd-hero h1`, `.main-content`) that exist ONLY on `due-diligence.html`, not `dashboard.html`.
**Why it happens:** CONTEXT.md's phrasing ("the deal-home owner-nudge pattern... in `public/js/due-diligence.js` + deal-home surface") reads as if the function already spans both files.
**How to avoid:** Per Finding #7 — author a NEW function in `deal-home.js`, matching the PATTERN (badge + `page-banner--warning` + `window.makeBannerDismissible`), not literally reusing the DD function.
**Warning signs:** A plan task with an action verb like "extend" or "wire" applied to `due-diligence.js`'s `renderOwnerNudge` in the context of `dashboard.html`/`deal-home.js`.

### Pitfall 3: Forgetting the WAL checkpoint on the seed-migration script
**What goes wrong:** The D-07 stage migration + D-10 hand-tuning script runs, appears to succeed, but `git status` and `git diff data/demo.db` show nothing changed — the migration silently landed only in `data/demo.db-wal`.
**Why it happens:** This has fired repeatedly across Phases 3 and 4 per STATE.md's own history; `better-sqlite3` in WAL mode does not flush to the main file on connection close by default.
**How to avoid:** End the migration script with `conn.pragma('wal_checkpoint(TRUNCATE)')` before `conn.close()`, exactly as `scripts/seed-dd-request-templates.js:50` already does. Verify with `git status --porcelain data/` (currently clean, confirmed this session) before AND after running the script.
**Warning signs:** Script exits 0, but `git diff --stat data/demo.db` shows 0 changes when a data change was clearly intended.

### Pitfall 4: A missing schema registration silently 500s a new route
**What goes wrong:** Adding a new Express route (e.g. `POST /api/synergies/:id/rebaseline`) without a matching `registerSchema()` call causes every request to that route to fail with a 500 and the specific error `"No schema registered for POST /api/synergies/:id/rebaseline — refusing rather than passing an unvalidated write through (VAL-01)."`
**Why it happens:** `validationMiddleware` (`validators/index.js:318-339`) is mounted globally and fails CLOSED by design — this is intentional (VAL-01), not a bug, but it means every new POST/DELETE route needs its registration landed in the SAME commit as the route itself, or local dev testing of the route will 500 immediately.
**How to avoid:** For each new route, add its `registerSchema()` call in `validators/workstream.js` in the same task/commit that adds the route in `server.js`.
**Warning signs:** A curl/fetch test against a brand-new route returns `500` with a validation-registry error message, not a 404 or a 400.

### Pitfall 5: A stage-value migration one-copy-behind
**What goes wrong:** Updating `server.js:3043` and `validators/workstream.js:114` to the new 4-value vocabulary but missing `public/js/execution.js:28-30` (or vice versa) leaves the client rendering/cycling through the wrong set of values while the server accepts/rejects a different set — a request the UI thinks is valid gets rejected, or the UI never offers a transition the server would accept.
**Why it happens:** This is the exact triplication CONTEXT.md and this document's Finding #1 both name explicitly — it is a documented, repeat failure mode in THIS codebase (the RAID `D-26` precedent, `validators/workstream.js:139-147`, exists specifically because this happened before with `RAID_LEVELS`).
**How to avoid:** Change all three copies in the same task/commit; the plan should list all three file:line locations explicitly in one task's action list (not split across separate tasks), mirroring how D-26's RAID widening was executed as one atomic change.
**Warning signs:** `grep -c "idea\|validated\|committed\|captured"` returning a different count in `server.js` vs `public/js/execution.js` after the change.
