<objective>
Give every write that lands in a real deal an attributable, append-only record: a store-layer hook on `writeDb()` that reuses the before/after values the existing snapshot-diff merge already computes, writing them as a batch into the separate `audit.db`; explicit security-event records for the control-plane actions D-08 names; and an admin-only filterable viewer.

Purpose: AUD-01 and AUD-02 are the compliance controls that make MNPI handling defensible, and there is currently zero audit code in this codebase. The mechanism choice was left to the planner's discretion; 03-RESEARCH.md's verified finding that SQLite gives no cross-database atomicity in WAL mode is why this is a store-layer hook rather than ATTACH-based triggers.
Output: `db/auditHook.js`, the `writeDb()` extension, security-event call sites, the admin viewer, and two node:test proofs.
</objective>

  <name>Task 1: Confirm the audit store's location and semantics before history starts accumulating (D-09 reversibility gate)</name>
  <decision>Approve the audit mechanism and storage location that the compliance record will be written into from this point on.</decision>
  <context>
    D-09 is rated one-way in CONTEXT.md: the audit trail is a compliance record, and relocating it later must not lose or rewrite history. Three specifics are worth a deliberate yes before the first row is written:

    (a) **Location and shape.** A dedicated `data/audit.db`, gitignored and zip-excluded, physically outside every deal file, with append-only enforced by SQLite ABORT triggers (Plan 03-01) so no code path — including an admin one — can rewrite history. Full before/after row JSON per entry (D-11).

    (b) **Mechanism.** A store-layer hook on `writeDb()` rather than SQLite triggers with ATTACH. 03-RESEARCH.md verified against sqlite.org that a WAL-mode database gives no cross-file atomicity even with ATTACH, so triggers would add per-connection bookkeeping and a SQL-side actor-context table for no atomicity gain, while the hook reuses the before/after values `writeDb()` already computes.

    (c) **The accepted trade-off.** This is best-effort, not two-phase commit. The audit row is written only after the source transaction commits, so a rolled-back write is never audited; but a crash in the window between the two commits loses that one entry while the underlying write still lands. Tamper-evidence and hash chaining are explicitly deferred to the shared-host milestone per CONTEXT.md. Task 2 surfaces an audit-write failure loudly rather than swallowing it, which is the mitigation available without a distributed transaction.
  </context>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| deal database commit → audit.db commit | Two independent single-file commits; the gap between them is where an entry can be lost |
| request identity → audit row actor | If the actor can be influenced by the client, every row in the trail becomes deniable |
| admin console → audit rows | The party with the strongest motive to alter history is the one with admin rights |
| deal deletion → audit store | The compliance record must outlive the thing it describes |
