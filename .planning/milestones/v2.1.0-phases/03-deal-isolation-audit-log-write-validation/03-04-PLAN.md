<objective>
Put a usable control plane on top of the resolver: the deal registry API (create, list, select, membership, archive, delete) with role tiers per D-02, membership scoping per D-03, and the small header deal switcher plus minimal create-deal form per D-04 — deliberately separate from the demo Projects UI. Also lands `validators/deals.js`, the first zod schema module, which Plan 06 generalizes across every remaining write endpoint.

Purpose: the resolver from Plan 03 is only reachable through a session's `deal_id` column. Without these routes and this UI there is no way for an Integration Lead to create a deal, join it, or switch into it — the isolation is real but unusable.
Output: six routes, four control-store registry helpers, the first zod validator module, the switcher UI, and two node:test proofs.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated caller → deal registry | The registry names pre-announcement acquisition targets; the list response itself is MNPI-bearing |
| caller-supplied dealId → session binding | A request body value decides which MNPI store the caller's subsequent requests reach |
| admin request → deal deletion | An irreversible destruction of an acquisition workspace with no other copy |
| browser DOM → deal names and target companies | User-controlled strings rendered into the app header on every page |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-17 | Information Disclosure (target name leak to a non-member) | GET /api/deals | critical | mitigate | The list is built from `listDealsForUser()` and never from the full registry for a non-admin; the refusal path for a non-member select returns a generic message that does not confirm the deal exists; asserted by case (e) of test/deal-registry.test.js |
| T-03-18 | Elevation of Privilege (self-binding to a deal you are excluded from) | POST /api/deals/select | critical | mitigate | Membership is re-checked server-side on select and again at bind time by the Plan 03 resolver — two independent checks, neither trusting the client; a refused select leaves the prior binding untouched |
| T-03-19 | Elevation of Privilege (unauthorized deal creation) | POST /api/deals | high | mitigate | ROLE_WRITE_POLICY entry restricting creation to admin and hrbp per D-02, enforced in the existing consolidated gate before the handler runs; asserted by case (f) |
| T-03-20 | Denial of Service / destructive loss | DELETE /api/admin/deals/:id | high | mitigate | Admin-only via the existing `/api/admin` rule PLUS a destructive guard requiring the deal's own id as an explicit confirmation value; asserted by case (b) of test/deal-lifecycle.test.js |
| T-03-21 | Repudiation (audit trail destroyed with the deal) | deleteDeal | high | mitigate | The delete path removes only the registry row and the deal file and holds no reference to the audit store at all (AUD-02 by construction); asserted by a source check that the control store never names the audit database |
| T-03-22 | Tampering (stored XSS via a deal name rendered in the header) | deal-switcher.js | medium | mitigate | All user-controlled strings set via textContent (repo-wide discipline), backed by the existing CSP; write-time sanitization for HTML-bearing fields lands in Plan 06 |
| T-03-23 | Tampering (registry row pointing at a missing file) | POST /api/deals | medium | mitigate | Registry insert is rolled back if database provisioning throws, so a half-created deal is never left selectable |
| T-03-SC | Tampering | npm/pip/cargo installs | low | accept | No new package; zod was gated and installed in Plan 03-01 |
</threat_model>
