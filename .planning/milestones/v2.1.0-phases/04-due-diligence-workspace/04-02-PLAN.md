<objective>
Give the clean-room a management surface: the deal's Integration Lead and an admin can hand a named member
need-to-know for named DD areas, take it away again, and every one of those decisions lands in the audit log.

Purpose: Plan 01 built the filter but left `deal.memberGrants` writable only by direct SQL. DD-04 is not
satisfied until a real operator can administer clearance, and D-02 requires every grant and revoke to be a
security event. This plan also proves D-23's central bet — that adding `memberGrants` alongside
`deal.members` breaks none of the four verified call sites that read `members` as a flat string array.

Output: `setDealMemberGrants`/`getDealMemberGrants`, the two grant routes, the admin Deals-tab editor, and a
regression suite covering both the grants themselves and the untouched `members` shape.
</objective>

<interface_contract>
- `setDealMemberGrants(dealId, username, ddAreas)` (db/controlStore.js) -> the updated deal object. Throws
  (never silently no-ops) when the deal does not exist, mirroring `updateDealMembers()`'s stated
  not-an-upsert contract. De-duplicates `ddAreas` into a set and preserves `DD_AREAS` declaration order.
  Writes `data.memberGrants[username] = { ddAreas }` and leaves `data.members` untouched.
- `getDealMemberGrants(dealId)` -> the whole `memberGrants` map, or `{}` when absent.
- `POST /api/deals/:id/grants` body: `{ username: string, ddAreas: string[] }`. A revoke is the same call with
  a shorter (or empty) `ddAreas` array — there is no separate revoke route; the audit event name is chosen by
  comparing before and after.
- Audit actions: `dd-area-grant` when the new set is a strict superset of the old, `dd-area-revoke` when it is
  a strict subset, `dd-area-grants-update` for any other change. `before` is the prior array, `after` the new
  array. No event is recorded when before and after are equal.
- `GET /api/deals/:id/grants` -> `{ members: [{ username, ddAreas }] }`, one entry per name on
  `deal.members`, with an empty `ddAreas` for members holding no grant.
</interface_contract>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> /api/deals/:id/grants | An authenticated admin or IL supplies a username and an area list |
| grants route -> control.db deal record | The authoritative clearance store every DD read consults |
| grants route -> audit.db | The accountability record for who opened a clean-room door |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-09 | Elevation of Privilege | `POST /api/deals/:id/grants` | critical | mitigate | ROLE_WRITE_POLICY's `/api/deals` prefix limits the route to admin and hrbp; a username absent from `deal.members` is refused, so clearance can never exist without membership |
| T-04-10 | Repudiation | grant/revoke | high | mitigate | One `recordSecurityEvent()` per real change with before and after arrays; the required-actor contract makes an anonymous grant impossible |
| T-04-11 | Elevation of Privilege | stale clearance after revoke | high | mitigate | `grantedAreas()` reads control.db per request; the grant is never copied onto the session row or into the deal database, so revocation is effective on the next request |
| T-04-12 | Tampering | grants payload | medium | mitigate | `DealGrantsSchema` constrains `ddAreas` to a `z.enum` over the eight taxonomy ids imported from `db/accessPolicy.js`; unknown keys stripped; array length capped |

| T-04-14 | Information Disclosure | admin grants panel | low | mitigate | `textContent`-only rendering of usernames and labels; the panel only ever displays members already visible on the same tab |
