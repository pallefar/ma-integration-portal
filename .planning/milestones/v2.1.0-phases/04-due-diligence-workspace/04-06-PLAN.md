<interface_contract>
- Pending instance shape: the existing `assessmentInstances` row gains `owner` (string), `dueDate`
  (`YYYY-MM-DD` string) and `status` set to `pending`. A pending row has NO `responses` key and none of the
  score fields the scorer produces. Existing submitted rows are untouched and keep `status` set to `submitted`.
- `POST /api/assessment-instances/assign` body: `{ templateId, owner, dueDate }`. Response
  `{ success: true, instance }` with the response-stripping helper applied, status 201.
- `POST /api/assessment-instances` gains an OPTIONAL `instanceId`. When present, the handler finds that row,
  requires its status to be `pending` (otherwise 400), attaches `responses` and the scorer's output, sets
  status to `submitted`, stamps the timestamp, and returns it — pushing nothing onto the lane. When absent,
  the route behaves exactly as it does today.
- `latestAssessInstanceFor()` considers only rows whose status is `submitted`.
- `GET /api/assessment-status` per-template entry gains `pending`: an array of
  `{ id, owner, dueDate }` for that template's pending instances. `satisfied` stays derived from submitted
  instances only, so a pending assessment never satisfies a gate.
- `WIZARD_ASSESSMENT_SUBJECTS` (server.js): the declared order `['acquirer-org', 'target-org', 'il']` used by
  the status rollup to order its report. Templates are matched to it by their existing `subject` field.
- `deal.setup` on the control.db deal record:
  `{ steps: { basics, team, assessments, scope, timeline, ddKickoff }, complete: boolean }` where each step
  value is `null` or `{ at: ISO string, by: username }`. `basics` and `team` are stamped by the create route;
  the rest by the setup route.
- `createDeal()` additionally accepts and stores `dealType`, `signingDate`, `expectedClose`, `day1Date`,
  `dealSizeM` and `currency`, all optional, plus the `setup` skeleton.
- `POST /api/deals/wizard/basics` VALIDATES ONLY. It persists nothing, audits nothing, and echoes back
  `{ success: true, basics }`. Its sole purpose is to give the wizard's first step a server-side rule set
  rather than a duplicated client-side one (D-07).
- `POST /api/deals/:id/setup` body: `{ step: string, data?: object, complete?: boolean }`. `step` is one of
  the six step names. Merges into `deal.setup`, stamps the step, and sets `complete` when every mandatory step
  is stamped or when `complete` is explicitly true.
</interface_contract>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> wizard step routes | An operator supplies deal identity, dates, membership and assessment ownership; the target's identity pre-announcement is the most sensitive value in the app |
| create route -> control.db plus the deals directory | A deal record and a new database file are provisioned together; a half-created deal is a broken workspace |
| assessment routes -> assessmentInstances | A pending row must never be mistakable for a real result |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-32 | Tampering | `POST /api/assessment-instances` with an instanceId | high | mitigate | Completion is refused unless the target row's status is pending, so a submitted, scored, compliance-relevant record can never be silently rewritten through this path |
| T-04-33 | Spoofing | fabricated assessment results | high | mitigate | The assign route calls no scorer and sets no score field; a pending row is identified by the ABSENCE of a score, so a zero can never be read as a real result |
| T-04-34 | Elevation of Privilege | wizard step routes | high | mitigate | All three new deal routes sit under the existing `/api/deals` role rule (admin and Integration Lead only) and are control-plane paths, proven by a pmo-refusal case |
| T-04-35 | Tampering | wizard step payloads | medium | mitigate | `WizardBasicsSchema` and `DealSetupSchema` registered in the shared registry; the step name is enum-constrained; the basics route's bounds are declared to match the create schema's so the two cannot diverge |
| T-04-36 | Information Disclosure | a target's real name pre-announcement | medium | accept | The wizard encourages a project codename over the target's real name through helper text rather than enforcement (04-CONTEXT.md "Specific Ideas") — enforcing it would block legitimate post-announcement deals; the mitigation is the clean-room and the audit trail, not a name filter |
| T-04-37 | Repudiation | setup progress | low | mitigate | Each setup step change records a `deal-setup-update` security event with the step as subject and the prior and new values |
| T-04-38 | Denial of Service | a half-created deal | medium | mitigate | The existing create route's provisioning rollback is unchanged: a failed database provisioning deletes the registry row, so no record can point at a missing file |
</threat_model>
