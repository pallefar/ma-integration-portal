## Decisions Made

- **`ownerHint` role mapping:** Tax's items carry `ownerHint: 'Finance'` — the interface contract lists exactly seven role strings (Legal, Finance, HR, IT, Commercial, Operations, Compliance) for eight areas, and Tax has no dedicated role, mirroring 04-RESEARCH.md's own `ws_finance` fold-in for the identical reason.
- **`seedDdRequestTemplates()`'s `{ inserted }` counts items, not rows:** the row count is always exactly 1 by construction (idempotent replace); the item count (80) is what a CLI operator or a future caller actually wants surfaced.
- **`GET /api/dd/request-templates` is unfiltered:** a template is a standard list with no MNPI content — only the instantiate route, which creates real per-area items, is clearance-gated.
- **The checklist-load control is gated workspace-wide, not per-area:** `totalItemCount() === 0` across every cleared area, so the control disappears as soon as the IL has started their own list by any means (seeded or manually added), rather than persisting as bulk-add clutter alongside a partially-built list.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The seed script's write never reached the committed `data/demo.db` file — it landed only in the gitignored WAL sidecar**
- **Found during:** Task 1 (verifying `data/demo.db`'s tracked-file diff after the first seed run)
- **Issue:** `openDbFile()` opens every SQLite file under WAL mode. Without an explicit checkpoint, a write is durable (crash-safe) but physically lives in the `-wal` sidecar until SQLite's own automatic checkpoint threshold or another writer forces one — and `data/*.db-wal`/`-shm` are gitignored by design (T-03-01's sidecar exclusion). The committed `data/demo.db` file itself stayed byte-identical to HEAD after the first run, which would have made `git status --porcelain data/demo.db` (an explicit Task 1 acceptance criterion) show nothing changed — silently failing to ship the seeded row.
- **Fix:** Added `conn.pragma('wal_checkpoint(TRUNCATE)')` to `seedDdRequestTemplates()` after the insert transaction, folding the write back into the main file and clearing the sidecar, before `conn.close()`.
- **Files modified:** `scripts/seed-dd-request-templates.js`
- **Verification:** `git status --porcelain data/demo.db` showed `M` after the fix; a fresh readonly connection to `data/demo.db` read the row back with no server process running.
- **Committed in:** `14e1672` (Task 1 commit)

**2. [Rule 1 - Bug] The first checkpoint attempt folded in unrelated stale WAL content from a prior, unrelated session**
- **Found during:** Task 1, immediately after fixing Deviation 1 above
- **Issue:** `data/demo.db-wal` already existed on disk (dated the same day, larger than a fresh WAL) before this plan touched anything — leftover from an earlier, unrelated manual smoke-test session against the real server (an `en.smoke.test.key` string and a malformed `123` key had been written into the `i18n` singleton and never checkpointed or discarded). Running `wal_checkpoint(TRUNCATE)` against the file as first attempted would have folded BOTH my own seed row AND that unrelated pollution into the commit — the pollution was verified present via a before/after diff against `git show HEAD:data/demo.db` (only `ddRequestTemplates` should differ; a diff scan additionally found `i18n` had changed).
- **Fix:** `git checkout -- data/demo.db` to restore the tracked file to HEAD, deleted the stale `-wal`/`-shm` sidecars (gitignored, disposable), then re-ran the (now-fixed) seed script against the clean file. A full collection-by-collection + singleton-by-singleton comparison against `git show HEAD:data/demo.db` afterward confirmed the only difference was the new `ddRequestTemplates` row (plus three new empty `dd*` tables created by the shared schema's idempotent `CREATE TABLE IF NOT EXISTS`, which predate this plan by design — Plan 01 added them to `db/schema.sql`, they simply hadn't been materialised inside this particular file yet).
- **Files modified:** `data/demo.db` (reset then correctly re-seeded)
- **Verification:** A programmatic diff (every `ARRAY_COLLECTIONS` row + every `SINGLETON_KEYS` singleton, `git show HEAD:data/demo.db` vs. the working copy) printed "CLEAN: no other row-level or singleton diffs vs HEAD" after the fix. `npm test` 151/151 immediately after.
- **Committed in:** `14e1672` (Task 1 commit)

**3. [Rule 1 - Bug] `test/deal-seed.test.js`'s fixture had no `ddRequestTemplates` rows, so its own row-count-parity assertion broke the moment the allowlist grew**
- **Found during:** Task 2 (extending `DEAL_SEED_COLLECTIONS`)
- **Issue:** `test/deal-seed.test.js`'s `(a)` subtest asserts every allowlisted collection has a matching, non-zero row count between the synthetic source fixture and the newly created deal. Adding `ddRequestTemplates` to the allowlist made the test iterate a collection its own fixture never populated — a pre-existing test directly invalidated by this plan's own change, not a pre-existing/out-of-scope failure.

The `(c)` subtest's "every non-seeded collection is empty" count is computed dynamically (`ARRAY_COLLECTIONS.length - DEAL_SEED_COLLECTIONS.length`), so it needed no hardcoded-number update.
- **Files modified:** `test/deal-seed.test.js`
- **Verification:** `node --test test/deal-seed.test.js` green (6/6); full suite 151/151.
