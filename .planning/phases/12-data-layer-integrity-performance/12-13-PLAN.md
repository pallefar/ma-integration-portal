## Planner decisions (this plan)
- **PD-22** Migration #1 moves a row iff `db_kind = 'deal' AND deal_id IS NOT NULL`; target = that deal's partition
  when the deal is still in control.db, else `legacy`. It takes the runner's `VACUUM INTO` backup first, imports by
  `legacy_id` (idempotent across a crash), seals `legacy` through db/auditLifecycle.js with actor
  `system:migration`/`system`, rebuilds audit.db with original ids preserved and chained (genesis 'control'), creates
  indexes and append-only triggers inside the same transaction, and verifies both chains before committing.
  Revision 1 (checker W-4): per target whose partition file already exists, the migration first reads `MAX(legacy_id)`
  and the sealed state through `dbFiles.openDbFileReadOnly` (never a read-write open of a possibly 0400 sealed file);
  it opens read-write (`openDbFile`) ONLY when rows remain to append — which by construction never happens for a
  sealed partition (the seal runs after every import); a sealed target that still has rows to import throws
  ('legacy-sealed-incomplete' → not-ready) instead of writing.
- **PD-25** audit.db v1 chain columns are nullable (partitions keep NOT NULL): compatibility with the raw-insert test and
  with a rollback release; verifyChain treats a missing hash as `unchained-row` (a verification failure). Revision 1
  (checker I-2): appendChained chains from the most recent row that HAS a `row_hash` (12-08 PD-30), so a raw-inserted
  or rollback-release row never leaves the next chained row's `prev_hash` undefined; verifyChain reports each hashless
  row once as `unchained-row` and links across it.
- **PD-2 / PD-3** (defined in 12-08) apply to audit.db from this plan on: every control-plane event, incl. the denial
  auditor's rows from several processes, is appended through `appendChained(…, { partitionId: 'control' })`.
- **PD-31** (revision 1, checker W-2) The migration's cost is rehearsed on a SYNTHETIC v0 audit file produced by a
  committed generator — never the developer's real data/audit.db (executors run in worktrees where it does not exist,
  and a real MNPI file must not feed a test artifact). Size: default 150,000 rows of ~1 KB (≈ 170 MB, ~2× the
  developer's 86 MB file), ~1,000 deal ids (80 % of deal rows on deals present in the generated control.db, 20 % on
  absent deals → legacy), 5 % control rows; `--rows` capped at 300,000 so peak scratch (original + backup + partitions
  + their WAL ≈ 4× the file) stays ≤ ~1.5 GB on this nearly full host. The rehearsal refuses to start unless free space
  ≥ projected peak + 1 GB, and removes its temp tree in a `finally` and on SIGINT/SIGTERM. Results are extrapolated
  linearly to the 5 GB worst case and labelled as an extrapolation.
