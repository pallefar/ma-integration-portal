## Planner decisions (this plan)
- **PD-7** Sealing requires the deal to be archived or deleted from the registry; seal = chained `partition-seal`
  final row → `wal_checkpoint(TRUNCATE)` → close → chmod 0400 (Windows read-only attribute) → SHA-256 of the main file →
  `audit-partition-sealed` control event {sha256, rows, headHash}. Re-sealing is idempotent and repairs a missing event.
  There is no unseal.
  Revision 1 (checker W-3): `PRAGMA wal_checkpoint(TRUNCATE)` reports `{ busy, log, checkpointed }`; `busy = 1` (another
  connection — e.g. the server's cached RW partition handle while the CLI seals from a second process — holds a read
  snapshot) or `checkpointed < log` means the WAL was NOT folded into the main file, and hashing then would record a
  SHA-256 that changes when the last connection later checkpoints on close (a false `sealed-sha=MISMATCH` /
  `modified-after-seal`, purge refused forever). So `sealPartitionFile` is synchronous (the 12-13 migration calls it
  inside a sync `up()`) and: (1) PRE-CHECK — before appending anything, run the TRUNCATE checkpoint and accept only
  `busy === 0 && checkpointed === log`, retrying 3 × 250 ms (synchronous wait via `Atomics.wait` on a
  SharedArrayBuffer; ≤ 750 ms, a rare admin action); still busy → throw `AuditSealRefusedError` reason
  'checkpoint-busy' with NOTHING appended, chmodded or hashed (file stays writable and unsealed); (2) append the seal
  row; (3) checkpoint again with the same acceptance + retries; still busy → refuse 'checkpoint-busy' WITHOUT chmod or
  hash — the seal row is committed, so appends are already refused (the backstop), and a repeated seal completes the
  file seal idempotently (the existing "last row already is a seal row" path); (4) close → chmod 0400 → SHA-256. Routes
  map 'checkpoint-busy' to 409 `{ error: 'The audit trail is in use; try sealing again in a moment.', reason:
  'checkpoint-busy' }` + an `audit-partition-seal-refused` event.
- **PD-8** Lifecycle routes are `GET /api/admin/deals/:id/audit`, `POST …/audit/seal`, `GET …/audit/export`,
  `POST …/audit/purge` — never under `/api/admin/audit*`, whose GET-only inventory is a Phase 3 test contract; the
  resolver already treats `/api/admin/deals/` as control-plane.
- **PD-9** Purge refusal order and codes: not-sealed → modified-after-seal (+ `audit-partition-tamper-detected`) →
  no-sealed-export (an `audit-partition-exported` event whose sealedSha256 equals the current seal) → retention-never →
  retention-not-elapsed; each refusal is a control event. `MA_AUDIT_RETENTION_DAYS`: unset, `never` or invalid (warning
  once) ⇒ never; a positive integer ⇒ days counted from the seal event. A permitted purge records
  `audit-partition-purged` BEFORE deleting the files. No timer, scheduler or boot hook ever purges.
