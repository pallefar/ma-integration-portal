## Planner decisions (this plan)
- **PD-10** An unparameterized list response is assembled from the stored raw JSON strings (`'[' + raws.join(',') +
  ']'`), byte-identical to `res.json(parsed)` because each stored `data` is exactly `JSON.stringify(item)`; visibility
  is computed from json_extract projections (clearanceArea, source) through ONE shared predicate also used by
  `reportRaidRows` (WR-04 "one filtered read path"). Arithmetic: parse + re-stringify of 1.6 MB ≈ 20 ms per call, so ten
  of them alone would consume most of the 300 ms p95 budget.
- **PD-11** `readCollections()` defines non-enumerable throwing accessors for every collection it did not load, so a
  handler that touches an unlisted lane fails loudly in the existing suites instead of seeing an empty array (an empty
  lane is a fail-open clearance risk). writeDb() on such an object writes only the loaded collections.
- **PD-12** List query: recognised keys limit, offset, status, owner, workstream, phase, q; none present ⇒ the legacy
  array; `limit` 1..200; `offset` ≥ 0 and only together with `limit` (else 400); status/phase from the route's enums;
  owner/workstream exact match; q = case-insensitive substring over title + notes evaluated in JS; other keys
  ignored; order of operations visibility → filters → total → page.
- **PD-13** The perf scripts reproduce the review's scratch profiles verbatim (R5 perf2.js 10×3; R2 load-probe.js Phase
  A; R2 runner.js eld resolution 5 ms) on byte copies of the committed demo/control databases; a budget passes only if
  it holds in EVERY one of 3 runs (stricter than a single run, never a median of runs).
