<objective>
Move deal audit into hash-chained per-deal partitions (D-12-04, core half): routing, chaining, the atomicity seam,
the cross-partition admin viewer, a verify CLI, and the soak proving Phase 8's guarantees still hold. Seal/export/
purge are plan 12-12; migrating the legacy single file and chaining audit.db is plan 12-13.

Purpose: DATA-04 / R2-01 / R2-10 / PR-09 — one unbounded append-only file of MNPI snapshots with no tamper evidence and
no per-deal lifecycle. This plan resolves the two hard seams explicitly:
(a) ATOMICITY — PD-1: the partition append runs, exactly like today's audit.db append, as the final step inside the
deal's `.immediate` transaction on the partition's OWN connection. No cross-file link (03-RESEARCH: no cross-file
atomicity under WAL; test/audit-log.test.js forbids that keyword in auditHook.js). Lock order is always deal file →
partition, and the partition is always the innermost lock (seal and migration take only partition/audit locks), so no
wait cycle exists. A throw from the append rolls the deal write back → nothing persisted → the client's identical
retry is safe (CR-01). The accepted residual is unchanged: a disk-level failure of the deal COMMIT after the partition
commit leaves an audited-but-uncommitted row, never a committed-but-unaudited one; the soak's 1:1 check detects either.
(b) WHERE CONTROL EVENTS GO + TWO WRITERS — PD-2/PD-3: recordSecurityEvent() rows (deal lifecycle, grants, reads,
Phase 11 `access-denied`) stay in audit.db; they are written outside any deal write, can concern archived, sealed or
non-existent deals and anonymous actors, and must never create a partition file from a probe. Their deal context
stays in `deal_id`, and the viewer joins them by that column. A chain stays valid with several writers because every
append = BEGIN IMMEDIATE → read the head row → insert chained rows → commit: SQLite's file write lock linearises all
appenders across threads and processes.
</objective>

## Planner decisions (this plan)
- **PD-1** Atomicity seam: the partition append is the FINAL statement inside the deal's `.immediate` transaction,
  executed as its own BEGIN IMMEDIATE on the partition's own connection (exactly Phase 8's CR-01 audit.db mechanism).
  Cross-file links are rejected (03-RESEARCH: no cross-file atomicity under WAL; test/audit-log.test.js scans
  auditHook.js for that keyword). Lock order is always deal → partition; the partition is the innermost lock (seal and
  the 12-13 migration hold only audit/partition locks), so no wait cycle can form. Residual unchanged: only a
  disk-level failure of the deal COMMIT after the partition commit yields an audited-but-uncommitted row.
- **PD-2** Every `recordSecurityEvent()` row — lifecycle, grants, reads, CLI/token use and Phase 11 `access-denied`
  (written outside any deal write, possibly for archived, sealed, non-existent deals or anonymous actors) — stays in
  audit.db with its `deal_id`; partitions receive only writeDb data deltas and lifecycle rows; a partition file is
  created only by an audited write in a resolved deal context. The viewer's `?deal=` joins partition rows with the
  control rows carrying that deal_id.
- **PD-3** Chain: `row_hash = sha256(JSON.stringify([ts, actor_username, actor_role, session_id, deal_id, db_kind,
  action, collection, row_id, before_json, after_json, request_method, request_path, ip, legacy_id, prev_hash]))`;
  genesis `sha256('ma-audit-genesis|' + partitionId)`; partitionId (deal id, `legacy`, `control`) derived from the file
  name by the verifier; every append reads the head row under BEGIN IMMEDIATE, which linearises all writers in all
  processes. No genesis row is written (row counts per change stay exact).
- **PD-4** `AUDIT_DIR` = `MA_AUDIT_DIR` if set, else `<dirname(MA_AUDIT_DB_PATH)>/audit` when only MA_AUDIT_DB_PATH is
  set (every existing isolated suite, the soak and the UAT lanes isolate partitions with no edit), else
  `<data dir>/audit` (data/real/audit in real mode).
- **PD-7 (backstop half)** A partition whose last row is `partition-seal` refuses every append (AuditPartitionSealedError
  → 409 fixed body); `chmodPrivateFile` becomes tightening-only so a sealed 0400 file is never re-opened writable.
- **PD-21** scripts/soak.js edit is limited to reading checks 2/4/8 from the deal partition, checkpointing/closing it,
  and adding check 10 (chain verifies); every existing check, threshold and message is unchanged.
- **PD-29** (revision 1, checker B-1) audit.db is never first-opened inside a deal write: writeDb() calls
  `auditHook.getAuditConnection()` BEFORE `applyWrite(data)` whenever the write is audited (`deltas !== null`) — a cache
  hit in a server process (12-06 opened it at boot), the first open (and any audit migration) in a CLI / store-level
  test / soak child, in both cases outside the deal lock. `getPartitionConnection(dealId)` never opens audit.db: it
  asserts `auditHook.isAuditOpen()` and otherwise throws `DbNotReadyError` (db/readiness.js, reason 'audit-not-open',
  NOT recorded via markNotReady — it is an invariant breach, not a file failure) without creating any file. Partition
  files themselves may be first-opened inside the deal transaction: lock order deal → partition is the established
  order, and the partition family has only the stamp-only baseline (bounded per-deal work).
- **PD-30** (revision 1, checker I-2) Chain head rule, shared by partitions and (from 12-13) audit.db: `prev_hash` =
  `row_hash` of the most recent row that HAS one (`WHERE row_hash IS NOT NULL ORDER BY id DESC LIMIT 1`), else the
  genesis; the seal check reads the absolute last row. `verifyChain` reports every hashless row as `unchained-row`
  (ok = false) and links the next chained row to the last hashed row, so one raw insert is reported once and never
  makes the following rows' `prev_hash` undefined. Partitions declare the hash columns NOT NULL, so there the rule is
  inert; it matters for audit.db's nullable columns (12-13 PD-25).
