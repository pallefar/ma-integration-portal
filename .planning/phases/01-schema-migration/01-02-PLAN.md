<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP client → /api/* → readDb/writeDb → SQLite | Request-derived values reach the SQL layer |
| operator → migration script → SQLite | The offline migration reads the source db.json snapshot and writes a new database |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Tampering | db/store.js + migration SQL layer | high | mitigate | Every query uses better-sqlite3 `.prepare(sql).run(...params)` / `.all(...params)`; no request-derived value is ever concatenated into SQL. Table names come only from the fixed db/collections.js inventory, never from input. |
| T-01-03 | Tampering (self-inflicted data loss) | scripts/migrate-db-json-to-sqlite.js source handling | high | mitigate | The migration reads the source via readFileSync/--source ONLY and writes only the --out path (temp-then-finalize); code review confirms no fs.writeFileSync/copyFileSync targets the source path. db.json is retained as a read-only archive. |
| T-01-04 | Denial of Service | concurrent SQLite writers (WAL lock contention) | low | mitigate | busy_timeout=5000 pragma set at open; single-process WAL mode; the transactional per-collection merge keeps write scope tight (only changed collections). |
| T-01-02 | Information Disclosure | new data/ma-portal.db + WAL/SHM sidecars | high | mitigate | The .gitignore + download-zip exclusions landed in Plan 01 (wave 1); only the demo data/ma-portal.db is committed (same precedent as db.json). Verified again at the Plan 03 cutover. |
</threat_model>
