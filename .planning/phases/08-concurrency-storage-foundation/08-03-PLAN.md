<objective>
Make D-06's claim — "one central middleware covers every write path" — actually true, and make it stay true.

Purpose: 08-RESEARCH.md found the claim is false today for a set of routes whose own `try/catch` converts any write failure into a hand-written `500` with no `Retry-After`. Those blocks pre-date this phase and were written to catch provisioning and validation failures; nobody anticipated `writeDb()` throwing a *retryable* error. Express 4 also does not auto-forward rejections from `async` handlers, so the two async write routes need explicit forwarding. Without both fixes the client's retry logic (plan 08-04) never fires on those routes and the user sees a dead-end 500 on transient contention.
Output: re-throw guards at every storage-wrapping catch site, explicit error forwarding on the async write routes, and a permanent coverage gate that turns red when a future route re-opens the hole.
</objective>

    Two placement rules that are not mechanical:
    - Where the catch performs a compensating action, the guard goes AFTER the compensation, not before it. At the deal-provisioning site the catch rolls the registry row back with `controlStore.deleteDeal()` precisely so a half-created deal is never left selectable; that rollback must still run on a contention failure, and only then is the error re-thrown in place of the hand-written 500. Losing the rollback would be a worse bug than losing the 503.
    - Where the try body mixes storage work with unrelated work (the media upload wraps base64 decoding and `fs.writeFileSync` alongside `writeDb`), keep the existing generic handling for the non-storage failures. The guard narrows the catch, it does not replace it.

    Then handle async forwarding (08-RESEARCH.md Pitfall 2). Enumerate the `async` write handlers — `grep -nE "app\.(post|put|patch|delete)\(.*async" server.js` currently reports `POST /api/rag/upload` and `POST /api/assessment`. Express 4.19.2 only wraps the synchronous invocation of a handler, so a rejected promise from these never reaches the error chain on its own. Give each an explicit forwarding path: either an outer `try { ... } catch (e) { return next(e); }` around the handler body, or a `.catch(next)` on the returned promise — and add `next` to the handler signature where it is missing. A guard that re-throws inside an async handler with no forwarding is worse than no guard, because the rejection becomes an unhandled promise rejection instead of a 503.

    Do not change any success-path response shape, any status code other than the swallowed 500s, or any validation. Add a `[security]`-prefixed comment at the first guard site explaining the D-06/D-11 contract in mitigation terms — that contention is retryable and must reach the client as 503 with a retry signal, and that converting it to 500 silently denies the client its retry path.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Express `/api` | Every write route's error response crosses back out here; the 503 body is attacker-visible |
| Express route handler → central error middleware | The internal boundary this plan repairs — a local catch that responds directly never crosses it |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-01 | Information Disclosure | 503 response body across all write routes | high | mitigate | Central middleware returns a fixed generic string; `test/busy-503-contract.test.js` asserts on every driven route that the body contains no filesystem path, no SQLite error text, and no deal identifier. A SQLite path or deal id in an error body leaks a pre-announcement MNPI target name. |
| T-08-09 | Denial of Service | routes whose catch swallows contention | medium | mitigate | A dead-end 500 denies the client its documented retry path, turning transient contention into a permanent user-visible failure and losing the write. Re-throw guards plus the coverage gate close it and keep it closed. |
| T-08-10 | Denial of Service | `async` write handlers under Express 4 | medium | mitigate | An unforwarded rejection becomes an unhandled promise rejection — the request hangs until the client times out rather than receiving a bounded 503. Explicit `next(e)` / `.catch(next)` forwarding, asserted structurally. |
| T-08-11 | Tampering | deal-provisioning rollback path | high | mitigate | The compensating `controlStore.deleteDeal()` rollback must still run before the re-throw; skipping it on a contention failure would leave a half-provisioned deal selectable in the registry — a deal row with no database behind it. Guard placement is after compensation, asserted by the existing deal-registry and deal-lifecycle suites staying green. |
</threat_model>
