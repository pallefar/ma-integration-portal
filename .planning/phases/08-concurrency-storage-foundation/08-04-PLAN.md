<objective>
Make routine contention invisible, and persistent failure honest.

Purpose: the server-side half of this phase turns lock contention into a `503 Retry-After` — a signal that is only useful if something acts on it. D-07 puts that responsibility in the one JavaScript file loaded on every page, inside the fetch interceptor that already exists there, so every write in the app inherits it without touching a single call site. D-08 covers the other end: when contention is not transient, the user must learn that their change was not saved while still holding the unsaved work in front of them.
Output: a bounded, jittered retry branch and a small give-up toast inside `public/js/transitions.js`'s existing fetch wrapper, plus a behavioral test that drives the wrapper in isolation.
</objective>

  <action>
    Extend the EXISTING `window.fetch` override — do not add a second one. A competing interceptor would race the auth-bridge wrapper and one of the two would win non-deterministically depending on script order.

    First, delimit the wrapper for testability: put a sentinel comment line containing `ma-fetch-wrapper:begin` immediately before the IIFE that starts at line 13, and one containing `ma-fetch-wrapper:end` immediately after its closing `})();`. These are the extraction markers plan 08-04's test slices on; they carry no runtime behavior.

    Inside that same IIFE, add a `503` branch to the existing `.then((res) => {...})` chain, sibling to the current 401 branch and reusing the SAME `isApi(url)` helper — do not write a second URL-matching helper. Behavior:
      - Retry only when the response status is `503` AND `isApi(url)` is true. Leave every other status and every cross-origin or non-API request untouched.
      - Retry only when the request body is safely re-sendable: `init.body` absent or a string. If the caller passed a stream or a `Request` object whose body may already be consumed, skip the retry and fall through to the give-up path rather than sending a corrupt second request.
      - Attempt cap: 2 retries, i.e. 3 total attempts (D-07's "2-3 attempts").
      - Wait between attempts: read the `Retry-After` response header, parse it as a whole number of seconds, and fall back to 1 second when it is absent or unparseable. Add randomized jitter of up to a few hundred milliseconds on top of every wait. The jitter is not cosmetic — without it, every browser tab blocked by the same contended write retries at the same instant and amplifies the contention it is recovering from.
      - Re-issue through `origFetch` with the same `input` and the same (token-augmented) `init` the first attempt used, so the retry carries identical auth and identical payload. This is safe because a 503 from the busy path means the transaction rolled back and nothing was written; and re-application of an identical payload converges to the same state (the idempotency property plan 08-01 proves).
      - Return the final response to the original caller either way. Do not throw, and do not swallow a success: a retry that succeeds must resolve with the successful response so existing call-site code sees its normal 2xx path.

    Add a comment above the branch, in this file's existing explanatory style, stating that a 503 here is transient write contention (distinct from the 409 stale-write conflict Phase 9 introduces — the two signals stay distinct and are handled differently), and naming the jitter's purpose as retry-storm avoidance.

    Keep everything IIFE-wrapped; add no implicit global. If anything must be reachable from elsewhere, assign it explicitly on `window` the way `openPlaybookSlide` is.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server response → browser JS | The 503 body and `Retry-After` header are server-controlled input the client acts on; a malformed header must not become an unbounded wait |
| client JS → DOM | The give-up toast writes to the page; a markup-assignment sink here would be a new XSS surface in the one file loaded on every page |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-02 | Denial of Service | client retry loop in `public/js/transitions.js` | medium | mitigate | Hard attempt cap of 2 retries plus randomized jitter on every wait. Without jitter, all tabs blocked by one contended write retry in lockstep and amplify the contention — a self-inflicted thundering herd. Asserted by the call-count tests. |
| T-08-12 | Denial of Service | `Retry-After` header parsing | low | mitigate | Parse the header as a whole number of seconds and fall back to 1 second when absent or unparseable; a non-numeric or absurd value must not produce an unbounded or `NaN` wait. |
| T-08-13 | Tampering | give-up toast DOM write | medium | mitigate | Set the message via `textContent` or a text node, never via markup assignment. The message is a fixed literal today, but adding a markup sink to the file loaded on every page is exactly the class of regression `test/client-xss-sinks.test.js` exists to catch — that test staying green is the gate. |
| T-08-14 | Repudiation | silent retry masking a real failure | high | mitigate | The transparency prohibition in `must_haves.prohibitions`: exhausted retries must surface a visible "not saved" message. A silent failure on MNPI deal data would leave the user believing a retention decision or DD finding was recorded when it was not. |
</threat_model>
