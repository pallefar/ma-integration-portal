  <action>
    Create the standalone harness. It must exercise the real stack, not a simulation of it (D-13), and it must never touch the committed `data/` files.

    Setup: create a scratch directory with `fs.mkdtempSync`, seed it with the existing `runMigration` + `runSplit` scripts exactly as `test/role-enforcement.test.js` does, insert the fixture users into control.db so real logins are possible, and build one env object carrying `MA_CONTROL_DB_PATH`, `MA_RUNTIME_DB_PATH`, `MA_DEMO_DB_PATH`, `MA_DEALS_DIR` and `MA_AUDIT_DB_PATH` pointed at that scratch directory. Every spawned child receives that SAME env object plus its own `PORT`, so all processes share one physical set of database files — which is what "the same data directory" means here. Using the live committed `data/demo.db` and `data/control.db` as the soak target would dirty git-tracked files on every run and contaminate the shipped demo dataset; that is forbidden.

    Processes: `spawn('node', ['server.js'], { env, ... })` for each worker — real separate OS processes, never `app.listen()` in one process. Allocate a distinct port per child, wait until each answers an HTTP request before starting the load (poll a cheap endpoint; do not sleep a fixed interval and hope), and tear every child down in a `finally` so an aborted run leaves no orphan listening on a port.

    Load: create a session per worker with `sessionsDb.createSession` against the scratch runtime.db and drive writes over native `fetch` with the `ma_session` cookie. Mix reads and writes across collections that are genuinely co-edited, so the workers contend on the same rows rather than politely partitioning. Every write carries a unique id derived from the worker index and a monotonic counter, and the harness records, per attempt, that id and the outcome bucket: acknowledged (2xx), cleanly refused (503 carrying `Retry-After`), or anything else. "Anything else" — a 500, a socket hang-up, a timeout, a non-JSON body — is a failure the run must report, not absorb.

    Configuration (D-14): default to 3 worker processes, a run duration of about 2 minutes, and a write interval that produces real contention at that scale. Read overrides from `SOAK_PROCESSES`, `SOAK_DURATION_MS` and `SOAK_WRITE_INTERVAL_MS`, falling back to the defaults when unset or unparseable, so a release gate can run the same script harder without editing it. Print the resolved configuration at the start of the run.

    Verification pass (D-15), after all children have exited: checkpoint the WAL first, then open the finished files through `db/dbFiles.js` and assert, printing a clear per-check verdict:
      - Every id in the acknowledged bucket is present in the final database and its stored content matches what was sent — exact, not merely present.
      - No id from the cleanly-refused bucket is present. A refused write that landed anyway would mean the 503 lied about the rollback.
      - `PRAGMA integrity_check` returns `ok` on every file the run touched.
      - The audit trail contains exactly one row per acknowledged audited write — a one-to-one match, asserted in both directions so neither a missing row nor a duplicate passes.
      - The count of cleanly-refused writes is reported and is allowed to be non-zero. Bounded 503s are the design working, not a failure. Report the rate; fail only if a refusal was not clean.
    Exit non-zero with a summary naming the first failing check; exit zero with the summary line otherwise, and remove the scratch directory on both paths.

    Then add `"soak": "node scripts/soak.js"` to `package.json`'s existing flat `scripts` block. Add no dependency — `node:child_process`, global `fetch`, and the existing `better-sqlite3` cover all of this, and this project has no HTTP-test library anywhere in `test/` by deliberate convention.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| soak harness → filesystem | The harness writes databases; if it targets the committed `data/` files it contaminates the shipped demo dataset |
| worker process → shared database files | The boundary under test: N real processes contending for one set of SQLite files |
| audit trail ↔ acknowledged writes | The compliance reconciliation surface — a drift here is a repudiation failure, not a performance issue |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-06 | Tampering | `scripts/soak.js` target files | high | mitigate | The harness seeds and targets an `fs.mkdtempSync` scratch directory via all five `MA_*_DB_PATH` overrides and never the committed `data/` tree. Asserted structurally (all five constants present, `mkdtemp` used) and empirically (`git status --porcelain data/` empty after a run, following a WAL checkpoint because the sidecar hides exactly this). Contaminating `data/demo.db` would ship altered demo content in the turnkey bundle. |
| T-08-05 | Repudiation | audit reconciliation | high | mitigate | The soak asserts a one-to-one match between audit rows and acknowledged writes in BOTH directions — a missing row and a duplicated row each fail. This is the running proof that D-10's no-swallow contract holds under real load rather than only in the unit test. |
| T-08-03 | Denial of Service | audit no-swallow amplification under sustained load | medium | accept | D-10's accepted trade-off (compliance over availability). Bounded and observed rather than assumed: the soak reports the refusal rate at default and harder settings, so a regression from "bounded 503s" into "writes effectively denied" shows up as a number in the summary instead of a surprise in production. |
| T-08-15 | Denial of Service | orphaned soak worker processes | low | mitigate | Every spawned child is torn down in a `finally`, and each is given its own port; an aborted run must not leave a listener holding a port or a lock on the scratch files. |
| T-08-01 | Information Disclosure | soak console output | low | mitigate | The harness prints ids, counts and verdicts. It must not print database file contents or full SQLite error text into a log that could be pasted into an issue — the scratch data is fixture data, but the habit is what carries into a release-gate run against realistic content. |
</threat_model>
