<objective>
Prove Option B end-to-end on one path: a write contended by a real second OS process serializes through SQLite's own WAL write lock, and the losing writer gets a clean, bounded `503 Retry-After` on the wire.

Purpose: this is the gating architectural proof for the whole v2.2.0 milestone (D-01). If cross-process `BEGIN IMMEDIATE` + `busy_timeout` does not serialize correctly here, every later phase's assumption is wrong — and it costs one commit to find out instead of ten.
Output: the three storage/server changes that constitute the mechanism, plus `test/concurrency-busy-retry.test.js` proving both halves of CONC-01 (bounded 503 on contention; zero lost updates across processes) with real spawned child processes.
</objective>

<assumption_delta_decision>
**Generalized noun (now primary):** the **SQLite database write lock is the serialization authority**, not the Node process.

**Decision: `promote`.** Before this phase, "writes are serialized because one Node process owns the write path and `writeDb()` is synchronous" was the primary model, and the in-process snapshot-diff merge carried the safety. After this phase, the primary model is "every writer — same-process or cross-process — serializes on `BEGIN IMMEDIATE` against the file, and waits inside SQLite up to `busy_timeout`." The in-process case is demoted to *one variant* of the general multi-process case, not a separate mechanism.

Rationale: the single-process assumption is not merely extended, it is retired — the in-process merge semantics (D-02) remain, but as merge detail *under* a lock the process no longer owns. Keeping both models alive would mean two serialization stories and two failure modes to reason about.

**Invariant test encoding the generalized intent:** `test/concurrency-busy-retry.test.js` Task 2 — every acknowledged write is present after concurrent multi-process writes. Note the deliberate consequence: the pre-existing `test/concurrent-write.test.js` in-process test remains valid but is NO LONGER the proof of serialization — it proves merge semantics only. Do not treat it as a multi-process proof (RESEARCH.md Pitfall 3).
</assumption_delta_decision>

| Boundary | Description |
|----------|-------------|
| browser → Express `/api` | Untrusted request bodies and headers cross here; the new 503 response also crosses back out |
