# Phase 7 — UI Design Contract

> Visual and interaction contract for IMO Reporting & Exports (RPT-01, RPT-02, RPT-03, RPT-04).
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.
> Every token below is grounded in a value or class that already exists in `public/css/style.css`
> or `public/execution.html`'s page-local `<style>` block, with a file:line citation, following the
> exact provenance discipline `06-UI-SPEC.md` established (declined-flag precedent: this codebase's
> spacing/typography is a set of rem values in consistent reuse, not a formal 4px/8pt grid — a
> checker flag on "no named scale" was already resolved once for this project and should not be
> re-litigated here).
>
> **This phase has one surface with no reuse precedent to cite:** the PDF steerco pack itself is a
> rendered document, not a DOM page — `@napi-rs/canvas` is vendored but currently unused anywhere in
> the codebase (07-CONTEXT.md `code_context`), and no PDF-writing precedent exists to point at. Where
> this spec cannot cite an existing rule for the pack, it states the value directly and marks it
> **(new — pack-only)** rather than implying a citation that doesn't exist.

## Internationalisation & Text Expansion

**Mandatory section (Phase 6 lesson, restated here because it applies again).** Every user-facing
string in this app renders through `data-i18n="key"` and exists in **four languages (EN/DE/ZH/CS)**.
This phase adds new strings on two structurally different surfaces, and the rule is different for
each:

**Screen strings (the Reports & Exports tab, buttons, labels, error text)** — the existing app-wide
contract applies unchanged:

- **No fixed-width chrome.** No `width`/`max-width` in absolute units on the tab label, the
  "CSV"/"JSON" link buttons, the dataset labels, or the "Generate steerco pack (PDF)" button. `.btn`
  is already a content-sized `inline-flex` (`style.css:439-441`) — do not add a fixed width when
  wiring these new buttons.
- **Wrap, never clip.** No `overflow:hidden`+`text-overflow:ellipsis` on any translated label in
  this tab. A clipped "Generate steerco pack" button that reads "Generate steerco pa…" on a German
  render is the exact data-integrity-adjacent failure class Phase 6 named for badges — here it's a
  primary CTA, which is worse, not better.
- **German is the sizing case; Chinese is the opposite failure.** "Generate steerco pack (PDF)" is
  short in English; the DE equivalent will run measurably longer and must reflow the button, not
  truncate it. ZH will be shorter and must not leave the button looking empty/collapsed — verify
  both ends, not just EN.
- **Verification is part of "done."** Any executor wave touching the new tab, its buttons, or its
  error text must take a screenshot at the longest available translation before calling the surface
  complete — the same standing instruction Phase 6 locked in after a live "looks very weird" report.

**The PDF pack itself renders in the deal's language** (per this task's brief) — this is a
**structurally different** i18n requirement from the screen contract above, and gets its own rules:

- The pack is a **generated document**, not a DOM page — there is no `data-i18n` attribute
  mechanism available to it (that hydration runs against live DOM nodes in a browser; the pack is
  produced server-side as a file). Whatever generation mechanism 07-RESEARCH.md selects must read
  the SAME `db.i18n.strings[lang][key]` store the app itself reads (CLAUDE.md §Key Abstractions,
  "i18n via CMS") and resolve every pack label string in the requesting session's active language
  BEFORE rendering — never render the pack in English and translate visually afterward.
- **No fixed-width layout boxes for translated labels in the pack**, mirroring the screen rule: a
  section header, table column heading, or stat-tile label must be laid out to its own measured
  text width for the resolved language, not a value hardcoded against the English string's length.
  This matters more in a rendered document than on screen, because there is no browser reflow to
  fall back on if a canvas/PDF layout routine assumes a fixed column width and DE overflows it.
- **Numbers, currency and dates are not translated strings** — `$12.3M`, stage names rendered as
  short color-coded labels, and the confidentiality footer's ISO-ish timestamp format stay
  consistent regardless of language; only the surrounding label text (headings, column names,
  the "unconfirmed"/"unphased" sentence wording) is looked up per-language.
- **Fallback-to-English is inherited, not reinvented**: a key missing a DE/ZH/CS translation falls
  back to English, exactly as `transitions.js`'s existing i18n hydration does for the screen — the
  pack generator must implement the identical fallback, not fail or blank the label.

Note for the planner: this is a *design* contract only — authoring the actual translation strings
for the ~10-15 new pack/tab labels this phase introduces is separate budgeted work, following the
Phase 5/6 precedent (carry-verbatim where meaning is unchanged, otherwise ship English and rely on
the fallback).

## Design Tensions Resolved

### 1. Why CSV/JSON is secondary-styled and PDF is primary-styled

Both are "export" actions, so treating them identically would be the naive choice. They are
deliberately differentiated because they carry different weight in the IL's actual workflow: the
steerco pack is the artifact that leaves the app and reaches an external audience (D-07's "the file
leaves the app; it must carry its own handling instructions" framing) and is the phase's headline
deliverable (RPT-02, the requirement given top billing in the phase goal — "the IL can produce
trustworthy status output... replacing manual deck assembly"). Raw CSV/JSON is a utility action (an
IL exporting a RAID list into their own spreadsheet is routine, low-ceremony). One `btn-primary`
per page keeps the accent color meaningful (Color contract's 10% reservation) rather than diluting
it across five equally-loud buttons.

### 2. Why exports live in a new Execution Hub tab, not a new page

`execution.html` already visualizes exactly the four datasets RPT-01 names (workstreams via
`ex-ws-grid`, tasks via the phase-grouped list, RAID via `raid-list`, synergies via `syn-list`) —
this phase's exports are a new *view* of data the page already owns, not a new domain. A standalone
`reports.html` would duplicate the header/nav chrome for zero data-fetching benefit (the export
links are static, server-hit URLs — they don't reuse the tab's already-fetched `state.*`, so there's
no client-state argument for co-location either; the argument is purely chrome consistency and
discoverability: an IL already on the Hub finds Reports as a fourth, equally-weighted tab rather
than hunting for a separate nav entry that doesn't exist anywhere in `main-header`'s nav-link list).

**Structural note for the planner:** `execution.js:1050`'s tab-switch handler hardcodes
`['tasks', 'synergy', 'raid']` as the array of pane ids to show/hide — this MUST become
`['tasks', 'synergy', 'raid', 'reports']` alongside adding the 4th `<button class="ex-tab"
data-ex-tab="reports">` and its `<div id="ex-pane-reports">` pane, or the new tab button will render
inert (clicking it will toggle nothing, since the id it isn't in is never queried).

### 3. Why exports are decoupled from any live tab filter

The RAID tab has a type filter (`raid-filters`, all/risk/issue/decision/dependency); the Synergy tab
has per-card expand state. If the Reports tab inherited "export what's currently filtered," a user
who left the RAID tab filtered to "Risk" earlier in their session could unknowingly export a partial
RAID file believing it was complete. **Locked rule:** every export and the pack always cover the
FULL dataset (subject only to server-side clearance filtering, D-08) — the Reports tab has no filter
controls of its own, and does not read or depend on any other tab's filter state.

### 2. Raw data export rows (RPT-01)

Four rows, one per dataset, each styled as a compact flex row (new `.rpt-export-row` class, values

```html
<div class="rpt-export-row">
  <span class="rpt-export-label" data-i18n="rpt.ds_workstreams">Workstreams</span>
  <span class="rpt-export-links">
    <a href="/api/reports/export?dataset=workstreams&amp;format=csv"
       class="btn btn-secondary rpt-export-link" data-i18n="rpt.csv">CSV</a>
    <a href="/api/reports/export?dataset=workstreams&amp;format=json"
       class="btn btn-secondary rpt-export-link" data-i18n="rpt.json">JSON</a>
```

Repeated for `dataset=tasks`, `dataset=raid`, `dataset=synergies` with their own `data-i18n` label
keys (`rpt.ds_tasks`, `rpt.ds_raid`, `rpt.ds_synergies`).

- **Mechanism: plain `<a href>` anchor navigation, not a `fetch()`-driven click handler.** This
  mirrors `public/admin.html:666`'s `download-zip` link exactly — an authenticated GET, the
  session cookie travels with normal navigation, the browser's native `Content-Disposition:
  attachment` handling triggers the download with zero custom JS. No loading/disabled state is
  needed for these two links (Copywriting Contract: CSV/JSON generation is a synchronous string
  join over already-computed rollup data — the same "no overlay" reasoning the phase brief names,
  just with literally nothing to show because there is no meaningful wait).
- **Filenames** (locked, since this is user-visible): `{codename}-{dataset}-{YYYY-MM-DD}.csv` /
  `.json`, e.g. `project-falcon-synergies-2026-08-08.csv`. **`{codename}` is `deal.name`** — the

  user-controlled/MNPI" — textContent-only) — **never `deal.targetCompany`**, which is the real
  legal target name and exists as a structurally separate field precisely so it can be withheld
  (`deal-wizard.js:741`). This is the concrete, code-grounded form of D-07/D-09's codename
  discipline for this phase's filenames.
- **Column contracts are NOT locked here** (07-CONTEXT.md's own Claude's Discretion list explicitly
  defers "CSV column contracts, escaping/encoding... and JSON export shape" to planning). The UI
  contract this spec DOES lock: **exported columns mirror the on-screen fields for that dataset**
  (D-08 parity — a file must never surface a field the screen doesn't already show that caller), and
  JSON export reuses the SAME enriched shape the corresponding `GET` route already returns (e.g.
  synergies JSON = `enrichSynergy()`'s output per item, `server.js:3352-3356` — not a bespoke export
  schema diverging from the live API). Illustrative (non-binding) column sets, for the planner's
  starting point: Workstreams — label, tasksTotal, tasksDone, pctComplete, blocked, ragStatus; Tasks
  — title, workstreamId, phase, status, owner, dueDate, source; RAID — type, severity, title, owner,
  workstreamId, status; Synergies — title, category, stage, targetM, realizedM, costIncurredM,
  netBenefitM, stale, lastConfirmedAt.
- **Integration note:** no server route today computes the workstream-level rollup the "Workstreams"
  dataset needs (the screen derives it client-side in `execution.js:76-144` from already-fetched
  tasks + template). The planner must add a server-side equivalent — this is a data-layer gap this
  UI contract surfaces, not one it resolves.

### 3. Clearance-scoped visibility — both sides of the symmetry (D-08, D-09)

Two DIFFERENT rules apply to this surface, and they must not be conflated:

**Rule A — the export CONTROLS are uniformly visible (D-08).** Unlike Phase 6's org/talent surfaces
(where an uncleared caller sees no control at all — absence, not disabled), every deal member sees
the IDENTICAL four dataset rows and the IDENTICAL Generate-pack button, regardless of their DD-area
grants. There is no client-side role/grant check anywhere in this tab. **What differs is the
CONTENT of the file**, not the presence of the button: a member uncleared for the Legal DD area who
clicks "CSV" on the RAID dataset receives a file with exactly the RAID rows `GET /api/raid` would
have shown them (`resolveRaidEntryClearanceArea()` + `accessPolicy.hasAreaGrant()`,
`server.js:3890-3916`) — the same rows, not fewer columns of the same rows. **This is the intended
design, not a leak**: D-08 states it explicitly — "the file contains exactly what the app would show
that caller... Export is a read surface, never a bypass." The UI researcher's job here is to make
sure the CONTROLS never imply a stronger guarantee than that (no "Export all RAID data" label that
overstates scope — the "RAID" dataset label is scoped-by-construction language, not a claim of
completeness).

**Rule B — org/talent data has NO control at all, anywhere (D-09).** The four dataset rows are
`workstreams` / `tasks` / `raid` / `synergies` — full stop. There is no fifth row, no disabled row,
no "coming soon" row for positions/decisions/flight-risk, and the steerco pack's four sections
(§5) never include an org/talent section. This is a **structural absence**, matching the exact
Phase 6 Tension-4 precedent this task's brief calls out by name: "a disabled control still tells the
user there is a view they're not allowed to see" — here the equivalent statement is stronger, since
D-09 isn't about a *clearance tier* (which could in principle be granted later) but a *category
exclusion by design* ("Named-people MNPI never lands in an emailable file"). If a future milestone
ever wants org/talent in an export, 07-CONTEXT.md is explicit that this is "its own gated decision,"
not a UI toggle to flip.

**Server-side symmetry, stated for the READ direction explicitly (the lesson this task's brief
calls out by name):** exactly as Phase 4/6 established for writes ("server-side authz is the actual
gate; the UI omission is a courtesy, not the control"), the identical rule governs this READ/export
surface. `GET /api/reports/export?dataset=raid&format=csv` must independently re-run the SAME
`resolveRaidEntryClearanceArea()`/`hasAreaGrant()` filter server-side — a hand-crafted request from a
valid session that never loaded this tab's HTML must not receive a wider RAID export than the tab
would have produced. The tab's own absence of a fifth "org" dataset row is equally a courtesy, not
the control: `GET /api/reports/export?dataset=positions` (or any org/talent variant) must not exist
as a route at all, or must 404/403 if a defensive stub is added — never silently honored.

### 4. Staleness marks (D-12, D-14) — scoped to synergies only, three renderings

Staleness (SYN-05) is a **synergy-only concept** in this codebase today — `isSynergyStale()`
(`server.js:3311-3316`) has no equivalent for tasks, RAID, or workstreams, and Phase 6's D-23
(reaffirmed by this phase's D-13) deliberately gives the flight-risk register no staleness signal
either (moot here anyway since org/talent is excluded per §3 Rule B). **This spec does not invent a
staleness concept for the other three datasets** — RPT-04's "and equivalents" phrase is satisfied by
there being no equivalent to invent; inventing one would be scope creep past what Phase 5 shipped.

Three renderings of the SAME server-computed `stale` flag and threshold (D-14: the deal's existing
`staleDays` setting, exactly-N-days-not-yet-stale boundary, `synergyStaleDays()` `server.js:3294`):

- **CSV**: a `stale` column (`true`/`false`, or the illustrative `Y`/`N` — planner discretion per
  §2) plus a `lastConfirmedAt` column — the data-only equivalent of "dimmed," since a CSV cell has
  no visual weight to reduce. No separate "stale items" sheet/section — one flat table, matching
  D-12's "no stale-appendix" rule at the file-format level.
  Since exports are session-scoped Excel-compatible UTF-8, do not encode staleness as a color or
  formatting flag that would only render correctly in one spreadsheet application.
- **JSON**: no new field needed — `enrichSynergy()` (`server.js:3352-3356`) already attaches `stale`
  to every item; JSON export is that shape, unchanged (§2's "no bespoke export schema" rule).
- **PDF pack** (the one genuinely new rendering, §5's Synergies section): a stale row renders its
  ENTIRE row text in `#94A3B8` (`--text-dim`) instead of the normal `#1E293B` (`--text-primary`) —
  this is the "dimmed" half of D-12 — plus a small filled tag reading **"Stale {N}d"** appended
  after the initiative title, using the exact `.syn-stale-badge` palette (text `#C77700`, background
  `rgba(233,131,0,.09)`, border `rgba(233,131,0,.25)`, `execution.html:70`) rendered as a filled
  rounded rectangle since the pack has no CSS to inherit the class from.
  **`{N}` is a day count that does not exist as a field on the API today** — `isSynergyStale()`
  returns only a boolean and the screen's own `.syn-stale-badge` shows the exact date in a hover
  `title` attribute, never an inline day count (`execution.js:701-703`). The planner must add a
  day-count field (e.g. `staleDays: Math.floor((nowMs - lastConfirmedAt) / 86400000)`) to the
  rollup/enrichment path this pack reads from — computed via the SAME single-clock `ctx` pattern
  `enrichSynergy()` already uses, not re-derived per row. **This spec deliberately does NOT extend
  the live execution-tab `.syn-stale-badge` to show this day count inline** (it remains
  tooltip-only, Phase 5's shipped behavior) — D-12's "inline where they are read" is scoped to the
  NEW report surfaces this phase builds, not a retroactive change to Phase 5's screen UI. If the
  planner judges reusing the new day-count field to also upgrade the live badge is low-cost, that is
  a reasonable additive unification left to their discretion, not a locked requirement here.
- **Exec summary headline (page 1 of the pack)**: the plain sentence "{staleCount} of {total}
  synergy initiatives are stale (unconfirmed for more than {staleDays} days)." — `staleCount` sourced
  from the same rollup field already computed (`server.js:3397`), never recounted independently by
  the pack renderer (D-02's "one source of truth" rule extended to the pack explicitly).

### 5. The steerco pack — full page design (RPT-02, RPT-03, D-04..D-07)

**Page geometry (new — pack-only).** US Letter, declared in both unit systems so whichever mechanism
research selects can use its native one: **816×1056px @ 96dpi** (canvas-raster-friendly) equivalent
to **612×792pt @ 72dpi** (hand-rolled-PDF-friendly). Margins: **0.75in all sides** (72px / 54pt) — a
generous, board-document margin, not the app's own dense card padding. Content column width: 672px
/ 504pt after margins.

**Every-page header band** (D-05): height 60px/45pt, bottom border 2px/1.5pt solid `#E98300`
(`--te-orange`) — the same accent-underline idiom the app's own `.main-header` uses
(`border-bottom: 3px solid var(--te-orange)`, `style.css:177`), scaled down for a document header.
Contents, left-to-right: TE logo (`public/te-logo.png`, natural size 119×68px, aspect ratio ≈1.75:1
— rendered at 28px/21pt height → ~49px/37pt width, preserving aspect ratio, never stretched) on the
left; on the right, a two-line right-aligned block — codename (`deal.name`, bold, 12px/9pt,
`#244C5A`) above generation date (regular, 8px/6pt, `#94A3B8`).

**Every-page footer band** (D-07, mandatory, no exceptions): height 24px/18pt, separated from body
content by a 1px/0.75pt hairline (`#E2E8F0`, `--border-color`). Contents: centered text reading
**"CONFIDENTIAL — {codename} · generated {timestamp} · by {username}"** at 8px/6pt, `#94A3B8`, plus
"Page {N} of {M}" right-aligned on the same line. **`{codename}` is `deal.name`, never
`deal.targetCompany`** (same rule as filenames, §2) — this is the one line of this entire spec where
getting the field wrong is a compliance failure, not a cosmetic one (D-07: "The file leaves the app;
it must carry its own handling instructions and provenance"). `{timestamp}` and `{username}` come
from the same `req.portalUser`/`Date.now()` pair the audit event for this generation records (§7) —
never a client-supplied value.

**Page 1 — Executive Summary (D-04):**

1. Header band (above).
2. **Headline stat row**: 4–5 tiles in a single horizontal row across the content width, each a
   label (10px/7.5pt bold uppercase, `#94A3B8`) above a big number (20px/15pt bold, `#244C5A`) —
   the pack-scale equivalent of the screen's `.syn-rollup-tile` idiom (`execution.html:75-77`).
   Tiles, left to right: **Gross realized** (phased-backed only, D-01), **Unphased** (D-01's
   separate labelled line — rendered as its own tile, not a footnote, so it never reads as folded
   into "gross"), **Cost incurred**, **Net benefit** (this tile's number renders in `#C0392B` when
   negative, `#244C5A` otherwise — reusing the screen's exact `netColor` logic,
   `execution.js:657`), **Deal target**.
3. **RAG workstream strip**: one row of small colored chips, one per workstream — each chip a
   filled rounded rect (12px corner radius) colored via the SAME `ragColor()` thresholds already in
   `execution.js:105-110` (green ≥80%, amber ≥40%, red otherwise, red also on any-blocked), with the
   workstream label inside/beneath at 10px/7.5pt. This is a compact single-row summary, NOT the
   full per-workstream bar detail — that lives in §2's dedicated section.
4. **Top risks**: a short list (top 3–5 RAID entries where `type === 'risk'`, ordered
   critical→high→medium→low) — each row: title (10px/7.5pt regular) + severity as colored text
   (reusing the RAID severity palette, Color contract above) — no filled pill, matching the pack's
   general density-first table styling (§ "RAID" section below).
5. **Stale count sentence** (§4): "{staleCount} of {total} synergy initiatives are stale..."

**Section 2 — Workstreams & Tasks:**

- A horizontal bar per workstream — track `#eef2f2` (`--bg-subtle`), fill colored via `ragColor()`,
  label left / percentage right — the pack-rendered equivalent of `.ex-ws-track`/`.ex-ws-fill`
  (`execution.html:107-108`).
- Below: a task table, columns Title / Workstream / Phase / Status / Owner / Due date, one row per
  task, 1px/0.75pt `#E2E8F0` hairline between rows (no zebra striping — the app's own list styling
  doesn't zebra-stripe either, `.ex-task`/`.raid-row`, so the pack doesn't invent a new visual habit
  here).
- **Pagination**: when the task table exceeds the page, it continues onto additional pages carrying
  the SAME header/footer bands; the column-header row REPEATS at the top of every continuation page
  (a standard report-table contract) — the section title itself does not repeat, only the column
  headers, so a reader can tell "still Workstreams & Tasks, page 2" from the footer's page number.

**Section 3 — Risks & Decisions (RAID):**

- One table, columns Type / Severity / Title / Owner / Status, grouped by `type` in the same fixed
  order the screen's own filter buttons use (`RAID_TYPES`, risk→issue→decision→dependency,
  `execution.html:987`) — consistent ordering between the live filter UI and the pack's static
  grouping.
- Severity renders as colored TEXT (not a filled pill) — this section is a dense table, and a filled
  pill per row (the screen's `.raid-lvl` treatment paired with a background chip) would visually
  compete with row density at print scale; plain colored text at the same hex values reads clearly
  at 10px in a table cell without the extra ink.
- **Clearance-filtered content needs no special "restricted" placeholder** — rows this caller isn't
  cleared for are already absent from the payload before the pack renderer ever sees them (§3 Rule
  A). The pack must never render a placeholder row implying "N more entries hidden" — that would
  disclose the existence of restricted content, the exact disclosure Phase 6's absence-not-disabled
  principle forbids, now extended to a generated document.

**Section 4 — Synergies (RPT-03's "avoiding double-counting" requirement, D-01/D-02):**

- **Section-level recap, not re-derivation**: a small caption line atop the section repeats the
  same 4 headline numbers from page 1 (gross realized, cost, net benefit, target) at a smaller
  scale (10px/7.5pt, not the 20px tile treatment) — explicitly labelled as read from
  `GET /api/synergies/rollup`, the SAME endpoint page 1's tiles read from (D-02's single-source-of-
  truth rule). **The pack must never sum the per-initiative rows below to re-derive these numbers
  independently** — that is exactly the double-counting risk RPT-03 names (a per-item sum computed
  a second time, in a second code path, from possibly-differently-rounded per-item values, could
  silently drift from the rollup's own total — the same class of bug D-02's "screen and pack render
  from the identical rollup" rule exists to prevent).
- **Per-initiative table**: Title, Category (Revenue/Cost, plain colored text — `.syn-cat` palette,
  `execution.html:24-25`), Stage (Idea/Validated/Committed/Captured, `SYN_COLORS` above), Target,
  Realized, Cost incurred, Net benefit, and a small horizontal bar (realized-vs-target,
  gradient `#E98300`→`#3f7a37`, the exact 2-stop gradient `.syn-fill` already uses,
  `execution.html:31`, reproduced as a canvas/PDF linear gradient using the identical two color
  stops).
- **Stale rows**: entire row text in `#94A3B8` + "Stale {N}d" tag (§4). **No stale appendix** — stale
  initiatives stay in their normal row position in this same table, sorted however the rest of the
  table is sorted (not pushed to the bottom, not pulled to a separate page) — D-12's explicit rule,
  restated here at the point of implementation so it isn't lost between the staleness section and
  the layout section.

**Pagination footer-numbering note for the planner**: "Page N of M" requires knowing the total page
count M before the footer of page 1 can be finalized — whichever generation mechanism is chosen must
either do a two-pass layout (measure, then render footers) or build pages into an in-memory
structure before emitting them in page order. This is a generation-mechanism concern
(07-RESEARCH.md's territory per 07-CONTEXT.md's Claude's Discretion list), not a UI decision, but is
flagged here because the footer contract above is infeasible with a naive single-pass streaming
writer.

### 6. Demo mode parity (D-11)

Every control and every rendering rule above applies **identically** in demo mode — same four
dataset rows, same Generate-pack button, same pack page design, same TE branding, same
confidentiality footer (demo's codename is whatever the demo deal's `name` field holds — the
showcase already treats its own data as fictional, so no additional masking is needed beyond what
already applies to every other demo surface). The only difference is the audit side-effect (§7):
demo generates no audit rows, matching Phase 3 D-08's existing audit-scoping precedent
(`db_kind` never `demo`-scoped in `auditHook.js`). **No conditional UI branch exists anywhere in
this contract for `req.isDemo`** — if the planner finds themselves writing `if (isDemo) { hide
export button }` anywhere, that is a contract violation; the only demo-conditional code in this
phase's entire surface is the audit call site itself.

### 7. Audit, in-flight UX and the CSV/JSON vs. PDF asymmetry (D-10)

Every export and every pack generation writes an audit event (real deals only, §6) — who, deal,
format, scope, row counts — following the exact `recordSecurityEvent()` dual-call shape Phase 6
established for the flight-risk register (`server.js:4507-4522`, `db/auditHook.js:126-141`). This is
a server-side concern this UI-SPEC does not re-derive, but the UI's in-flight/success/failure
contract deliberately differs between the two families:

- **CSV/JSON (`<a href>` navigation, §2)**: no client-visible in-flight state at all — a plain
  anchor click that either downloads a file or (on server failure) shows the browser's own native
  download-failure UI. This is not an oversight: matches `download-zip`'s existing, already-shipped
  UX exactly, and is justified because CSV/JSON generation is a synchronous string-join over
  already-computed data (fast enough that a loading state would be theater).
- **PDF pack (`fetch()`-driven, disabled-button idiom, Copywriting Contract)**: pack generation does
  real synchronous work — laying out and rendering multiple pages of tables and bars — which can
  take a perceptible few seconds, unlike the near-instant raw exports. This asymmetry is why the
  pack alone gets the `admin-cms.js:37` disabled+label-swap treatment while CSV/JSON do not; it is a
  deliberate two-tier contract, not an inconsistency to reconcile.
  Concrete sequence: `btn.disabled = true; btn.textContent = 'Generating pack…';` → `fetch(...)` →
  on success, receive the PDF as a blob, trigger the download via a temporary `<a>` element's
  synthetic click (the standard blob-download pattern, since `fetch()` responses aren't
  navigable URLs the browser can download directly), then immediately restore
  `btn.disabled = false; btn.textContent = 'Generate steerco pack (PDF)';` — the download itself is
  the success confirmation, no additional toast; on failure, show the inline error text
  (Copywriting Contract, explicit `display:'block'`, never `''`) and restore the button identically.
