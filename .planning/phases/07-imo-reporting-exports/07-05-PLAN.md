<objective>
Build the pack's frame and its first page: the part that makes every subsequent section correct by
construction.

The frame owns three things no section may own: the TE-branded header band (D-05), the every-page
confidentiality footer carrying the codename, timestamp, username and page-of-total counter (D-07),
and the two-pass layout that makes that counter possible at all. Page one is the executive summary
D-04 puts first — the artifact the steering committee actually reads — carrying the D-01 phased and
unphased split as separate tiles so the headline can never read as folded together.

This plan is pure composition: it draws into canvases and returns page descriptors. It has no route,
no database access and no HTTP concern. Plan 07-06 adds the sections, the route and the button.

Purpose: the footer contract and the single-source-of-truth rule are cheapest to get right in the
frame, before four sections exist to get them wrong in four places.
Output: lib/reportPack.js with geometry, chrome, paginator, language resolver and page one.
</objective>

<task type="auto">
  <name>Task 1: Page frame, confidentiality footer and the two-pass paginator</name>
  <files>lib/reportPack.js, test/reports-pack.test.js</files>
  <reversibility rating="costly">
    D-07's every-page confidentiality marking is a compliance floor, not styling. Once packs carrying
    these marks have circulated, removing or weakening them is a policy change with an audit trail
    behind it, not a visual tweak. Building it into the page frame rather than into each section is
    what makes it structurally un-droppable.
  </reversibility>
  <action>
    Create lib/reportPack.js as CommonJS following the established module shape, exporting buildPack
    and the helpers below.

    Declare the geometry constants from 07-UI-SPEC.md §5 at the top of the module in CSS pixels at
    ninety-six dots per inch, with the point equivalents named in a comment: page width and height,
    uniform margins, the resulting content column width, header band height, footer band height. Do not
    scatter these numbers through drawing code.

    Write the language resolver: given the database object and a requested language code, return a
    lookup function that resolves a key from the app's translation store for that language, falling back
    to the English entry, then to a caller-supplied English literal, then to the key itself — the exact
    order the browser-side helper uses. Validate the requested code against the four shipped languages
    and default to English for anything else. The active language exists only in the browser, so the
    caller must pass it explicitly; the resolver never guesses.

    Write drawHeaderBand(ctx, model): the TE logo drawn from the existing repository logo image at the
    height 07-UI-SPEC.md fixes, preserving its natural aspect ratio and never stretched; on the right, a
    right-aligned two-line block with the deal CODENAME in bold above the generation date; and the band's
    bottom accent rule in the brand orange at the specified thickness — the document-scale echo of the
    app header's own accent underline (D-05).

    Write drawFooterBand(ctx, model, pageNumber, pageCount): the hairline separator, then the centred
    confidentiality line reading the word CONFIDENTIAL followed by the deal codename, the generation
    timestamp and the generating username, with the page-of-total counter right-aligned on the same
    line (D-07). Both the header and the footer read the deal's CODENAME field. The deal's real
    legal-target field must not be referenced anywhere in this module — it exists as a separate field
    precisely so it can be withheld before announcement, and this footer is the one line in the whole
    design where getting the field wrong is a compliance failure rather than a cosmetic one. Timestamp
    and username come from the values the caller resolved server-side, never from anything a client
    supplied.

    Write the page frame wrapper: a function that, given a page descriptor and its position in the
    document, renders a canvas through the PDF module's page renderer, drawing the header band, then the
    descriptor's own body callback constrained to the content column between the bands, then the footer
    band. Sections cannot opt out of the bands because sections never call the page renderer directly —
    they only produce body callbacks.

    Write the two-pass paginator, which is the reason this task exists. Pass one: each section is asked
    to measure itself against the available content height and to return an ordered array of page
    descriptors, each carrying its own body callback and whatever continuation state it needs (for
    example, a table's row slice and whether its column-header row must repeat). No pixels are produced
    and no PDF bytes are written in pass one. Between the passes, the total page count is known. Pass
    two renders each descriptor through the page frame with its correct page number and the now-known
    total, and hands the rendered pages to the PDF builder. Comment the reason plainly: a single-pass
    writer emits page one's footer before later sections have been measured, so its counter would always
    read page one of one — the tell-tale of a single-pass implementation.

    buildPack(model) is the public entry: it takes an already-assembled, already-clearance-filtered data
    model plus the resolved language, timestamp and username, runs both passes over the registered
    section composers, and returns a PDF Buffer. In this task register only a single trivial section so
    the frame and paginator are exercisable; Task 2 registers the executive summary and Plan 07-06
    registers the rest. buildPack performs no database access, no clearance evaluation and no HTTP work
    — the caller supplies a finished model. That separation is what lets Plan 07-06 prove the pack and
    the raw exports apply the identical filter, because both consume the same filtered lanes.

    All drawing uses opaque fills on a solid white page. Do not reproduce the app's dark translucent
    card backgrounds or any blur filter — they are designed to sit over a blurred dark hero image and
    have no printable equivalent (07-UI-SPEC.md §Color print-safety rule). The app's alpha-over-white
    chip fills are fine to reuse as-is. Every string is drawn with the registered vendored font family
    named in the font specification, at the sizes and the two weights 07-UI-SPEC.md fixes; never a
    generic family name, which renders Chinese as empty boxes with no error at all.

    Create test/reports-pack.test.js as a pure unit test over lib/reportPack.js with a hand-built model
    — no server boot in this file yet. Assert: a model forced to paginate across several pages produces
    a PDF whose page-object count equals the paginator's own count; every rendered page's descriptor was
    passed the correct page number and the same total; a model whose deal carries a distinctive sentinel
    in its legal-target field produces a pack in which that sentinel appears nowhere in any drawn string
    (assert this by capturing every string the drawing code passes to the text-drawing call through an
    instrumented context, so the assertion holds regardless of rasterisation); the footer's page counter
    on page one reads the true total and not one; and a requested language with no entry for a key falls
    back to English rather than blanking or throwing.
  </action>
  <verify>
    <automated>node --test test/reports-pack.test.js</automated>
  </verify>
  <done>
    Every page of a multi-page pack carries the branded header and the confidentiality footer with a
    correct page-of-total counter; the codename appears and the legal target name does not; the language
    resolver falls back to English; and buildPack returns a valid PDF buffer.
  </done>
</task>

<task type="auto">
  <name>Task 2: Page one — the executive summary</name>
  <files>lib/reportPack.js, test/reports-pack.test.js</files>
  <action>
    Register the executive-summary section as the pack's first section, composing 07-UI-SPEC.md §5's
    page-one design in its fixed order (D-04: the one-page executive summary comes first, then a section
    each for workstreams and tasks, risks and decisions, and synergies).

    The headline stat row: five tiles across the content column, each a small uppercase label above a
    large bold number, in this order — gross realized, unphased, cost incurred, net benefit, deal target.
    The unphased tile is a tile of its own, matching the five-tile row Plan 07-04 gave the screen, so the
    phased and unphased figures can never read as one number (D-01). The net benefit number renders in
    the danger colour when negative and in the dark teal otherwise, reusing the screen's own rule — a
    negative net benefit early in a deal is a real state a steering committee needs to see, not an error
    to hide.

    Every one of those five numbers is read from the rollup object the caller supplied. The renderer must
    NOT sum the per-initiative rows to derive any of them. That second summation, from a second code
    path, over per-item values that were already rounded once, is exactly the drift RPT-03's
    avoid-double-counting requirement names and exactly what D-02's one-source-of-truth rule exists to
    prevent. Say so in a comment at the point of temptation.

    The RAG workstream strip: one row of small filled rounded chips, one per workstream from the
    server-side workstream rollup, coloured by the band that rollup already computed — never re-derived
    from percentages here — with the workstream label at the small label size. This is a compact
    single-row summary; the per-workstream bars belong to the workstreams section in Plan 07-06.

    Top risks: the highest three to five entries from the supplied RAID collection whose type is risk,
    ordered from the most severe level downward through the four-level severity vocabulary. Each row is
    the title at body size followed by the severity as coloured TEXT in the existing severity palette —
    no filled pill, matching the pack's density-first table styling.

    The stale-count sentence: the plain sentence 07-UI-SPEC.md §4 fixes, naming how many of how many
    synergy initiatives are stale and the threshold in days. Both the count and the total come from the
    rollup object and the supplied collection length, never recounted independently (D-12/D-02).

    Every label on this page resolves through the language resolver with an English literal as the
    in-code fallback, and no label may be laid out against a width measured from its English string — a
    German label must be measured in German, because a rendered document has no browser reflow to fall
    back on when a fixed column assumption overflows (07-UI-SPEC.md §Internationalisation).

    Empty-deal behaviour: a deal with no synergies, no workstreams and no RAID entries still produces a
    valid page one, with zeroed tiles and the per-section empty-state line — never a blank page and never
    a generation failure. The Copywriting Contract's blocked-action message for a completely empty deal
    is the ROUTE's concern in Plan 07-06, not this renderer's; this renderer must remain able to render
    zeros.

    Extend test/reports-pack.test.js: assert each of the five tiles renders the exact value supplied in
    the rollup, using a rounding-edge fixture whose per-initiative amounts do not sum cleanly, so a
    re-summation would produce a visibly different number and fail; assert the unphased figure appears as
    its own labelled tile rather than inside the gross tile's text; assert the RAG chips use the bands the
    workstream rollup supplied; assert the risk list is ordered most-severe-first and truncated to the
    stated maximum; assert the stale sentence's numbers equal the supplied rollup count and collection
    length; and assert an entirely empty model still renders a page one without throwing.
  </action>
  <verify>
    <automated>node --test test/reports-pack.test.js</automated>

    figures, a RAG workstream strip, the top risks and the stale sentence; every number traces to the
    supplied rollup with no second summation; an empty deal still renders.
  </done>
