<objective>
Extend the conflict contract to the Due Diligence workspace — findings, request items and the
finding-to-task/RAID conversion — with the clean-room area gate applied to the conflict body itself.

Purpose: DD findings are one of CONC-02's five named collections and the most clearance-sensitive data
in the app. This is where the conflict body stops being a convenience and becomes an access-control
surface.
Output: DD edits are conflict-safe, and a conflict never widens what a caller can see.
</objective>

**server.js — `POST /api/dd/findings`.** Inside the `if (b.id)` branch, call `conflictIfStale`
immediately after the existing `ddAreaRefused(req, res, deal, finding ? finding.area : null)` guard and
before the empty-title guard, returning early when it responded. Placement after the clearance gate is
deliberate: the conflict response must never confirm that a finding exists in an area the caller cannot
see, which is exactly what the route's own comment already establishes for the convert path.

Pass the clearance filter through `conflictIfStale`'s hook so the conflict body's `currentRecord` is
evaluated against the CURRENT record's area rather than the area the caller believed it had. A
concurrent writer may have moved the finding into an area this caller is not cleared for — the very
race the conflict is reporting. When the current record fails that gate, respond with the conflict but
with `currentRecord` and the field values omitted, keeping only the version and the attribution, so the
user still learns their write was rejected without learning the record's new contents.

**server.js — `POST /api/dd/request-items`.** Same placement, after `ddAreaRefused` and before the
empty-text guard. Additionally, the conflict body's `currentRecord` must be run through
`publicDdItem()` — the same projection the route's own success response uses. The success path already
narrows what leaves this route; the conflict path must narrow identically or it becomes a wider
disclosure surface than the endpoint it belongs to.

precheck silently never fires.

**server.js — `POST /api/dd/findings/:id/convert`.** This route mutates the finding (it writes the
finding's link-id arrays) and creates a task and/or a RAID entry in the same `writeDb(db)` call. Under
D-02 the mutation of the finding carries a version precondition like any other edit. Call
`conflictIfStale` immediately after the existing `ddAreaRefused` guard and before the `source` and
`workstreamId` derivations, returning early when it responded, with the same clearance filter Task 1
wires. Do not add a precondition to the created task or RAID entry — a create has no prior state to be
stale against, and the route's own source-string dedupe already makes a re-click a no-op.

This is the one in-scope route that touches more than one versioned collection in a single write. The
finding is the only UPDATE among them; the task and RAID entry are INSERTs, which carry no version
predicate. Confirm by test that a conflict on the finding rolls back the whole call — no orphan task,
no orphan RAID entry, no audit row — which is what the throw-inside-the-transaction shape from plan 01
guarantees (Pitfall 6).

**validators/dd.js** — add the `version` field to the convert route's schema.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `/api/dd/*` | Untrusted JSON body crossing into the clean-room-guarded DD collections |
| DD 409 response → browser | The conflict body echoes a DD record's current state — the most clearance-sensitive data in the app |
| convert route → tasks/RAID collections | One write spanning three collections, two of them outside the DD clean room |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-17 | Information Disclosure | DD conflict body `currentRecord` | high | mitigate | The conflict body passes through the same `ddAreaRefused`/`hasAreaGrant` gate the route's read path applies, evaluated against the record's CURRENT area rather than the caller's believed one. A record whose area concurrently moved out of the caller's clearance yields a conflict carrying version and attribution only, with no field values. |
| T-09-18 | Information Disclosure | DD request-item conflict body vs. the route's own projection | high | mitigate | `publicDdItem()` is applied to the conflict body's `currentRecord`, identically to the route's success response. Asserted by comparing the 409 body's key set against the 200 body's, not by inspection. |
| T-09-19 | Information Disclosure | conflict as an existence oracle | medium | mitigate | `conflictIfStale` is called strictly AFTER the route's clearance gate, so a caller with no grant for a finding's area gets the existing 403/refusal and never learns from a 409 that a record with that id exists. Matches the convert route's own documented ordering rule. |
| T-09-20 | Tampering | multi-collection rollback on the convert route | high | mitigate | The conflict is thrown inside `applyWrite`'s transaction body, so the finding update, the task insert, the RAID insert and the audit append all roll back together. Asserted by a test that checks for orphan rows after a 409, not by reasoning about the transaction. |
| T-09-21 | Tampering | DD `version` field bypassing validation | medium | mitigate | `version` is declared on every DD upsert and convert schema as a bounded non-negative integer, so a string or float cannot reach `json_extract()`'s comparison. Without the declaration zod would strip it and the precheck would silently never run. |
| T-09-SC | Tampering | npm/pip/cargo installs | high | accept | No package is installed or upgraded in this plan. |
</threat_model>
