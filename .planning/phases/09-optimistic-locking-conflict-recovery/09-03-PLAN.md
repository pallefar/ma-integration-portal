  <action>
Complete the diff list against the five resolved E1 considerations and the E4 long-text one.

**Empty diff (E1-empty).** When the intersection of the user's payload keys and the server's current
record produces zero rows — a version-only bump, or a concurrent change that touched nothing the user
edited — render the field-diff empty-fallback sentence from the UI-SPEC Copywriting Contract inside a
`.conflict-diff-empty` element in place of the list. The apply action stays present and enabled: the
user's edit is still applicable, it just has nothing to compare against.

**Partial values (E1-partial).** A value that is empty string, null or undefined on either side renders
an explicit italic placeholder in that value box, styled by a `.conflict-diff-value-empty` class, rather
than an empty box. A blank cell reads as a rendering bug and makes the user distrust the comparison.
Non-string values (numbers, booleans, arrays, nested objects) are stringified for display — an array or
object renders as its JSON form so the user sees the real competing value, still set with `textContent`.

**Overflow (E1-overflow).** Give `.conflict-diff-list` a bounded height with internal vertical
scrolling, so eight or more rows scroll inside the body while `.conflict-modal-head` and
`.conflict-modal-actions` stay pinned and non-scrolling. The card itself must never exceed the viewport
height. Use a viewport-relative bound on the card and a bound on the list that leaves room for the
pinned chrome.

**One vs many (E1-zero-one-many).** A single row must not leave a tall empty gap: the list's height is
content-driven up to its bound, not fixed. The dialog width stays constant across one row and twelve —
do not size the card from its content width.

**Long text (E1-long-text).** A long value — a RAID description, a DD-finding narrative — is shown in
full inside its value box, wrapped on word boundaries with long unbroken tokens allowed to break, in a
per-field bounded-height box that scrolls internally. The value must never be shortened for display:
the user cannot decide between their version and the server's without seeing both completely. Do not
apply any single-line clipping or trailing-marker treatment to these boxes.

**Long names (E4-long-text).** The attribution line wraps onto a second line for a long display name.
The header may grow by a line; it must not clip. The name is never shortened.

Keep every string assignment on `textContent`. All new spacing sits on the UI-SPEC's 4px scale (4 for
label-to-value, 8 for row-to-row and button-to-button, 16 for value-box padding and section gaps, 24
for the card's outer padding). Typography and colour stay exactly as the UI-SPEC tables specify — the
orange accent remains confined to the apply button's background and the "mine" box's left border.

**In-flight action state (E2-loading).** Clicking an action disables ONLY the clicked button and swaps
its label to the corresponding in-flight label from the Copywriting Contract. The other action stays
enabled throughout, so a user who changes their mind while the resubmission is in flight can still take
it. No spinner element and no icon dependency — the label swap is the whole affordance, matching house
convention. Restore the original label and enabled state when the resubmission settles into a rendered
error.

**Reapply failure (E2-error).** When the resubmission comes back as a second conflict, a network
failure or a 5xx, render an inline `.conflict-modal-error` banner positioned above the actions, inside
the dialog, carrying the error copy from the Copywriting Contract with the specific reason
interpolated. Then:
  - On a second genuine conflict, re-render THIS dialog in place from the new 409 body — refresh the
    server-side column and the attribution from the fresh data, and leave the user's own column exactly
    as it was. Never construct a second overlay: route the re-render through the existing
    `activeConflictDialog` guard so the same overlay element is reused.
  - On a network failure or a 5xx, keep both columns as they are and surface the reason. The user's
    values are never cleared, reset or re-fetched.

**test/client-conflict-dialog.test.js** — create it on `test/client-busy-retry.test.js`'s harness,
extracting and evaluating the same `ma-fetch-wrapper` region of `public/js/transitions.js` in a node:vm
sandbox with a stubbed `fetch` and a minimal DOM. Cover, as behavior rather than as source inspection:
  - A 409 with the conflict marker renders exactly one overlay, and the stubbed fetch is called exactly
    once — the wrapper made no attempt of its own. This is the concrete gate on D-05 and Pitfall 11;
    assert the attempt count, do not eyeball the branch.
  - A 409 WITHOUT the conflict marker renders no overlay and the response is returned to the caller
    unchanged, with its status and body still readable. This is the Pitfall-1 gate: two unrelated 409s
    already exist in `server.js`.
  - Clicking the apply action issues exactly one further fetch, whose payload carries the server's
    fresh version in place of the user's stale one and is otherwise byte-identical to the original.
  - The apply path on a query-parameter route rewrites the `expectedVersion` value in the URL rather
    than the body.
  - Clicking the discard action issues no further fetch and removes the overlay.
  - A second 409 on reapply leaves exactly one overlay in the document, with the user's own column
    unchanged and the server-side column refreshed.
  - A 503 still takes the pre-existing retry path untouched — the 409 work did not disturb it. Swap in
    a recording fake for the sandbox's timer when asserting this, per the harness's own caveat.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| 409 response body → dialog DOM | Record values written by other users — MNPI free text — are rendered into the page |
| dialog apply action → `/api` | A user-initiated resubmission crossing back into the write path |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-13 | Tampering | diff-list value rendering | high | mitigate | Every value — including the JSON stringification of arrays and nested objects added in Task 1 — is set through `textContent`. No markup assignment anywhere in the component. Gated by a region-scoped grep over the wrapper region and by `test/client-xss-sinks.test.js`. |
| T-09-14 | Denial of Service | reapply loop on repeated conflict | medium | mitigate | A second conflict re-renders the dialog and stops — it never auto-clicks apply, never schedules a timer and never re-enters the wrapper's retry path. Every further attempt requires a fresh human click. Asserted by the fetch-call-count case in `test/client-conflict-dialog.test.js`. |
| T-09-15 | Spoofing | unrelated 409 rendering as a conflict | medium | mitigate | The dialog opens only on `conflict === true` in the parsed body. A dedicated sandbox case asserts a marker-less 409 renders nothing and passes the response through untouched. |
| T-09-16 | Information Disclosure | overlay left in the DOM after resolution | low | mitigate | The `activeConflictDialog` guard owns exactly one overlay; every exit path (apply success, discard, background click, Escape) removes it, so a record's current MNPI values do not linger in the DOM behind a later page state. |
| T-09-SC | Tampering | npm/pip/cargo installs | high | accept | No package is installed or upgraded in this plan. |
</threat_model>
