<planner_decisions>
Three items were Claude's Discretion in 09-CONTEXT.md and one was an open question in 09-RESEARCH.md.
They are decided here, once, and every later plan inherits them.

**PD-1 — Version field name and mechanics.** The field is a top-level integer `version` on the record's
own JSON blob, alongside `updatedBy` (username string) and `updatedAt` (ISO string). Stamping happens
in `db/store.js`'s `writeDb()`, never in a route handler, so every in-scope collection gets identical
behavior and the coverage gate can assert it structurally.

**PD-2 — Two enforcement layers, both load-bearing, closing two different windows.**
- *Route precheck* compares the CLIENT's remembered `req.body.version` against the freshly-read record.
  It closes the user-vs-user window (client GET → client POST) — the window CONC-02 exists for. It
  produces the informative 409 body the dialog needs, without paying for a failed transaction.
- *WHERE-clause check* compares THIS request's own read snapshot against what is on disk at the moment
  the `.immediate` transaction runs. It closes the cross-process window Phase 8's multi-process WAL
  model introduced (server `readDb()` → server `writeDb()`). It is the CONC-02-literal mechanism.
  Neither layer substitutes for the other.

**PD-3 — 409 body contract (fixed shape, one builder, every route identical):**
`{ conflict: true, conflictKind: 'version' | 'deleted', recordId, currentRecord, currentVersion,
changedBy, changedAt }`. `conflict: true` is the discriminator the client checks — never the status
code, because two unrelated 409s already exist in `server.js` (Pitfall 1).

**PD-4 — Open question resolved (09-RESEARCH.md Open Question 1 / assumption A2): an update whose
target row was concurrently deleted surfaces a 409 with `conflictKind: 'deleted'`, rather than staying
the pre-Phase-9 silent no-op.** Rationale: a `{ success: true }` response for a write that persisted
nothing is a false statement about MNPI data, and D-02's no-exemptions spirit covers it. Scoped to
`VERSIONED_COLLECTIONS` only — every other collection keeps the CR-02 no-resurrect no-op verbatim.
</planner_decisions>

Three cases:
  - **Same record, two writers.** Two children each read the same RAID record, then both write a
    changed value. Exactly one commits; the other is rejected by the version predicate. Assert on the
    outcome pair, not on which child wins — the ordering is genuinely nondeterministic. Assert the
    surviving record's stored value is one of the two submitted values in its entirety, never a blend
    of both, and that its version advanced by exactly one.
  - **Different records, two writers.** Two children each read and write a DIFFERENT RAID record in the
    same collection. Both must commit, both versions must advance, and neither may see a conflict —
    this is the criterion-3 assertion that the lock is per record and not per collection.
  - **Update racing a delete.** One child updates a record while another deletes it. The surviving
    outcome is either a clean delete or a clean update, never a resurrected row, and the losing writer
    is told — a version conflict or a deleted conflict, never a `{ success: true }` for a write that
    persisted nothing (PD-4).

child report its outcome through a channel the parent can read deterministically (exit code plus a

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `/api` write routes | Untrusted JSON body, including the new client-supplied `version` field |
| browser → `/api` responses | The 409 conflict body now echoes a record's current server state back to the caller |
