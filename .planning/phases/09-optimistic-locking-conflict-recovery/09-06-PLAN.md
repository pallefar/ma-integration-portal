    - validators/*.js — the `EmptyBodySchema` registrations for these routes; confirm they read no body

  <action>
Each of these seven routes today resolves nothing: it filters the lane, compares lengths to detect
not-found, and writes. To carry a precondition it must first resolve the record.

For every one of the seven, in this order:
  1. Keep the route's existing role and clearance gates exactly where they are, untouched.
  2. Resolve the target record from the lane by id. When it is absent, return the route's existing
     not-found response with its existing wording — do not change it, and do not turn a not-found into
     a conflict. Deleting something already gone is not a conflict; the record is in the state the user
     wanted.
  3. Call `conflictIfStale` with the resolved record, taking the expected version from the query
     channel through `parseExpectedVersion`. Return early when it responded. For the two DD routes,
     pass the same clearance filter plan 04 wires on their POST siblings, so the delete conflict body
     is narrowed identically.
  4. Then perform the existing filter-and-reassign and `writeDb(db)` unchanged.

Do not change any registered schema: the precondition travels in the query string, so `EmptyBodySchema`
stays correct for all seven and the body remains rejected-if-present.

The storage layer already carries the second half of this: plan 01's version-aware DELETE predicate
means a delete that loses the race between this request's read and its write is rejected inside the
`.immediate` transaction even when the route-level precheck passed. Both layers stay.

**test/optimistic-locking-contract.test.js** — append, for RAID as the representative and for at least
one route from each of the other collection families (task, synergy, org position, DD finding): a stale
`?expectedVersion=` delete returns 409 with the marker and the record still exists; a current-version
delete succeeds; a repeat delete of the now-gone record returns the route's not-found status, not a
conflict; and an omitted `expectedVersion` still deletes (no precondition supplied means no route-level
precondition — the storage layer still guards the cross-process case).
  </action>

The server's 409 body is identical for an edit conflict and a stale delete. The client selects the copy
variant from the intercepted request's method, which the wrapper already holds — no new server field is
introduced, and the two surfaces stay one component.

Add the destructive variant to `showConflictDialog`, taken when the method is `DELETE`:
  - Title, primary label, secondary label and the in-flight primary label all come from the
    stale-delete rows of the UI-SPEC Copywriting Contract.
  - The primary action is styled destructive — `--status-danger`, via a `.conflict-btn-delete` class —
    and is the only coloured action in this variant; the orange accent is not used here.
  - No diff list: this variant shows the title, the attribution line and the actions. Attribution
    follows exactly the same rules as the edit variant, including the fallback sentence when actor or
    time is missing, so a lazily-stamped record produces a readable line rather than a blank one or an
    interpolated missing value.
  - The dialog itself IS the confirmation. Do not add a browser confirmation prompt and do not stack a
    second dialog — one explicit destructive click is the whole gesture.
  - Clicking the destructive action swaps its label to the in-flight delete label and disables it while
    leaving cancel enabled, then re-fires the original DELETE with the server's fresh version. Extend
    `withFreshVersion` so that for a query-carried precondition it rewrites the `expectedVersion` value
    in the URL rather than a body field — build the rewritten URL through the URL API rather than string
    surgery, so an existing query string and encoding survive.
  - A second conflict on that resubmission re-renders this same dialog shell in place with refreshed
    attribution, through the existing `activeConflictDialog` guard. A not-found on resubmission (someone
    else completed the delete) renders the inline error banner from plan 03 with that reason, rather
    than a silent success or a silent failure.
  - Cancel closes the dialog and sends nothing. The record is kept.

Note that `DELETE /api/synergies/:id/cost-entries/:eid` is a DELETE-method route that updates a synergy
initiative rather than deleting a record. It will now render this variant. That is acceptable — the
user is in fact deleting a cost entry — but record it in a comment so a future reader does not read it
as a bug.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → in-scope DELETE routes | An untrusted `expectedVersion` query parameter is now the only precondition input these routes accept |
| delete 409 response → browser | A conflict body for a record the caller is trying to destroy, including DD records inside the clean room |
| destructive dialog action → `/api` | A user-initiated re-fire of a destructive request |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-26 | Tampering | `expectedVersion` on DELETE routes | medium | mitigate | Parsed and bounds-checked by the single `parseExpectedVersion` helper from plan 02, which rejects a non-integer or negative value with a 400 before any record is read, and never interpolates it into SQL. `EmptyBodySchema` stays registered so a request body is still rejected. |
| T-09-27 | Information Disclosure | DD delete conflict body | high | mitigate | The two DD delete routes pass the same clearance filter their POST siblings use, evaluated against the record's current area, so a delete conflict cannot become a wider read channel than the DD read path. Asserted by a test that moves a record's area out of the caller's grant. |
| T-09-28 | Elevation of Privilege | precheck placed before a role or clearance gate | high | mitigate | Every `conflictIfStale` call is inserted AFTER each route's existing role and area gates, never before, so an uncleared caller still receives the original refusal and never learns from a conflict body that a record exists. Placement is stated per route in Task 1 and asserted by the pre-existing clearance tests continuing to pass unmodified. |
| T-09-29 | Denial of Service | destructive re-fire loop | medium | mitigate | The destructive action re-fires only on a human click, never automatically and never on a timer. A second conflict re-renders and stops. Asserted by the fetch-call-count cases in the sandbox harness. |
| T-09-30 | Repudiation | confirming a delete the user did not intend | medium | mitigate | The stale-delete dialog is itself the confirmation surface with exactly one destructive click, per D-08, and no browser prompt is stacked on it. Cancel sends no request at all. A grep gate asserts no confirmation prompt was added inside the wrapper region. |
| T-09-SC | Tampering | npm/pip/cargo installs | high | accept | No package is installed or upgraded in this plan. |
</threat_model>
