**server.js** — add the version precondition to the two main upsert routes.

In `POST /api/integration-tasks`, call `conflictIfStale` inside the `if (b.id)` branch, immediately
after the `if (!task) return res.status(404)` guard and BEFORE the empty-title guard and the field
mutation block, returning early when it responded. Placement matters: the handler's own comment records
that `readDb()` hands back a shared cache, so a mutation followed by an early return would silently
stick in the read model. The precheck must run before anything is mutated.

In `POST /api/synergies`, do the same inside its `if (b.id)` update branch — after the not-found guard,
before any field assignment.

Leave the create branches of both routes untouched. A create carries no version precondition because
there is no prior state to be stale against. The same applies to `POST /api/integration-tasks/instantiate`
and `POST /api/integration-tasks/from-remediation`, which only push new records.

Extend `conflictIfStale`'s input resolution into a shared `parseExpectedVersion(req)` helper that reads
`req.body.version` when present and falls back to `req.query.expectedVersion` when it is not, so the
one contract covers both the JSON-body routes here and the body-less DELETE-shaped routes in later
plans. Parse the query form with an explicit integer check: a value that is not a non-negative integer
responds 400 before any record is read, rather than being coerced. There is no query-schema mechanism
in `validators/index.js` (it validates `req.body` only), so this bounds check lives in the helper — one
place, not per route. Record that reasoning in a `[security]`-prefixed comment at the helper.

**validators/workstream.js** — add `version: z.number().int().nonnegative().optional()` to
`TaskUpsertSchema` and `SynergyUpsertSchema`. On the synergy schema, add a one-line comment stating
that this is the optimistic-lock version of the initiative record itself, distinct from the per-entry
`version` field inside the same record's nested `baselines` array — the word is already overloaded in
this object and a future reader will otherwise conflate the two. Without the schema field zod strips
the key and the precheck silently never fires while every existing test stays green.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `/api/integration-tasks`, `/api/synergies*` | Untrusted JSON body plus, on the cost-entry delete, an untrusted query parameter |
| browser → 409 responses from these routes | The conflict body echoes the current task/initiative state back to the caller |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09-09 | Tampering | `parseExpectedVersion` query-channel parse | medium | mitigate | Explicit non-negative-integer check in the one shared helper, responding 400 before any record is read. No coercion, no `parseInt` fallthrough to `NaN`, and never interpolated into SQL — it reaches `json_extract()` only as a bound parameter. |
| T-09-10 | Spoofing | the unrecognized-stage 409 vs. the conflict 409 | medium | mitigate | The pre-existing business-rule 409 keeps its original body and never gains the `conflict` marker. A dedicated negative-control test asserts this, so a business refusal can never be mistaken by the client for "someone else changed this". |
| T-09-11 | Information Disclosure | conflict body for tasks and synergy initiatives | medium | accept | Neither collection is area-gated: integration tasks and synergy initiatives are visible to every deal member who can reach the Execution Hub, so echoing the current record to a caller who just attempted to write it exposes nothing they could not already GET. The area-gated collections are handled with the clearance filter in plans 04 and 05. |
| T-09-12 | Tampering | mutation-before-precheck ordering | high | mitigate | `readDb()` hands back a shared cache; a route that mutates the resolved record and then returns 409 leaves the read model dirty for the rest of the request. Every precheck call is placed after the not-found guard and before the first field assignment, and each route's acceptance criterion asserts the stored record is unchanged after a 409. |
| T-09-SC | Tampering | npm/pip/cargo installs | high | accept | No package is installed or upgraded in this plan. |
</threat_model>
