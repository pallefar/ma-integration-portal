Reshape the accumulated cases into the four-part gate, reusing `test/busy-503-contract.test.js`'s
mechanics verbatim rather than inventing a second scanning approach.

**Part 1 — structural coverage scan.** Read `server.js`'s live source text. Isolate each route
handler's body with the same character-index brace-matching helper the 503 contract test uses. For
every handler whose body both references one of the versioned lane helpers and calls `writeDb(`, assert
the handler also calls the version precheck before that `writeDb(` call. Exempt, by an explicit
allow-list carrying a one-line reason each: handlers that only push new records (the instantiate,
from-remediation, copy-to-target, import and create branches), and the append-only decisions route. The
allow-list is the point — a new route is caught by default and its author must consciously classify it.
Never hand-maintain a list of protected route paths; that list is exactly what rots.

**Part 2 — live inventory cross-check.** Assert every name in `VERSIONED_COLLECTIONS` is present in
`ARRAY_COLLECTIONS`, that both lanes of each demo/custom split are listed, and that the set's size
matches the enumerated expectation. Assert `orgDecisions` is absent, with an inline comment citing the
append-only finding and CONC-02's naming of it, so a future developer who adds it has to confront the
reason. Cross-check the other direction too: every lane helper referenced by an in-scope route resolves
to a collection that is in the set — this is the check that would have caught a missing `custom*` lane.

**Part 3 — real behavior proof.** Consolidate the per-collection cases plans 01 through 06 appended
into a table-driven suite covering, for each of the seven in-scope collections: a stale update returns
409 with the marker and the stored record is unchanged; a current update returns success and the stored
version advances by exactly one; a stale delete returns 409 with the marker and the record survives; a
current delete succeeds. Run each case against both the demo lane and the custom lane for the three
dual-lane collections — a suite that only exercises demo mode would pass while every real-deal write on
the same feature stayed unprotected.

**Part 4 — negative control.** Assert both pre-existing unrelated 409s — the empty-deal steerco pack
and the unrecognized synergy stage — return a 409 whose body has no conflict marker, so neither can
ever open the conflict dialog. Assert as behavior against the running routes, not by grepping the
source for a status code: a grep-only check would pass even if the discrimination were missing.

**test/optimistic-locking-cross-process.test.js** — extend beyond RAID. Add the same-record and
different-record pairs for an integration task and for a synergy initiative, so the per-record
granularity claim is proven on more than one collection and not on a shape that happens to be unique to
RAID. Add one cross-collection case: two children writing different collections concurrently both
commit, proving the version predicate does not serialize unrelated work beyond what Phase 8's write
lock already does. Keep every case on real spawned processes — in-process contention simulation
deadlocks, per Phase 8's own research finding, so do not attempt it.

**scripts/soak.js** — teach the reconciliation about the new outcome class. Today a write either is
acknowledged, or fails with a bounded 503. A 409 is a third outcome and must be counted as its own
class, not folded into either:
  - A 409-rejected write must NOT count as an acknowledged write and must NOT count as a lost write.
    Without this the soak would read every legitimate conflict as data loss and mask a real regression.
  - Assert the invariant that matters: for every acknowledged write, the record's stored state reflects
    that write, and no acknowledged write was overwritten by a concurrently-409'd one. A 409 means
    nothing persisted — the same guarantee Phase 8's CR-01 fix established for 503 — so the audit
    one-to-one reconciliation must still hold with 409s in the mix.
  - Report the 409 count in the soak's summary output alongside the bounded-503 count, so an operator
    can see the conflict rate rather than inferring it.
  - Keep the `committedButUnaudited` violation exactly as Phase 8 left it.

Then run the soak against real servers and record the result in the SUMMARY: acknowledged count, lost
count, 503 count, 409 count, audit reconciliation and violation count.
