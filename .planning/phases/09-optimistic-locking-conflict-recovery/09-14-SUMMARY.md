# Phase 9 Plan 14: In-app delete confirm Summary

A delete on any of the five covered surfaces now asks once, in the `.conflict-modal` shell, and the same overlay becomes the "still delete it?" stale-delete dialog when the DELETE meets a conflict — no browser-native confirm precedes or follows it (R7 F-6, SC7).

## What was built

- **`window.maConfirmDelete(message, url)`** (`public/js/transitions.js`, inside the `ma-fetch-wrapper` region): opens a conflict session in a new `confirmState` rendered by `renderConflictSession` — title = the page's question via `textContent`, actions "Cancel" + red "Delete" (`CONFIRM_DELETE_LABEL`, `.conflict-btn-delete`), in-flight "Deleting…". "Delete" sends the DELETE through the internal `attemptFetch` with `{ reapply: true, confirmSession }`; a 2xx settles with the Response, a marker 409 adopts the body and re-renders the SAME session as the existing stale-delete variant (no banner), anything else settles with the Response so the page shows its own error, and a network failure rejects.
- **Five handlers routed through it**: task, initiative, cost entry, RAID entry (execution.js) and org position (org.js), each with its existing question verbatim and its `maVersionOf` precondition unchanged. Cancel => `null` => nothing happens (org re-enables its button).
- **UI-SPEC A8** + reworded "Destructive confirmation" row + a new "Delete" primary-action row.
- **Tests**: CF1–CF11 (node:vm), C5 structural guard, `synergy-cost-ui (c)` re-expressed.
- **Browser scenarios** (`f6-confirm.js`): `delete-confirm-raid`, `delete-confirm-surfaces`, `confirm-widths`; `raid-delete-f1`, `raid-f2-delete-anyway`, `org-delete-anyway-f2` updated.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Vacuous inline-error check in `org-delete-anyway-f2`**
- **Found during:** Task 3 (new `delete-confirm-surfaces` refusal check returned `null`)
- **Issue:** the 09-12 scenario (and my first draft) queried `.org-delete-error`; the element is `#org-delete-error`, so "no inline org error alongside the dialog (WR-02)" could never fail.
- **Fix:** both scenarios read `document.getElementById('org-delete-error')`; the WR-02 check is now real and passes.
- **Files:** scripts/uat/phase9-scenarios/f1f2-pages.js, f6-confirm.js
- **Commit:** bbe0203

**2. [Rule 2 - Missing critical] Exit lock while the first DELETE is in flight**
- **Found during:** Task 1 design
- **Issue:** in the confirm state `originalRes` is `null`, so Escape/overlay-click while the DELETE was on the wire would resolve `null` ("nothing sent") although the delete may still land — the page would show a stale row.
- **Fix:** Cancel is disabled and Escape/overlay are ignored while `confirmState && inFlight`; once a 409 turns it into the stale state normal exits apply.
- **Files:** public/js/transitions.js
- **Commit:** 6264ada
