Per D-10-09. In openDbFile(dbFilePath, schemaPath): replace the bare mkdirSync with ensurePrivateDir(path.dirname(dbFilePath)), which creates the missing directories with mode 0o700 and then chmods 0o700 ONLY the directories this call itself created (explicit chmod because umask can strip bits from mkdir's mode argument) — it never chmods a pre-existing directory (the repo's own data/ dir and any shared parent of an MA_*_PATH override stay as they are; real mode's data dir is chmodded by ensureRealDataDir in 10-01, fatal on failure). If the file does not exist, create it with fs.openSync(dbFilePath, 'a', 0o600), close it and chmod it 0o600 — a failure on a path this call created is always fatal (we own it; failure means something is badly wrong). If the file pre-existed, tighten it with chmodPrivateFile(dbFilePath, {preExisting: true}) (tightens a pre-existing 0644 file). Then construct the Database and run the existing pragma/schema contract unchanged; afterwards chmodPrivateFile on `-wal` and `-shm` when present (pre-existing sidecars use {preExisting: true}).

Failure policy for pre-existing paths (D-10-09 + PRD acceptance 6 — dev/demo boot must not crash): chmodPrivateFile takes an options object {preExisting, strict} where strict defaults to dbFiles.IS_REAL_MODE. On a chmod error: win32 EPERM/ENOSYS → ignored (unchanged); preExisting && !strict && code in {EPERM, EROFS} → console.warn once per path `[security] could not tighten <path> to 0600 (<code>) — dev/demo continues; real-deal mode refuses to start on this` and continue; anything else (strict real mode — the real data dir is owned by the service user, so a failure is a misconfigured host — or any other error code) → throw an Error prefixed `[security]` naming the path and the error code (fail closed). Call fs.chmodSync through the fs module object at call time (not a destructured reference) so tests can stub it. Add a `[security]` comment: R2-06/OPS-08, why chmod after create (umask), why sidecars inherit, why only self-created directories are chmodded, and why dev/demo tolerates EPERM/EROFS while real mode does not.

Create test/file-modes.test.js: skip the whole file when process.platform === 'win32'; call process.umask(0o022) before requiring anything; unit cases on a temp dir: openDbFile on a new nested path → every newly created dir 0700, file 0600, and after one write (`CREATE TABLE IF NOT EXISTS t(x)` + insert) the -wal and -shm exist and are 0600; a pre-created 0644 file and 0644 -wal are 0600 after openDbFile; a PRE-EXISTING parent directory at 0755 is still 0755 after openDbFile creates a new file inside it (only self-created dirs are chmodded); with fs.chmodSync stubbed to throw an EPERM error (and separately EROFS) for one pre-existing 0644 database path, openDbFile in dev mode returns a working connection and console.warn received exactly one `[security] could not tighten` line, while chmodPrivateFile(samePath, {preExisting: true, strict: true}) throws. Add a child-process case for the whole app (a non-owned or read-only file cannot be produced without root, so the stub stands in for it): spawnSync process.execPath with an inline `-e` script that stubs fs.chmodSync to throw EPERM for the pre-placed 0644 temp DB copies, then requires server.js in dev mode (MA_* temp paths, no MA_MODE) and listens on 127.0.0.1:0 → GET /healthz 200, exit 0, stderr contains `[security] could not tighten`; the same script with MA_MODE=real and MA_DATA_DIR = a pre-populated temp dir → exits non-zero with a `[security]` message (real mode stays fatal).
