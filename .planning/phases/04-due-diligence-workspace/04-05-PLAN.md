<objective>
Let a DD request item point at where its evidence actually lives — TE's licensed virtual data room — and
record who was given access to which part of it, without the app ever becoming a document store.

Purpose: DD-05. TE already licenses a VDR; duplicating documents into this app would create a second,
unmanaged copy of the most sensitive material in an acquisition. The value this app adds is the reference plus
the access-grant record, so the IL can answer "who could see the HR folder, and when" from one place.

Output: a per-item data-room reference, an area-level aggregate view, an audited access-grant record, and a
test proving no document ever enters the system.
</objective>

<interface_contract>
- `vdrLink` on a `ddRequestItems` row: `null`, or
  `{ url: string, folderRef: string, label: string, updatedAt: string, updatedBy: string }`.
  `url` must be an absolute http or https URL. `folderRef` is the data room's own folder or index
  identifier as the operator sees it. `label` is a short human caption. There is at most ONE per item.
- Setting a reference: send `vdrLink` inside the existing `POST /api/dd/request-items` upsert body.
  Sending `vdrLink: null` clears it. The server stamps `updatedAt` and `updatedBy`; a caller-supplied value
  for either is ignored.
- `GET /api/dd/vdr-links` optional `area` query. Response:
  `{ areas: [{ area, label, links: [{ itemId, text, url, folderRef, label, updatedAt, updatedBy }] }] }`,
  containing only areas the caller is cleared for and only items that actually carry a reference.
- `POST /api/deals/:id/vdr-grants` body: `{ username: string, vdrRef: string, note?: string }`. Response
  `{ success: true, grant: { username, vdrRef, note, grantedBy, grantedAt } }`. The record is written ONLY as
  an audit security event with `action: 'vdr-access-grant'` — there is no separate collection to drift out of
  sync with the trail, and the audit store is the one place in this system that survives deal deletion.
- `GET /api/deals/:id/vdr-grants` is NOT part of this phase: reading the grant history is the admin audit
  viewer's job (D-20 defers an IL-scoped audit read).
</interface_contract>

| browser -> POST /api/deals/:id/vdr-grants | A compliance assertion about who may see external MNPI is recorded here |
