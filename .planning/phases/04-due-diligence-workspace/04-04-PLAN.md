<objective>
Build the DD findings register and the one-click conversion that turns a finding into owned, tracked
integration work — closing the loop from "we found something in diligence" to "someone owns fixing it".

Purpose: DD-02 and DD-03. Findings are the output of diligence; a finding that never becomes a Day-1 task or
a RAID entry is a note in a document nobody reads. D-12 requires the link to run both ways so an IL can prove
at close which findings were actually dispositioned.

Output: the findings collection surfaced through clean-room-filtered routes, a four-level RAID severity scale,
the conversion route with bidirectional references and source dedup, and the findings UI.
</objective>

<interface_contract>
- `ddFindings` row shape: `{ id, area, title, severity, owner, status, notes, linkedTaskIds, linkedRaidIds,
  createdAt, createdBy }`. Ids are minted with `newId('ddfind')`.
- `severity` is one of `low`, `medium`, `high`, `critical`. `status` is one of `open`, `mitigating`, `closed`
  (the same three values the RAID lane already uses).
- `linkedTaskIds` and `linkedRaidIds` are arrays of ids, empty on create.
- `DD_AREA_WORKSTREAM` (server.js), locked by D-25 and shaped exactly like the existing `REMEDIATION_WS`
  literal: `legal` to `ws_legal`, `financial` to `ws_finance`, `tax` to `ws_finance`, `hr` to `ws_hr`,
  `it` to `ws_it`, `commercial` to `ws_sales`, `operations` to `ws_ops`, `complianceEsg` to `ws_legal`.
- `RAID_LEVELS` becomes `['low', 'medium', 'high', 'critical']` in BOTH `server.js` and
  `validators/workstream.js` — they are two independent copies today, not one shared import.
- Conversion source string: `'dd-finding:' + finding.id`, written to the created task's and the created RAID
  entry's `source` field. The RAID lane's create path does not set `source` today; add that field.
- `POST /api/dd/findings/:id/convert` body: `{ toTask: boolean, toRaid: boolean }` — at least one must be
  true. Response: `{ success: true, task: <task or null>, raid: <entry or null>, finding: <updated finding> }`.
  A re-conversion returns the ALREADY-EXISTING task and entry rather than creating new ones.
- Converted task defaults: `title` from the finding's title, `workstreamId` from `DD_AREA_WORKSTREAM`,
  `phase` set to `day1`, `owner` from the finding's owner, `status` set to `todo`.
- Converted RAID defaults: `type` set to `risk`, `title` from the finding's title, `severity` copied
  verbatim from the finding, `workstreamId` from `DD_AREA_WORKSTREAM`, `owner` from the finding's owner,
  `status` set to `open`, `notes` from the finding's notes.
</interface_contract>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> /api/dd/findings | Untrusted finding text, severity and area cross here; findings are the most sensitive DD content |
| findings route -> task and RAID lanes | Conversion moves MNPI-derived content into collections that carry no area-based read restriction |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-20 | Information Disclosure | `GET /api/dd/findings` | critical | mitigate | `filterByAreaGrant()` on every list response, identical to the request-item path; by-id routes assert against the stored area |
| T-04-21 | Information Disclosure | conversion widening the audience | high | accept | Converted tasks and RAID entries have no area-based read restriction today and are visible to every deal member. Accepted for this phase and made explicit in the UI: the convert control states that the created task or entry is visible to the whole deal team, so an IL converting a restricted finding is choosing to widen its audience knowingly. Revisit with Phase 6's ORG-03 work if a real deal demands area-scoped tasks. |
| T-04-22 | Tampering | `POST /api/dd/findings` and the convert body | high | mitigate | `DdFindingUpsertSchema` and `DdFindingConvertSchema` registered in `WRITE_SCHEMAS`; area, severity and status all constrained by enum; the convert refine forbids a no-op call |
| T-04-23 | Elevation of Privilege | convert route as a read side-channel | high | mitigate | The convert handler asserts clearance against the finding's own area before reading any of its fields, and a refusal is audited — a caller cannot use conversion to copy an uncleared finding's title into a collection they can read |
| T-04-24 | Tampering | severity downgrade on conversion | medium | mitigate | The four-level RAID scale lands in both copies in the same commit; the handler copies severity verbatim with no mapping table, asserted by a round-trip test |
| T-04-25 | Denial of Service | repeated conversion | low | mitigate | Source-string dedup makes a repeated conversion return the existing records without writing |
</threat_model>
