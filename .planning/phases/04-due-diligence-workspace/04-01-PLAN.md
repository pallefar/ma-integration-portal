<interface_contract>
Identifiers this plan creates and later plans depend on — do not rename them:

- `DD_AREAS` (db/accessPolicy.js): ordered array of `{ id, label }`, exactly these eight ids in this order —
  `legal` ("Legal"), `financial` ("Financial"), `tax` ("Tax"), `hr` ("HR"), `it` ("IT"),
  `commercial` ("Commercial"), `operations` ("Operations"), `complianceEsg` ("Compliance/ESG"). (D-10)
- `DD_AREA_IDS`: the eight id strings derived from `DD_AREAS`.
- `grantedAreas(deal, user)` -> `string[]`: every `DD_AREA_IDS` entry when `user.role` is `admin` or `hrbp`
  (admin + Integration Lead see every area, D-16); otherwise `deal.memberGrants[user.username].ddAreas`
  intersected with `DD_AREA_IDS`; `[]` when the user, the deal or the grant entry is absent.
- `hasAreaGrant(deal, user, areaId)` -> boolean.
- `filterByAreaGrant(items, deal, user)` -> the input array filtered to items whose `area` is granted,
  preserving relative order.
- `assertAreaGrant(deal, user, areaId)` -> throws `AreaAccessError` (a class carrying `status = 403` and
  `message = 'You are not cleared for that due-diligence area.'`) when not granted; returns undefined otherwise.
- `deal.memberGrants` shape: `{ [username]: { ddAreas: string[] } }` — an additive field on the control.db
  deal record. `deal.members` stays a flat array of username strings (D-23).
- `ddRequestItems` row shape: `{ id, area, text, owner, status, dueDate, blocked, vdrLink, notes, source,
  createdAt, createdBy }`. `status` is one of `open`, `requested`, `received`, `reviewed`, `closed` (D-14).
  `blocked` is a boolean. `vdrLink` is `null` in this plan (Plan 05 fills it).
- `overdue` is COMPUTED on read and attached to the response object, never stored: true when `dueDate` is a
  non-empty `YYYY-MM-DD` string strictly earlier than today's UTC date AND `status` is not `closed` (D-15).
- Uniform refusal: every DD by-id route returns HTTP 403 with the body
  `{ error: 'You are not cleared for that due-diligence area.' }` for BOTH an unknown item id AND an item in
  an uncleared area — one status, one message, no distinction (Phase 3's WR-02 anti-enumeration precedent).
</interface_contract>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> /api gate | Untrusted request body and query string cross here; identity is resolved from the session cookie or the break-glass header |
| /api gate -> deal database | The resolver binds exactly one SQLite file; a wrong bind is a cross-deal MNPI leak |
| DD route handler -> accessPolicy | The row-level clean-room boundary this plan introduces: a deal member is inside the deal but outside an area |
