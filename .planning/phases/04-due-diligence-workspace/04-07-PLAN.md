<interface_contract>
Seven steps, in this order, with these element id conventions (copied from the existing wizard precedent so
the shared styles apply): the container carries `id="deal-wizard"`, the step counter
`id="current-step-num"`, each step panel `id="wizard-step-N"` with class `wizard-step`, and each progress
segment `id="wizard-stepN-fill"`.

1. **Basics** — deal name, target company, deal type, signing date, expected close, Day-1 date, deal size,
   currency. Next submits to `POST /api/deals/wizard/basics`. Mandatory.
2. **Team and access** — member usernames plus an explicit need-to-know notice naming who will and will not
   see the deal. Next submits basics plus members to `POST /api/deals`, then immediately binds the session
   with `POST /api/deals/select`. Mandatory. This is where the deal comes into existence (D-05).
3. **Readiness assessments** — lists the deal's own published templates from `GET /api/assessment-templates`
   and requires an owner and a due date for each of the three subjects before Next. Next calls
   `POST /api/assessment-instances/assign` once per template, then stamps the `assessments` setup step.
   Mandatory (D-08); it does NOT block later work (D-09).
4. **Integration scope** — workstream selection, integration depth, and an optional checklist-template
   instantiation. Skippable.
5. **Timeline markers** — Day-1, 30, 60 and 100-day dates. Skippable.
6. **Data room and DD kickoff** — an optional data-room base reference and an optional
   "load the standard DD request checklist" action calling `POST /api/dd/request-items/instantiate`. Skippable.
7. **Review** — a read-only summary of what each step produced, a Finish control that stamps
   `complete`, and a redirect to the dashboard.

- Every skippable step shows a Skip control alongside Next; skipping stamps nothing and advances.
- A step's Next is disabled while its request is in flight and re-enabled on any response.
- A non-2xx response renders the server's `error` string. That string is already field-path prefixed
  (for example `targetCompany: Target company is required.`), so the handler splits on the first colon and
  places the message next to the field whose name matches the prefix, falling back to a step-level error
  banner when no field matches.
</interface_contract>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser page -> /api wizard routes | Every step's payload crosses the same gate as any other write; the page is a client of the same pipeline |
| operator -> the basics step | The target company's identity pre-announcement is entered here |
| page access map -> the wizard page | A client-side convenience gate in front of a server-enforced one |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-39 | Elevation of Privilege | wizard page reachable by a non-privileged role | medium | mitigate | The page-access map redirects a non-admin, non-Integration-Lead role, and every endpoint the page calls is independently restricted server-side by the existing role policy — the page gate is convenience, never the control |
| T-04-40 | Tampering | client-side validation bypass | medium | accept | A user can call the endpoints directly and skip the page entirely. Accepted because the page holds no rule the server does not also hold: D-07's single-source-of-truth design is what makes bypassing the page harmless |
| T-04-41 | Information Disclosure | operator-supplied values rendered on the page | high | mitigate | Text-only rendering throughout, asserted by a source check; deal and target names are MNPI |
| T-04-42 | Information Disclosure | a target's real name entered before announcement | medium | accept | Codename guidance is advisory, matching 04-CONTEXT.md's "Specific Ideas" — enforcement would block legitimate post-announcement deals |
| T-04-43 | Denial of Service | double-submit on a step | low | mitigate | Each Next is disabled while its request is in flight and re-enabled on any response, so a double click cannot create two deals |
| T-04-44 | Tampering | a second, unguided creation path | medium | mitigate | The superseded modal is removed rather than left dormant, and a source assertion fails the suite if any file still calls it |
</threat_model>
