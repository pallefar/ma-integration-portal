<objective>
Close G-04-8: re-entering the wizard after an interruption creates a DUPLICATE deal
and silently re-binds the session to it, orphaning the original.

Confirmed in source, do not re-investigate: `public/js/deal-wizard.js` sets
`state.dealId = null` on every page load and makes no attempt to detect an existing
incomplete setup, so a reload restarts at Step 1; re-walking steps 1-2 posts to
`POST /api/deals`, which calls `controlStore.createDeal()` unconditionally with no
dedup or in-progress check. The UAT produced `deal_msc1wlvu62ced9fc` and
`deal_msc1xn4g4ec9a1ed`, both named "Project Meridian" with the same target, with the
session re-bound to the second and the admin console listing two indistinguishable rows.

The design is decided and NOT open for reconsideration: on entering the wizard,
detect the session's bound deal whose setup is unfinished and RESUME its setup where
it left off. The deal's own `setup.steps` object is the resume cursor — no new state
is invented. D-05 (create-early) is preserved exactly: the deal is still created the
moment basics and team succeed.

Purpose: an interruption must be survivable without producing a second, orphaned
copy of a deal — for MNPI records, two indistinguishable deal rows is a data-integrity
and audit problem, not a cosmetic one.

Output: a server-side duplicate guard a stale cached script cannot bypass, a wizard
that resumes rather than restarts, and regression coverage at both layers.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> POST /api/deals | Deal creation crosses here; the payload carries a pre-announcement target company name, which is MNPI |
| GET /api/auth/me -> the wizard's resume cursor | The session's own server-side deal binding decides which deal the wizard adopts |
| GET /api/deals -> the resumed wizard's state | The adopted deal record's name and target company are rendered back into the page |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-52 | Tampering | `POST /api/deals` | high | mitigate | The duplicate guard is scoped by `createdBy` to the CALLING session's own username plus an exact name and target match — it can never return another user's deal to a caller, and it only ever returns a deal that caller created |
| T-04-53 | Information Disclosure | wizard resume adoption | high | mitigate | The wizard adopts only the deal `GET /api/auth/me` reports as this session's own binding, cross-referenced against `GET /api/deals`, which is already membership-filtered server-side — the client never selects a deal by guessing an id, and a non-member's `GET /api/deals` simply will not contain it |
| T-04-54 | Information Disclosure | resume notice rendering | high | mitigate | The notice names a deal and a target company (both MNPI) and is written with textContent only, exactly like every other operator-supplied value in this file; the standing "assigns no markup sink" test covers the whole file including the new code |
