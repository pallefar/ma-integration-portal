<objective>
Ship the curated standard M&A due-diligence request checklist as a seeded template every new deal inherits,
plus the one-click route that turns it into live, ownable request items.

Purpose: D-13 — the 34-task integration-checklist precedent proved that an operator handed a blank page keeps
their spreadsheet. Diligence is the first thing a new deal does; it must arrive with a defensible starting
list the IL prunes rather than authors.

Output: the template content as reviewable source, the demo-store seeding script, the deal-seed allowlist
entry, the instantiate route, and a test proving both the seeding path and the dedup.
</objective>

<interface_contract>
- `DD_REQUEST_TEMPLATE` (db/ddRequestTemplateSeed.js): one object
  `{ id: 'ddtpl_standard', name: 'Standard M&A due-diligence request list', version: 1, items: [...] }`.
- Each item: `{ id, area, text, ownerHint }` where `area` is one of the eight `DD_AREA_IDS` and `id` is
  `dd_<area>_<two-digit index>` (for example `dd_legal_01`, `dd_complianceEsg_10`). `ownerHint` is a short
  role string (`Legal`, `Finance`, `HR`, `IT`, `Commercial`, `Operations`, `Compliance`) and seeds the
  created item's `owner` field.
- Item count: exactly 10 per area, 80 total. The item TEXTS are locked to 04-RESEARCH.md's
  "## Seeded DD Request Checklist Content" section — copy each semicolon-separated phrase verbatim as one
  item's `text`, in the order listed there, mapping that section's headings to area ids: Legal to `legal`,
  Financial to `financial`, Tax to `tax`, HR to `hr`, IT to `it`, Commercial to `commercial`,
  Operations to `operations`, Compliance/ESG to `complianceEsg`.
- `seedDdRequestTemplates(demoDbPath)` returns `{ inserted: number }`. Idempotent: it replaces an existing
  `ddtpl_standard` row rather than appending a second one.
- Instantiate source string: `'ddtemplate:' + templateId + ':' + itemId`, stored on the created item's
  `source` field, mirroring `POST /api/integration-tasks/instantiate`'s own dedup convention.
- `POST /api/dd/request-items/instantiate` body `{ templateId: string }`; response
  `{ success: true, created: number, skipped: number }` where `skipped` counts template items in areas the
  caller is not cleared for.
</interface_contract>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| committed demo store -> new deal database | The allowlist copy is the only channel by which anything pre-exists inside a real acquisition workspace |
| browser -> POST /api/dd/request-items/instantiate | An authenticated contributor triggers a bulk write into MNPI storage |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-15 | Information Disclosure | `db/dealSeed.js` allowlist | high | mitigate | Only `ddRequestTemplates` is added; the allowlist direction (never a denylist) means the two live DD collections added in Plan 01 are structurally never copied, proven by `test/deal-seed.test.js`'s empty-collections sweep |
| T-04-16 | Elevation of Privilege | instantiate route | high | mitigate | `grantedAreas()` is computed once per call and every item outside it is skipped and counted, so a bulk write cannot materialise content the caller could not have created one at a time |
| T-04-17 | Tampering | instantiate payload | medium | mitigate | `InstantiateDdRequestsSchema` bounds and requires `templateId`; the coverage gate fails the suite if the route ships unregistered |
| T-04-18 | Denial of Service | repeated instantiate calls | low | mitigate | Dedup by the stable source string makes a repeated call a read-only no-op; the write path is entered only when something was actually created |
| T-04-19 | Information Disclosure | skipped-count status line | low | mitigate | The UI reports only a count of items outside the caller's clearance and never names or labels an uncleared area |
</threat_model>
