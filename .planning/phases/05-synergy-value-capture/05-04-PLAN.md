<objective>
Deliver SYN-02 and SYN-04: cost-to-achieve as a planned figure plus a dated actual-cost list with a
computed net benefit (D-20, D-21), and task linkage stored as a list of task ids on the initiative
with a strictly informational relationship to value and stage (D-22, D-23).

Purpose: gross-only reporting is how synergy programs flatter themselves; Phase 7's RPT-03 needs net
benefit and needs it computed once. And a task-to-initiative link has to live in the synergy lane so
the existing task provenance and dedupe machinery cannot collide with it.
Output: two cost sub-routes, two new upsert fields, a task-id list, and two new test files.

Planner note (D-22, verified constraint, not a style preference): the rejected alternative — writing
a synergy reference into the task's own `source` string — collides with a real dedupe already in
`server.js` (`if (lane.some(t => t.source === source)) return`), which would cap a task at exactly
one initiative and could suppress a legitimate task creation. The linkage direction chosen here is
the one that leaves the task model untouched.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `POST /api/synergies/:id/cost-entries` | Untrusted date, amount and free-text note cross here |
| Browser → `DELETE /api/synergies/:id/cost-entries/:eid` | An untrusted entry id in the path selects which stored row is removed |
| Browser → `POST /api/synergies` `taskIds` | Untrusted id strings that are resolved against the bound deal's own task lane |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-18 | Tampering | `taskIds` on the upsert | medium | mitigate | Every supplied id is validated against `taskLane(db)` — the bound deal's own lane, resolved by the Phase 3 session-bound resolver — before any mutation, so an id from another deal is simply not found and the whole request is refused with no partial write |
| T-05-19 | Tampering | cost-entry delete by path id | medium | mitigate | The handler filters by the entry's generated id and 404s when no entry matches; it never indexes into the array, so a crafted numeric path segment cannot remove an arbitrary neighbouring row |
| T-05-20 | Tampering | task completion as a value channel | high | mitigate | No server code path reads task status when computing realized value, derived totals or stage; asserted by a no-side-effect test that completes a linked task and diffs all three fields (D-23) |
| T-05-21 | Input Validation | cost-entry `date` | medium | mitigate | Reuses `validators/dd.js`'s `isValidCalendarDate` refine rather than a bare length cap, closing the same shape gap the phase's month validator closes for `YYYY-MM` fields |
| T-05-22 | Denial of Service | unbounded `taskIds` / `costEntries` growth | low | mitigate | `taskIds` is capped by an array maximum in the schema; cost-entry notes and amounts are capped by the file's existing text and numeric-string bounds |
| T-05-23 | Information Disclosure | free-text cost note | low | transfer | Note text is rendered through the existing `esc()` discipline in Plan 07 and stored in the bound deal database only; generic injection hardening is canon and is covered by `/gsd-secure-phase`, not minted as a bespoke prohibition here |
| T-05-SC | Tampering | npm/pip/cargo installs | high | accept | No package is installed in this phase — 05-RESEARCH.md's Package Legitimacy Audit records zero new dependencies |
</threat_model>
