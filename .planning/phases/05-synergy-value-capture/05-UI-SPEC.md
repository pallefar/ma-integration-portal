# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Stack constraint (fixed, not a design choice):** vanilla JS, no framework, no build step. Styling lives in
> `public/css/style.css` (global) plus a `<style>` block inside `public/execution.html` (page-local, `.ex-*`/`.syn-*`/
> `.raid-*` classes). Rendering is string-concatenated `innerHTML` in `public/js/execution.js`, wrapped in one IIFE.
> This contract extends that file's existing classes and constants — `SYN_STATUSES`/`SYN_LABELS`/`SYN_COLORS`
> (lines 28-30), `renderSynergy()` (lines 216-285), `.syn-card`/`.syn-head`/`.syn-title`/`.syn-meta`/`.syn-money`/
> `.syn-track`/`.syn-fill` (execution.html lines 21-33) — it does not invent a parallel component system.

## Spacing Scale

The existing `.ex-*`/`.syn-*` CSS uses rem values close to but not strictly aligned to an 8-point grid (e.g. `.6rem`,
`.9rem`, `.75rem`). Do not retrofit existing card padding. **New CSS authored for this phase's new sub-components
must** use the declared scale below (rem equivalents at 16px root, existing project default):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (0.25rem) | Gap between a stage pill and its caret; badge internal padding |
| sm | 8px (0.5rem) | Gap between grid cells; cost-list row internal padding |
| md | 16px (1rem) | Gap between card sections (phasing / baselines / cost-to-achieve) when expanded |
| lg | 24px (1.5rem) | Padding around the expanded detail block |
| xl | 32px (2rem) | — (not needed at card-internal scale; reserved) |

Exceptions: the existing `.syn-card` outer padding (`.9rem 1.1rem`) and `.syn-track` height (`8px`) are pre-existing
and untouched — only the phase's new elements (grid, baseline list, cost list, stage picker, staleness badge) follow
the 4px-multiple scale above.

## Visual Hierarchy (focal point)

Checker Dimension-2 resolution — what draws the eye first, by context:

- **Page level (Synergy Tracker tab):** the four rollup stat tiles are the primary visual anchor — the only
  25.6px/800 numerals on the page. The card list reads second; the accent-colored "Generate phasing rows" CTA
  appears only inside an expanded card, so it never competes with the rollup at page level.
- **Collapsed card:** the stage pill (+ staleness badge when present) is the primary control and the first-read
  element after the title; `.syn-money` stays the right-edge anchor exactly as today.
- **Expanded card:** the monthly phasing grid is the primary content area — first sub-section in DOM order, the
  only scrollable region, and holder of the sole accent-colored button. Baseline history and cost-to-achieve are
  deliberately quieter (micro-label typography, no accent) so the grid keeps focus.

Typography-FLAG disposition (checker Dimension 4): the recommendation to re-space 11.5/12.8/13.75px was **declined
with reason** — all three sizes are lifted verbatim from the existing codebase (0.72/0.8/0.86rem appear 57 times in
`style.css` and in `renderSynergy()` itself); re-spacing them would make this phase's components inconsistent with
every neighboring surface. Hierarchy within the dense sub-components is carried by weight (600 vs 800), case and
color, per the app's established convention, not by size steps.

## Component Contract — new surfaces this phase adds

### 1. Stage control (replaces the single-click status cycle)

The existing `.syn-status` button cycles forward through 5 values on click with no concept of "stop" or "go back."
That model breaks under D-08 (gated forward) and D-09 (reasoned backward). Replace with:

- **Pill click (`.syn-stage`)** — advances one stage forward only (`idea→validated→committed→captured`). At
  `captured`, the click is a no-op (no wraparound back to `idea`) — this is what prevents an accidental silent
  demotion via the old cycle-and-wrap behavior. A rejected advance (D-08 gate) triggers the alert-with-reason
  contract above and the pill does not change.
- **Caret button (`.syn-stage-caret`)** — a small 24×24px `▾` button immediately right of the pill. Click opens an
  absolutely-positioned 4-row menu (`.syn-stage-menu`) listing all four stages; the current stage is marked
  (checkmark, not removed from the list). Selecting a stage *ahead* of current runs the same D-08 gate as the pill.
  Selecting a stage *behind* current runs the D-09 reason-prompt flow. Selecting the current stage closes the menu
  with no request. Menu closes on outside click or `Escape`.
- Both controls stay disabled (`pointer-events:none`, 0.5 opacity, no caret shown) when the calling user lacks write
  access to the initiative's workstream — mirrors the existing DD-04 "server-side authz, not UI hiding" precedent:
  the route independently rejects regardless of what the client renders.

### 2. Monthly phasing grid — progressive disclosure contract

**This is the highest-risk surface in the phase.** Do not render 36 rows inline in the default card view.

- **Collapsed (default) card state** shows exactly what today's `.syn-card` shows, plus the new compact indicators
  (stage pill+caret in place of the old status button, staleness badge if flagged, "N of M tasks done" line). No
  grid, no baseline list, no cost list are in the DOM at all in collapsed state — not merely `display:none`, absent
  from the rendered `innerHTML`, so a collapsed card costs nothing extra to render even across 5+ initiatives.
- **Expand toggle** — a full-width `.syn-expand-toggle` button at the card's bottom edge, label "▸ Phasing, baseline
  & cost details" collapsed / "▾ Hide details" expanded. Clicking rebuilds `.syn-detail` into the card via the same
  `renderSynergy()` re-render (see persistence rule below).
- **Expanded state** reveals three sub-sections in this order: ramp auto-fill controls + monthly grid, baseline
  history, cost-to-achieve. Each sub-section carries the "Section label" typography role as its heading.
- **Expansion-state persistence across re-render (concrete rule — this closes the "how does expand state survive a
  re-render" gap):** `renderSynergy()` rebuilds `#syn-list.innerHTML` wholesale on every status/realized/delete
  action today. Add a module-level `state.synExpanded` object (`{ [initiativeId]: true }`) that is **never** reset
  by `renderSynergy()` — it is read at the top of each card's render to decide whether to include `.syn-detail` in
  that card's markup, and written to only by the expand-toggle click handler. A user who expands a card, then edits
  a realized-value cell (which triggers a full re-render), must not lose their expanded state.
- **Ramp auto-fill controls** (`.syn-ramp-controls`): run-rate number input, start-month `<input type="month">`,
  curve-shape `<select>` (options: Cost 30/70/100, Revenue 10/40/70, Linear — D-05's three named shapes, verbatim),
  and the primary CTA button "Generate phasing rows". Generating rows when rows already exist prompts
  `window.confirm('This replaces the existing phasing rows. Continue?')` before the request — regenerating is
  destructive to manually-edited rows and must not be silent.
- **Grid — desktop (≥768px):** a `.syn-grid` scroll container, `max-height:360px; overflow-y:auto;`, with a sticky
  `.syn-grid-head` header row (Month / Target $ / Realized $). Each `.syn-grid-row` is a 3-column flex row.
- **Grid — mobile (<768px):** the row-based layout is abandoned entirely, not squeezed into horizontal scroll.
  Default view shows a 4-month window (prior month + current + next 2) as stacked `.syn-grid-mobile-row` cards, each
  full-width with the month as a bold header and Target/Realized as labeled rows beneath it. A text link "Show all
  36 months" expands the remaining rows inline, same stacked-card shape, no modal and no separate page (keeps to the
  single-page-render model this app already uses everywhere).
- **Editable vs read-only cells — the unambiguous rule (closes the tension explicitly flagged in this phase's
  brief):** an arrived month's Realized cell renders as an actual `<input type="number" class="syn-realized-input">`
  (existing input styling, reused verbatim). A **future** month's Realized cell renders as a `<span
  class="syn-grid-locked">` containing an em dash and a `title="Not yet arrived — editable once this month begins"`
  tooltip — **never** an `<input disabled>` or a `display:none`-toggled element. Using a structurally different DOM
  element (span vs input) for the locked state, rather than a style-toggled disabled input, is a deliberate choice:
  it closes the exact bug class found live in Phase 4 Wave 7 (a value assigned to the right element but rendered
  invisible because `style.display=''` silently reverts to the stylesheet default) by making "editable" and
  "locked" two different tags, not two states of the same tag. Target-$ cells are editable in every row regardless
  of arrival (forward planning is normal; only *realized* value is forward-booking-restricted per D-06).
- `.syn-grid-locked` styling: `color:var(--text-dim); background:var(--bg-subtle,#eef2f2); border:none; padding:.25rem .45rem; border-radius:4px; font-style:italic;` — visually flat and inert, contrasted against the bordered white `.syn-realized-input` box next to it in the same column.

### 3. Baseline history (D-12/D-14/D-15)

- `.syn-baselines` list, newest-first, **except** the very first entry is always pinned at the top labeled **"Deal
  case"** (D-14 — never "v1", never re-sorted out of first position even as more baselines accumulate below it).
- Each `.syn-baseline-row`: date, actor (who), stage-at-time (small stage-colored dot, not a full pill — avoids
  competing visually with the card's live stage pill), run-rate, and the reason — truncated to one line with the
  full text in a `title` attribute (matches the existing `.ex-src`/tooltip-truncation convention already used for
  long remediation-source text elsewhere in this file).
- **Re-baseline control (D-15, AUTHZ explicit):** a `.syn-rebaseline-btn` button, label "Re-baseline this
  initiative", rendered **only** when `window.__portalUser && (window.__portalUser.role === 'admin' ||
  window.__portalUser.role === 'hrbp')` — the `hrbp` role string is Integration Leader (renamed only in the UI
  label, unchanged internally per the existing app-wide convention). For every other role the button is **absent
  from the rendered markup**, not disabled — matching this phase's own D-15 wording exactly ("absent/disabled for
  other roles," resolved here to absent, the stronger of the two, consistent with DD-04's precedent that hiding a
  control client-side is cosmetic and the route enforcement is what actually matters). Clicking opens the same
  `window.prompt`-based reason flow as D-13's forced re-baseline.

### 4. Cost-to-achieve (D-20)

- `.syn-cost` section: a single planned-figure line ("Planned: $X.XM, expected {Month Year}") followed by
  `.syn-cost-list` — a plain list, **not** a grid, of dated actual-cost entries. Each `.syn-cost-row`: date, amount,
  optional note, delete button (reuses `.ex-del`). Add-entry mini-form matches the existing `.ex-add` pattern (date
  input + number input + text input + Add button) already used three times in this same file for tasks/synergies/
  RAID — no new form pattern invented.

### 5. Task linkage (D-22/D-23) — informational, not a control

- Renders as plain text + a thin progress track: **"4 of 6 tasks done"** using the existing `.ex-ws-track`/
  `.ex-ws-fill` bar styling (reused, not a new bar component). Rendered inside a `<div class="syn-task-progress">`,
  **never** a `<button>` — no `cursor:pointer`, no hover state, no click handler attached at all. This is the
  concrete rule that satisfies "must not look like a control that changes value or stage" from the phase brief:
  using a non-interactive tag with zero interactive CSS, rather than a disabled-looking button, removes the
  ambiguity by construction. Zero linked tasks renders the empty-state copy above instead of "0 of 0 tasks done".

### 6. Staleness (D-16/D-17/D-18/D-19)

- **Badge:** `.syn-stale-badge` pill next to the stage pill on any card whose `lastConfirmedAt` is more than the
  deal's configured threshold (default 30 days) old. Uses the warning palette declared above. Label: "Stale" with a
  `title` showing the exact last-confirmed date.
- **"Confirm current" control:** a small secondary button (`class="btn btn-secondary"`, matching the existing
  button system used elsewhere on this page), label **"Confirm current"**, placed next to the staleness badge (or,
  on a non-stale card, available at all times in a lower-emphasis spot in the card meta row — confirming resets the
  30-day clock even before it lapses, matching D-16's "deliberate action" model). Clicking calls a dedicated
  confirm-current write (touches `lastConfirmedAt` only) — **it must not share a click target, form field or route
  branch with the title/notes edit fields**, per D-16's explicit "not by editing a note" rule. Concretely: a note
  edit is a text-input `change` event; "Confirm current" is a distinct button `click` event hitting a distinct
  payload shape, so a code reviewer (or the checker) can verify the two can never be triggered by the same
  interaction.
- **Nudge:** stale initiatives surface via the existing Phase 4 deal-home owner-nudge pattern (`renderOwnerNudge()`
  in `public/js/due-diligence.js` — badge on a heading + a dismissible `.page-banner.page-banner--warning`, session-
  scoped dismissal via `window.makeBannerDismissible`). D-19 explicitly reuses this surface rather than inventing a
  second one; the new deal-home nudge counts `mine`-scoped stale synergy initiatives the same way DD's nudge counts
  `mine`-scoped open DD items, and stacks as an additional banner rather than merging text into the existing one.

### 7. Rollup restructure (D-18/D-21)

Replace the current 2-figure (`Realized` / `Deal target`) `#syn-rollup` card with:

- `.syn-rollup-tiles`: four stat tiles in a row (desktop) / 2×2 wrap (mobile, existing `flex-wrap:wrap` behavior on
  the rollup's containing flex already handles this with no new CSS), each using the "Rollup stat" typography role:
  **Gross realized**, **Cost incurred**, **Net benefit**, **Deal target** (existing derived total, D-04, kept for
  the demo showcase / PMO console / dashboard consumers that still read it unchanged).
  Net benefit = Gross realized − Cost incurred; render with the destructive color if negative (cost currently
  exceeds realized value — a real, expected early-deal state, not an error state).
- Below the tiles, one line in the "Body / data value" role using D-18's exact wording:
  **"realized $XM, of which $YM unconfirmed"** — `$X` = gross realized total, `$Y` = the portion of that total
  coming from initiatives currently flagged stale. Omit the sentence entirely (not "$0M unconfirmed") when no
  initiative is stale — a zero-value sentence reads as an error, not reassurance.
- The existing `%-of-target` progress bar (`.syn-track`/`.syn-fill`) is retained beneath the stale-split line,
  unchanged in appearance, now driven by Deal target vs Gross realized.
