<objective>
Deliver SYN-01's core capability end-to-end: a synergy initiative carries a phased, ramped monthly
target over the deal's horizon, generated from a run-rate + start month + curve shape (D-01, D-02,
D-03, D-05, D-24), with realized value entered period-by-period and only for months that have
already arrived (D-06, D-25). The existing targetM/realizedM pair becomes the derived rollup of
those rows (D-04).

This is the phase's tracer plan: Task 1 wires ONE path — validator, route, ramp math, storage,
derived read, client render, CSS, end-to-end test — before any horizontal expansion happens.

Purpose: prove the sub-route architecture, the derived-rollup rule and the client grid render on
one real path before seven more plans build on them.
Output: a working monthly phasing grid on the Synergy Tracker tab, backed by two new sub-routes
and a new test file.

Canon-referral note (prohibition probe): injection / XSS / prototype-pollution on this phase's new
free-text and numeric fields is canon — covered by `/gsd-secure-phase`, the existing `esc()` render
discipline and the zod pipeline. Not minted as a bespoke prohibition here.

Planner assumption (flagged, from 05-RESEARCH.md A1 and the phase brief): the arrived-month check
uses real wall-clock time uniformly in demo and real-deal mode, with NO `timeTravelDay` awareness,
following `computeOverdue()`'s established precedent (`server.js:3200-3205`). Consequence recorded
deliberately: the demo showcase's simulated day-N narrative and the grid's arrived/locked split are
driven by different clocks, so Plan 08's hand-tuned demo seed must date its phasing months around
today's REAL date, not relative to the demo's acquisition date.

Planner assumption (flagged, from the assumption-delta scan): this phase takes two singular-to-plural
transitions and each needs an explicit identity model. Resolved here rather than silently: a
**phasing row's identity is its `month` string** (unique within one initiative, which is why D-25's
sub-route is keyed on `:month` and why regeneration replaces the whole array rather than merging).
A **baseline entry's identity is `newId('bl')` plus a monotonically increasing `version` integer**
(Plan 03) — array position is never an identity.
</objective>
