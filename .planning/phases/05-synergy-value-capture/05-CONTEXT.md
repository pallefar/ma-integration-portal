# Phase 5: Synergy Value Capture - Context

**Gathered:** 2026-08-03 → 2026-08-06 (resumed from checkpoint)
**Status:** Ready for planning

<domain>
## Phase Boundary

Synergy tracking becomes a real value-capture program instead of a single
target-vs-realized pair. In scope: phased/ramped targets over time with
period-by-period realized value (SYN-01), cost-to-achieve (SYN-02), confidence
stage-gates with preserved baseline history (SYN-03), linkage to the integration
tasks that deliver an initiative (SYN-04), and a staleness signal (SYN-05).

Out of scope — belongs to Phase 7 (IMO Reporting & Exports): CSV/JSON export of
synergies, the formatted steerco PDF pack, and cross-lane report assembly. This
phase produces the data model and the in-app views those reports will read;
it does not produce the reports.

Phase 5 depends only on Phase 3 and is independent of Phase 4.

</domain>

<decisions>
## Implementation Decisions

### Phasing model

- **D-01:** Monthly periods are the phasing granularity. User chose monthly over
  the recommended quarterly. The consequence was surfaced before the choice —
  36 rows per initiative over a 3-year horizon — and accepted, mitigated by
  D-05 auto-fill.
- **D-02:** Run-rate (steady-state annual) is tracked separately from in-year
  realized value. An initiative can be at 100% run-rate while in-year banked
  value is far lower; practitioners treat this distinction as essential.
- **D-03:** The phasing horizon is 3 years, configurable per deal — covers the
  standard cost-synergy ramp to full run-rate without forcing a small
  acquisition into a full 3-year grid.
- **D-04:** The existing `targetM` / `realizedM` fields become **derived
  totals** (rollup of the phased rows) — not removed, not independently
  editable. Chosen for demo-showcase safety: every existing consumer (demo
  showcase, PMO console, dashboards) keeps working untouched.
  — **Reversibility:** costly — these two fields are read by the demo showcase,
  the PMO console and the dashboard rollups; changing them from derived back to
  independently-editable (or removing them) means revisiting every one of those
  call sites plus the seeded demo data.
- **D-05:** Monthly rows are generated by ramp-template auto-fill: the IL enters
  run-rate + start month + curve shape (cost 30/70/100, revenue 10/40/70, or
  linear); rows generate automatically and remain individually editable. This is
  what makes monthly granularity workable.
- **D-06:** Realized value is editable **only for months that have arrived** —
  no forward-booking into future months. Forward-booked value is the main way
  synergy tracking loses trust.

### Stage vocabulary + migration

- **D-07:** **Replace** the 5 execution statuses with exactly the 4 SYN-03
  confidence stages: `idea → validated → committed → captured`. One canonical
  field, one axis. Mapping applied once: `identified→idea`,
  `validated→validated`, `planned`+`executing`→`committed`,
  `realized→captured`.
  Rejected: a 5-gate rename keeping `executing` (mixes a confidence axis with an
  execution state — the very thing the stage-gate exists to fix), and a second
  independent `confidenceStage` field alongside `status` (two axes to keep in
  sync; nonsense combinations such as status=Executing + stage=Idea become
  possible).
  Costs surfaced and accepted before choosing: 3 of the 5 demo seeds map onto
  `committed` (addressed by D-10); 2 new i18n keys × 4 languages added and 3
  retired (`syn.st_identified`/`planned`/`executing`/`realized`); demo.db seed
  rows are rewritten — which per the standing WAL trap means a
  `wal_checkpoint(TRUNCATE)` before committing, or `git status` will lie.
  — **Reversibility:** one-way — reverting needs a data migration of every
  stored initiative back to the 5-value vocabulary plus restoration of the
  retired i18n keys in all four languages. Safe to take now only because
  `data/deals/` is empty (see D-11).
- **D-08:** Stage advancement carries **minimal hard gates, enforced
  server-side** with a stated rejection reason: `committed` requires an owner
  AND a phased target (run-rate + start month, per D-05); `captured` requires
  realized value recorded in at least one arrived month (per D-06).
  Rejected advisory-only and ungated: an ungated stage label is decoration, and
  Phase 7's RPT-03 (confidence-stage movement) can only trust stage counts if
  the gates are real.
- **D-09:** Backward stage movement (de-scoping) is **allowed but requires a
  non-empty reason**, recorded in the initiative's baseline history alongside
  the stage change. Rejected forward-only (would force modelling a separate
  `dropped` terminal state) and silent-backward (an unexplained demotion is
  worse than none).
- **D-10:** The 5 demo seed initiatives are **hand-tuned** to spread across all
  four stages and carry believable phasing rows, rather than taking the
  mechanical map verbatim. The demo showcase is a maintained deliverable per
  PROJECT.md; 3 of 5 identical-looking cards would undersell the new capability.
  Same migration effort, better showcase.
- **D-11:** **Hard cutover — no read-time compatibility shim.** The 4 stages
  become the only accepted values in all three duplicated copies
  (`server.js:3043`, `validators/workstream.js:114`,
  `public/js/execution.js:28-30` including `SYN_LABELS`/`SYN_COLORS`); legacy
  values are rejected by the validator. Verified safe during discussion:
  `data/deals/` is **empty** — no real-deal database exists yet, so no real data
  is stranded. A shim would be permanent dead weight no test could prove
  unreachable. Migration surface is 5 seed rows in `demo.db` plus the legacy
  `ma-portal.db` copy.

### Baseline history

- **D-12:** Baseline history is an **explicit snapshot model**: a `baselines[]`
  array on the initiative, each entry pinning the full prior target curve +
  run-rate + stage with who/when/why. **Not** a keystroke-level change log.
  Separation of concerns, decided deliberately: `baselines[]` = intentional
  re-baselining, user-visible, readable by deal members; `audit.db` = exhaustive
  forensic record, admin-only, unchanged by this phase.
  Rejected: a full `history[]` array (buries the real signal in
  typo-correction noise and duplicates what audit.db already stores) and
  deriving history from audit.db (would require a `rowId` filter on
  `queryAudit()` **and** a non-admin deal-scoped read path into a compliance
  control — its own authz design and threat review — for a *computed* rather
  than *intentional* baseline).
- **D-13:** A new baseline version is created by an **explicit re-baseline act**
  at any time, AND is **forced** (with a required reason) for any run-rate or
  curve-shape change once the initiative has reached `committed`. Before
  `committed` the numbers are still being worked out, so ordinary edits stay
  ordinary edits; after `committed` nothing can be edited quietly, and the trail
  is in-app rather than only in audit.db.
- **D-14:** **Baseline v1 is pinned as the "deal case"** and is never
  superseded. Variance reports against **both** the deal case and the current
  baseline. This is the number the deal was approved on — losing it behind three
  re-baselines is how synergy programs stop being accountable; Phase 7's RPT-03
  depends on it.
- **D-15:** **AUTHZ (explicit):** re-baselining is restricted to the Integration
  Lead and admin, **enforced server-side**. Baseline history is readable by any
  authenticated member of that deal. Stated explicitly rather than left for the
  planner to infer, because an authz bug has surfaced at the review gate in four
  consecutive phases — most recently CR-01, where a completion branch checked
  `status` but never compared `pending.owner` to the caller. Rejected
  owner-can-also-re-baseline (weakens the governance meaning of the number AND
  requires exactly the owner-vs-caller comparison this codebase has gotten wrong
  before) and any-member-writes.

### Staleness rule

- **D-16:** Staleness is driven by an explicit `lastConfirmedAt` stamp, set by a
  deliberate **"confirm current"** action or by a real value/stage change — but
  **not** by editing a note or title. The point of SYN-05 is that someone stands
  behind the number; a typo fix must not make a six-week-old forecast look
  confirmed. Works identically at every stage.
  Rejected period-completeness (says nothing about `idea`/`validated`
  initiatives, which have no realized value yet and would read as permanently
  stale, and cannot distinguish "not updated" from "genuinely zero this month")
  and any-write `updatedAt` (freshness only as honest as the editor).
  **Note:** no `updatedAt`/`lastConfirmedAt` field exists anywhere in the
  synergy lane today — this is greenfield.
- **D-17:** The staleness threshold is **30 days, configurable per deal**,
  applied uniformly to every stage. Matches the monthly phasing cadence of D-01
  and the monthly reporting rhythm; one number is also what Phase 7's RPT-04
  needs to split current from stale. Rejected stage-dependent defaults (more
  faithful, but a rule the IL and the steerco pack both have to explain) and 14
  days (more items sitting stale at any moment, dulling the signal).
- **D-18:** Stale initiatives are **visibly badged AND the headline rollup
  splits the figure**: "realized $XM, of which $YM unconfirmed". Matches SYN-05's
  own wording — visibly flagged rather than silently trusted — without hiding
  value, and gives Phase 7 a number to print. Rejected flag-only (a rollup made
  entirely of stale numbers still presents as one confident figure) and
  exclude-from-rollup (headline jumps for reasons unrelated to value capture).
- **D-19:** Stale initiatives **nudge their owner by reusing the Phase 4
  deal-home in-app owner-nudge pattern** (DD-02), not a new notification
  surface. A flag nobody sees does not change behaviour.

### Cost-to-achieve (SYN-02)

- **D-20:** Cost-to-achieve is modelled as a **single planned figure (with an
  expected spend month) plus dated actual-cost entries** — a list, not a fixed
  monthly grid. Cost-to-achieve is naturally lumpy (severance, IT migration,
  advisory fees); a 36-row monthly grid would be mostly zeros. Monthly net
  benefit remains computable by bucketing the dated entries into the D-01 grid.
  Rejected a full monthly cost grid mirroring the value ramp (symmetric and
  trivially reportable, but doubles the grid the IL maintains for data that
  rarely arrives evenly) and two bare totals (no timing, so a steerco pack
  cannot show when cost lands relative to value).
- **D-21:** The headline synergy rollup reports **gross realized, cost incurred,
  and net benefit**, alongside the stale split from D-18. Gross-only is how
  synergy programs flatter themselves; RPT-03 requires net benefit anyway, so
  building it here means Phase 7 reads a number rather than recomputing one.

### Task linkage (SYN-04)

- **D-22:** Linkage is stored as **`taskIds[]` on the initiative** — a task may
  serve several initiatives. Keeps the change inside the synergy lane: the task
  model, its routes and its validator are untouched, so the blast radius stays
  in this phase.
  Rejected `source: 'synergy:<id>'` on the task for a **verified** reason, not a
  stylistic one: `source` is a single string already carrying template and
  remediation provenance and used for dedupe
  (`server.js:3006` — `if (lane.some(t => t.source === source)) return`), so a
  task could link to exactly one initiative and overloading the field would
  collide with that dedupe. Also rejected denormalizing both directions (two
  places to keep in sync; every delete path must clean up both).
- **D-23:** Completing linked tasks **does not** affect realized value or stage.
  The link shows a delivery-progress indicator ("4 of 6 tasks done"); realized
  value and stage stay deliberate entries per D-06 and D-16. Deriving value from
  task completion is forward-booking wearing a different hat — exactly the
  credibility failure D-06 exists to prevent. Rejected auto-advance, and
  rejected (for now) the softer "prompt the IL when all linked tasks are done".

### Claude's Discretion

No area was delegated with "you decide" — all 23 decisions were chosen
explicitly by the user. The planner retains normal latitude on: table/grid
layout and interaction details for the monthly phasing editor, the shape of the
`baselines[]` entry beyond the fields named in D-12, where the "confirm current"
control sits in `public/js/execution.js`, and how the ramp-curve auto-fill
percentages are stored (constants vs. deal setting).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **Ramp auto-fill has no analog yet** — D-05's curve generation is new logic;
  nothing in the codebase generates period rows today.
- **Deal-home owner nudges (Phase 4, DD-02)** — the surface D-19 reuses for
  stale-initiative nudges. Do not build a second notification surface.
- **`newId('syn')`** — the collision-resistant id generator already used by the
  synergy create path; baseline versions and phasing rows should use the same
  helper rather than array indices.
- **Zod validator registry** (`validators/`, `registerSchema(method, path,
  schema)`) — every new or changed request body must be registered here; this is
  the established VAL-01 pipeline.
- **`audit.db` via `writeDb()`** — audit rows are produced automatically for
  deal writes. No per-route audit code is needed for the new fields.

### Established Patterns
- **Triplicated enums** — `SYN_STATUSES` exists independently in `server.js`,
  `validators/workstream.js` and `public/js/execution.js`. The RAID precedent
  (D-26, `validators/workstream.js:139-147`) documents these as deliberate
  independent copies that MUST be changed together. A partial edit is a known
  failure mode in this repo.
- **Upsert-in-one-POST** — `POST /api/synergies` handles both create and update,
  branching on `b.id`. New fields must be handled on both branches; the update
  branch currently validates before mutating the shared `readDb()` cache, and
  that ordering must be preserved.
- **Demo/real lane split** — `synergyLane()` branches on
  `db.settings.demoMode === false` to choose `customSynergyInitiatives` vs
  `synergyInitiatives`. Every new read and write path inherits this branch.
- **i18n via `data-i18n`** — status badges render
  `data-i18n="syn.st_" + status`. Renaming stages requires adding the new keys
  in all four languages (EN/DE/ZH/CS), not just changing the JS labels.
- **Server-side authz, not UI hiding** — the DD-04 precedent from Phase 4;
  D-15's re-baseline restriction must be enforced in the route, not the view.

### Integration Points
- `POST /api/synergies` — extended for phasing rows, stage gates (D-08),
  demotion reason (D-09), re-baseline (D-13, D-15), confirm-current (D-16),
  cost entries (D-20) and `taskIds[]` (D-22). The planner should consider
  whether re-baseline and confirm-current warrant their own routes rather than
  overloading this handler further.
- `public/js/execution.js` `renderSynergy()` — the rollup gains the net-benefit
  and stale-split figures (D-18, D-21); cards gain stage badges, phasing,
  staleness and task-progress.
- Demo seed data in `data/demo.db` (and the legacy `data/ma-portal.db`) —
  5 rows, rewritten per D-07 and D-10.

### Known trap (from prior phases, applies here)
Writing to a committed `.db` can land only in the gitignored `-wal` sidecar,
leaving the tracked file byte-unchanged — `git status` will show nothing. After
any change to `demo.db`, run `wal_checkpoint(TRUNCATE)` and diff the committed
`.db` against HEAD before trusting a clean tree. This has fired repeatedly.

<specifics>
## Specific Ideas

- Ramp curve shapes are named and fixed: **cost 30/70/100**, **revenue
  10/40/70**, plus **linear** (D-05), taken from standard PMI ramp practice.
- The stale rollup wording the user chose: *"realized $XM, of which $YM
  unconfirmed"* (D-18).
- Baseline v1 is labelled the **"deal case"** in the UI, not "v1" (D-14).
- Task-linkage progress reads as **"4 of 6 tasks done"** (D-23).
