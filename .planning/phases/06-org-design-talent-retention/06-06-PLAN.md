<objective>
Deliver D-15 and close D-17 — the Phase-4 accepted risk this phase is not allowed to defer again,
because D-15 deliberately creates a SECOND route for clearance-restricted content into an unfiltered
log, and the leak was already proven live once: converting a Legal DD finding republished its title
and notes through the RAID log to a member cleared only for HR.

Purpose: the register and the RAID log are already describing the same things — the demo database
holds a seeded RAID risk about key engineers being approached by competitors, with no link to any
retention record. D-15 links them. D-17 makes that safe, and retro-fixes the Phase-4 instance while it
is there.
Output: a one-click bidirectional conversion, a provenance-based outbound RAID filter, and the two
companion fixes that must not ship a commit later than the filter.

**THE SINGLE MOST DANGEROUS ITEM IN THIS PHASE, and its own wording is misleading.** D-17 reads like a
one-line reuse of the existing area-keyed list filter. It is not, and the failure mode is not a leak —
it is fail-closed-to-useless. That helper keys on an `area` field. RAID entries have no `area` field;
they carry a workstream id. Verified against the live demo database: every seeded RAID row has
`{id, type, title, severity, probability, owner, workstreamId, status, notes, createdAt}` and no area
key at all. A naive reuse therefore evaluates membership of `undefined` in the granted set, which is
false for every possible set including the full admin set — **emptying the RAID log for every caller,
admin included**. Worse, it looks correct from the restricted side: a test asserting "an uncleared user
does not see the converted entry" passes, while the open side silently breaks.

The inverse mapping is also unavailable. The area-to-workstream map is many-to-one — two functional
areas collapse into the finance workstream and two more collapse into the legal workstream — so a
workstream id cannot be resolved back to a clearance key without guessing.

**The correct shape, therefore, is new access-control code: provenance resolution.** A per-entry
resolver reads the entry's `source` string, matches the DD finding prefix and looks that finding's own
area up in the findings lane, matches this phase's new flight-risk prefix and returns the fixed `hr`
area, and returns null for everything else. An entry resolving to null is returned unfiltered —
general RAID entries are not MNPI, and D-17's scope is content republished from restricted sources, not
the whole log. This is why D-17's own text accepts that the phase's blast radius widens into the RAID
lane: the widening is real and larger than a one-line filter call.

**The test must prove BOTH directions.** A one-directional test passes a filter that blanks the lane.
`test/raid-access-filter.test.js` asserts the exclusion AND asserts that an admin, and an appropriately
cleared member, still receive unlinked entries and entries whose provenance they are cleared for.

**Two companion fixes land in the SAME commit as the filter, not a follow-up.** First, the critical
severity level has never had a CSS rule — the severity enum was widened to four values in Phase 4, the
rule set was left at three, and the DD conversion route already copies a critical severity verbatim, so
the gap is live and reachable today independently of anything this phase does. Second, the
due-diligence page currently tells operators that a converted finding is visible to the whole deal
team rather than only to cleared members; that sentence becomes factually wrong the instant the filter
ships, and a green test suite cannot catch a copy-only staleness bug — only a live read or a source
assertion can.

**Planner discretion recorded (06-RESEARCH.md Assumptions Log A1 — the source prefix is genuinely the
planner's naming call):** the flight-risk conversion's source string is the literal prefix
`org-flightrisk:` followed by the entry id. It must be distinguishable from the DD finding prefix by
its own leading token, because that distinction is what the outbound filter branches on.
</objective>
