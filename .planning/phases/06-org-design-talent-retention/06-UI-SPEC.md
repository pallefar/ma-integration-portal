> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Color-reuse disambiguation rule (resolves the `#EF4444` vs `#C0392B` red-on-red risk):**
`#EF4444` (`--status-danger`) appears **only** on destructive-action UI (delete confirmations,
irreversible-operation buttons) — never on a data/severity signal. `#C0392B` (RAID high) and
`#C0341D` (RAID critical) appear **only** as severity-of-data indicators (flight-risk level,
overdue markers) — never as an action button. The two reds are visually close but contextually
never adjacent to each other in the same control, so a user is never asked to distinguish them
side-by-side; this rule exists so the planner and executor don't accidentally cross the streams
(e.g. never use `--status-danger` for a "high risk" badge).

Critical structural note carried into Surface Contract §5: **flight-risk severity is NOT rendered
as a second colored badge/pill on the tree card.** It is rendered as a card border-accent
(the same idiom as `.dd-item--overdue{ border-color:#C0392B; box-shadow:inset 0 0 0 1px
rgba(192,57,43,.35); }`, `due-diligence.html:21`), occupying a different visual channel
(border, not fill) from the decision badge (a filled pill). This is the direct resolution of
Design Tension 5 below.

## Internationalisation & Text Expansion

**Added at the step-9.5 probe gate (user decision) — the authored spec omitted this axis entirely
and the checker's 6/6 pass did not catch it.**

Every user-facing string in this app renders through `data-i18n="key"` and exists in **four
languages (EN/DE/ZH/CS)** — ~698 keys today. `public/js/execution.js:1008` is the governing
precedent: severity badges render `data-i18n="raid.lvl_" + severity`, i.e. **badge text is
translated, not literal**. D-14's five decision values therefore need five new keys × four
languages, and D-16's severity labels already have theirs.

Locked contract for every new surface in this phase:

- **No fixed-width chrome.** Every badge, pill, chip and count row sizes to its content. No `width`
  or `max-width` in absolute units on the level chip, the decision badge, the severity accent's
  label, the switch labels, or the deal-home count rows.
- **Wrap, never clip.** No `overflow:hidden` + `text-overflow:ellipsis` on translated label text.
  A longer translation must reflow its container, not be silently truncated — a clipped
  `redundant`/`in-selection` badge is a data-integrity problem, not a cosmetic one, because the
  label IS the decision.
- **German is the sizing case.** DE is the longest of the four for this vocabulary; ZH is the
  shortest and exercises the opposite failure (a pill collapsing to near-nothing). Both ends get
  looked at, not just EN.
- **Verification is part of "done".** The executor's visual pass for any wave touching the tree
  card, the decision badge, the deal-home panel or the nudge must be run at the longest available
  translation, not only at EN. This is the same class as the layout regression previously reported
  on this project as "looks very weird", and it is why this is a locked contract rather than a
  backstop.

Note for the planner: this is a *design* contract only. Actually authoring the five DE/ZH/CS
translations is separate work already budgeted in 06-CONTEXT.md D-14 ("~5 i18n keys × 4
languages"), and Phase 5's D-07 precedent applies — where a translation's meaning is genuinely
unchanged it may be carried verbatim, otherwise English text ships and relies on
`transitions.js`'s documented fallback-to-English contract.

## Design Tensions Resolved

Six tensions named in the brief, each resolved concretely rather than left to executor judgment.

### 1. Making a vertical indented tree read as an org view (not a fallback list)

Three signals carry the hierarchy, stacked (not one alone):

- **Indent guide**: a 1px vertical rule (`var(--border-color)`, the existing `#E2E8F0` border
  token used app-wide, e.g. `.dd-item{ border:1px solid var(--border-color); }`
  `due-diligence.html:20`) runs down the left edge of each depth level's card column, continuous
  through a node's children — the same "rail" a file-tree or nested-comment UI uses, achievable
  in pure CSS with a `border-left` on a wrapping `.org-node-children` container, no JS layout math.
- **Elevation decreases with depth**: depth-0 (top-level) nodes get `box-shadow:var(--shadow-sm)`
  (`style.css:40`, the existing lightest shadow token); depth ≥1 nodes get `border` only, no
  shadow — mirroring `.dd-item`'s own flat, border-only treatment (`due-diligence.html:20`). A
  flat depth-0 tree would look like a plain list; the elevation drop-off between root and children
  is what a screenshot reads as "chart," not "list."
- **A level chip**, not just indent position: each card carries a small pill showing the node's
  `level` free-text value (D-08) at the micro-label size/weight (0.64rem/800, cited above) with a
  neutral `var(--bg-light)` fill — this is the same visual role a reports-line count plays in a
  real org chart, made legible even after the tree is scrolled past its visual indent (narrow
  viewports flatten indent per Tension 6, so the chip is the fallback hierarchy signal there).

Connector *lines between* sibling cards (the rejected boxes-and-lines approach) are explicitly
NOT built — the indent rail plus elevation plus level chip is the full signal set.

### 2. Density at 200+ nodes

- **Default expand depth: 2 levels** (root + one level of children expanded; everything below
  depth 2 starts collapsed). Matches the codebase's existing bias toward showing summary-first,
  drill-in-on-demand (the DD area-head pattern: areas render open, items inside them do not
  auto-scroll into deep detail).
- **Per-node collapse affordance**: a small `▸`/`▾`-style toggle (plain text glyph, no icon
  library — consistent with "no icon library" in Design System) at the left of each card with
  children, click-to-expand/collapse; state held in a plain JS `Set` of expanded node ids, not
  persisted server-side.
- **Indent cap**: visual indent (§1's 1.25rem-per-level rail) stops increasing past depth 6
  (6 × 1.25rem = 7.5rem / 120px of indent) — beyond that, the rail stays flat and the level chip
  (§1) becomes the only depth signal, so an 8-level-deep org never pushes card content off a
  narrow viewport.
- **Search**: a single text input (styled like `.dd-add input[type="text"]`,
  `due-diligence.html:27-28`) filters by title, level, or occupant name (client-side substring
  match against the already-fetched tree — no new search endpoint). On a match at depth *N*, every
  ancestor from root to that node is force-expanded (added to the expanded-id `Set`) and the tree
  scrolls the first match into view; non-matching siblings stay collapsed/hidden rather than
  greyed out, so a 200-node search result reads as a short list, not a haystack.
- **Vacant/unassigned bucket**: vacant positions (D-05's `employeeId: null`) render **inline in
  the tree at their actual `reportsToId` position** — not pulled into a separate bucket — because
  a target-state design specifically needs to show *where* an open role sits in the structure.
  Employees with no position at all (imported via D-10 but not yet placed, or present in
  `employees` but never mapped) render in a **separate collapsed section below the tree**, titled
  "Unassigned employees ({N})", using the same `.dd-empty`-style italic treatment when zero.

### 3. The two-tier clearance contract — DOM-verifiable absence

The rule (D-20, generalized to every restricted surface this phase touches, not just the rollup):
**a server response for an uncleared caller omits the restricted fields/rows entirely; the client
renders nothing because there is nothing to render** — not a zero, not a masked value, not a
greyed-out control.

DOM contract, stated so it is grep-assertable against raw `innerHTML` (the same method Phase 4's
UAT used to prove T-04-46):

- The deal-home restricted tier (D-19) is a **`<section class="org-summary-restricted">`** —
  a different tag from the open tier's **`<div class="org-summary-open">`** (tag-level distinction,
  per the Phase-5-orphaned-`</div>` countermeasure: a stray CSS/class typo can survive undetected,
  a missing `<section>` tag cannot — `document.querySelectorAll('section.org-summary-restricted')`
  returns 0 for an uncleared caller and exactly 1 for a cleared one, verifiable by a live
  `innerHTML` grep with zero false positives from styling).
- For an uncleared caller, `GET /api/org/summary`'s response has **no `restricted` key at all**
  (not `restricted: null`, not `restricted: {}`) — `deal-home.js`'s render function must branch on
  `summary.restricted !== undefined`, matching the existing `renderDiligence()` pattern of
  iterating only what the array actually contains (`deal-home.js:151`, "never a client-side list
  of every possible area").
  covers the current/target switch (Tension 4) and the flight-risk owner nudge (D-22): the switch
  control and the nudge banner/badge are both children of code paths gated on the same
  `restricted !== undefined` check, so their absence is structural, not a CSS `display:none`.
- The `org.html` page itself: for an uncleared member, the target-state UI (switch control,
  target-state tree render, decision badges, flight-risk register tab) is **never inserted into
  the DOM** — the page fetches `GET /api/org/positions?state=current` only (D-07's filter never
  even offers a `state=target` request from an uncleared session; the client has no code path that
  constructs that URL unless a `restricted` capability flag from an initial `GET /api/org/summary`
  or equivalent probe is present).
- **The client-side omission above is NOT the control.** Exactly as stated for the write path in
  Surface Contract §5 ("Server-side authz is the actual gate; the UI omission is a courtesy, not
  the control"), the same rule governs this READ path: `GET /api/org/positions?state=target` MUST
  be refused server-side for an uncleared caller — a hand-crafted request with that query string,
  from a valid session that simply never loaded the page's JS, must not return target-state rows.
  Stated explicitly here because D-07 is a *read* restriction and this project's review gate has
  already caught precisely this class once on the read side: Phase 4 Wave 2 found `server.js:446`
  role-checking GETs **only** on `/api/admin`-prefixed paths, so any authenticated role could read
  any deal's membership + clearance map. The planner must treat the server filter on `state` as
  the security boundary and this section's DOM-absence rules as defence in depth on top of it.

### 4. The current/target switch — absent, not present-but-inert

Per Tension 3's principle applied specifically here: **the switch control does not render at all**
for an uncleared user — no toggle, no disabled toggle, no single "Current" label standing in for a
missing pair. A disabled control still tells the user "there is a Target view you're not allowed
to see," which is exactly the disclosure D-07 forbids ("a masked row still discloses that
decisions exist"). For a cleared user, the switch is two plain-text toggle labels ("Current" /
"Target", §Copywriting) with the active one styled via the micro-label weight (0.68rem/800) and
`var(--te-dark-teal)` color — not a settings-style animated switch component (no such component
exists in this codebase to reuse, and a plain label-pair keeps the control visually inert until
interacted with, avoiding a distracting affordance on a page most sessions load in current-only
mode).

### 5. Five decision values + four risk levels on one card — avoiding confetti

Resolved by putting the two vocabularies on **different visual channels**, not different colors
within the same channel:

- **Decision badge** (D-14, 5 values) renders as a **filled pill** in the card's top-right corner,
  sized/weighted like `.raid-type` (`execution.html:109`, "flex:none; font-size:.64rem;
  font-weight:800; border-radius:12px; padding:.18rem .6rem"). Palette: `retain` → green tint
  (`rgba(63,122,55,.12)` bg / `#3f7a37` text, the existing RAID-low green); `redeploy` → info-teal
  (`rgba(59,130,246,.12)` bg / `#3B82F6` text, `--status-info`, `style.css:30`); `in-selection` →
  the reserved 10% accent orange (`--te-orange`, in-progress convention); `redundant` → the RAID
  high red (`rgba(192,57,43,.1)` bg / `#C0392B` text, matching `.raid-type.risk`,
  `execution.html:110`); `open` → neutral grey (`var(--bg-light)` bg / `var(--text-dim)` text,
  matching `.deal-home-checklist-status`'s undone state, `dashboard.html:17`).
- **Flight-risk level** (D-16, 4 values) renders as a **card border-accent**, not a pill — reusing
  `.dd-item--overdue`'s exact idiom (`border-color` + `box-shadow: inset 0 0 0 1px …`,
  `due-diligence.html:21`) rather than inventing a second badge shape. Only `high`/`critical`
  entries get a visible border-accent by default (low/medium render with the card's normal
  border, consistent with `.dd-item--overdue` only firing on overdue, not on every item) — this
  also keeps the tree from turning into a wall of colored borders at 200 nodes, surfacing only
  what actually needs attention.
- **The one card that can carry both** (a `redundant`-decision position occupied by a
  `high`/`critical`-flight-risk person) shows a filled pill (top-right) AND a border-accent (card
  edge) simultaneously — two different visual grammars stacked, not two pills competing for the
  same corner. This combination is rare by construction (a person already decided `redundant` has
  little reason to still carry an *unmitigated* flight-risk entry in practice) but the render
  logic does not special-case it — both signals simply co-render.

### 6. Narrow-width behavior

The user has previously reported a layout regression as "looks very weird" (header scramble) —
every breakpoint below is explicit, matching the codebase's dominant breakpoint (`768px` appears
in more `@media` rules than any other value, e.g. `style.css:869`, `:1045`, `:2083`, `:2756`,
`:5429`, `:6032` etc.):

- **Org tree at ≤768px**: card padding drops from the desktop `.65rem .9rem` (due-diligence
  precedent) to `.5rem .65rem`; the indent rail (§1) caps at depth 3 instead of 6 (3 × 1.25rem =
  60px, leaving ≥260px of card width at a 320px viewport after 16px page margins); the level chip
  and decision badge both keep their position but `flex-wrap:wrap` (the existing `.dd-item-meta`
  pattern, `due-diligence.html:24`) so they drop to a second line rather than compressing text.
- **Two-tier deal-home panel at ≤768px**: the existing `.deal-home-dd-row` pattern already
  `flex-wrap:wrap`s at this width (`dashboard.html:24`); the open/restricted `<div>`/`<section>`
  tags stack vertically (single column) with no additional breakpoint-specific rule needed beyond

## Surface Contracts

Concrete DOM/CSS/interaction contracts per surface named in the brief.

### 1. `public/org.html` + `public/js/org.js`

Structural template: copy `due-diligence.html`'s shell verbatim (`app-container` → `main-header`
→ `nav.navigation-bar` with `Overview` / `Integration Leader Portal` links → `main.main-content`
→ a `.org-wrap{ max-width:1100px; margin:0 auto; }` content column, matching `.dd-wrap`
`due-diligence.html:12`). Page-local `<style>` block only — no new CSS file, matching the D-12
citation of `due-diligence.html`'s own pattern. `textContent`-only rendering throughout
(`due-diligence.js`'s established discipline — zero `innerHTML` assignment). No `pageAccess` entry
in `transitions.js` (D-12, IN-02 precedent, verbatim).

### 2. Org tree (D-11)

- Card DOM: `<article class="org-node" data-position-id="{id}">` (an `<article>`, not a bare
  `<div>` — a deliberate tag choice, see the vacant/occupied distinction below) containing:
  a collapse toggle (`<button class="org-node-toggle">`, present only if the node has children),
  the level chip, the title (`<span class="org-node-title">`), the occupant slot, and the decision
  badge (top-right, absolute-positioned within the card per Tension 5).
- **Occupied vs vacant — tag-level distinction** (the Phase-5-orphaned-`</div>` countermeasure
  applied here): an occupied position's occupant slot is `<span class="org-node-occupant">{name}
  </span>`; a vacant position's occupant slot is `<em class="org-node-occupant org-node-vacant">
  Vacant</em>` — a *different element tag*, not just a modifier class. This means
  `document.querySelectorAll('em.org-node-vacant').length` is grep/DOM-assertable against the
  server's own vacant count independent of whether the `.org-node-vacant` CSS class survives a
  future stylesheet edit intact.
- Children container: `<div class="org-node-children">` wrapping recursively-rendered child
  `<article>`s, holding the indent rail border (Tension 1) and the collapse/expand `display` state.
- Rendering is pure DOM construction from a single `GET /api/org/positions?state=current` (or
  `&state=target` for a cleared, target-toggled session) response — no client-side tree-building
  library; parent/child nesting is computed once client-side from the flat `reportsToId` list into
  a nested structure before render, same shape of transform `due-diligence.js` already does
  grouping DD items by area.

### 3. Current/target state switching (D-06, D-07)

- Absent entirely for an uncleared session (Tension 4). For a cleared session: two plain-text
  toggle labels rendered inside the page hero (`.org-hero`, mirroring `.dd-hero`,
  `due-diligence.html:13`), state held in a JS variable, re-fetching
  `GET /api/org/positions?state={current|target}` on toggle — no client-side diffing between the
  two states, no combined single fetch that includes both (D-21's rationale generalized: shipping
  target-state rows to a client that then hides them locally is exactly the forbidden pattern).
- Switching to Target when the deal has zero target-state positions yet: renders the same empty
  state as §Copywriting ("No positions mapped yet") but with body copy substituted to "No target
  design started yet. Positions copied from current state, or added new, will appear here." —
  never a silent blank page.

### 4. Position editor + bulk paste import (D-10)

- **Manual add/edit**: a form styled like `.dd-add` (`due-diligence.html:26-28`) — dashed border,
  inline fields (title text input, `level` as an `<input list="org-level-suggestions">` bound to a
  `<datalist>` per D-08, `reportsTo` as a searchable select of existing position titles, an
  optional employee-link picker). Submitting POSTs to a new `/api/org/positions` route.
- **Bulk paste importer**: a `<textarea rows="6">` styled identically to `#wiz-roster-raw`
  (`pmo.html:186` — monospace font, `.75rem`, dashed/solid border per `.dd-add` treatment),
  labelled "Paste roster (CSV or JSON) — title, level, reportsTo, name, email" mirroring the
  existing precedent's exact label wording pattern ("Paste Roster JSON or CSV Content"). A
  **"Preview"** step (parses client-side, shows a row-count + first-N-rows table before commit)
  precedes **"Import"** (the actual POST) — this two-step flow is new relative to the `pmo.html`
  precedent (which imports directly) because a 150-row paste with a typo'd `reportsTo` needs a
  chance to be caught before 150 positions are created; row-by-row partial-validity handling is
  explicitly left to planner discretion per 06-CONTEXT.md, but the Preview step's existence is
  locked here so a rejected paste is never silently swallowed.
- **Orphan guard (Claude's Discretion in 06-CONTEXT.md, resolved here for the UI contract)**:
  deleting an employee linked to a position **refuses the delete** (per the Copywriting Contract's
  "This cannot be undone" framing does NOT apply here — this is a block, not a confirm) unless the
  caller first either unlinks the employee from the position or deletes the position itself. The
  position-delete confirmation (§Copywriting) is what actually surfaces the reassignment
  requirement to the user.

### 5. Decision register (D-13, D-14)

- **Badge on the tree card**: per Tension 5, a filled pill top-right, always present (every
  position has a derived decision — `open` is itself one of the 5 values, so there is no
  "no decision yet" gap state on the card itself).
- **History view**: a per-position panel/modal listing every `orgDecisions` entry for that
  position in reverse-chronological order, each row showing `type` (as the same pill styling,
  smaller), `rationale`, `decidedBy`, `decidedAt`, `effectiveDate` — styled as a simple

  (`due-diligence.html:37`). Empty state (a position with only its initial seed/creation, no
  explicit decision recorded — if that's possible per the data model): "No decisions recorded
  yet."
- **Record-a-decision form**: type (select, the 5 fixed values, no free text — D-14's rollup
  requirement), rationale (required textarea), effectiveDate (date input). Visible only to
  IL/admin (D-04) — for every other cleared-but-non-IL area member, the form is **not rendered**

  restated explicitly ("an authz bug has surfaced at a review or verification gate in five
  consecutive phases") and a disabled-but-visible form control is the exact class of "hidden in
  the UI, not filtered server-side" failure DD-04 (and D-04 here) forbids. Server-side authz is
  the actual gate; the UI omission is a courtesy, not the control.
