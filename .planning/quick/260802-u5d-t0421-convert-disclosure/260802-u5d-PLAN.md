# Quick Task: Close T-04-21 — the missing clean-room disclosure on finding conversion

## Why

`/gsd-secure-phase 4` returned `OPEN_THREATS` with **59/60 closed** and one blocking
threat at severity `high`. `T-04-21` was never an unmitigated risk — it was an
**accepted risk conditioned on a UI control that was never built**:

> "the convert control states that the created task or entry is visible to the whole deal team."

No such disclosure exists anywhere in `public/js/due-diligence.js`,
`public/due-diligence.html`, or `public/css/style.css`. The acceptance therefore
rests on a control that does not exist.

**The underlying leak is real and I proved it live** (orchestrator repro, server on
:3406, deal `T0421 Probe`, pmo granted `["hr"]` only, never `legal`):

```
BEFORE convert — pmo sees the legal finding via /api/dd/findings:  NO  (clean-room holding)
AFTER  karen converts it — pmo reads via GET /api/raid:
  title: "Change-of-control clause voids Siemens master agreement on close"
  notes: "Counsel estimates EUR 4.2M exposure; target has not disclosed to counterparty."
  workstreamId: "ws_legal"   source: "dd-finding:ddfind_msc730nffa1253e8"
also leaked via GET /api/integration-tasks: YES
```

Mechanism, confirmed in source:
- `server.js:3618-3629` copies `finding.title` **and** `finding.notes` verbatim into the RAID entry; `:3596` copies the title into the task.
- `app.get('/api/raid')` (`server.js:3126-3128`) returns `raidLane(readDb())` with **no** `filterByAreaGrant()`; same for `/api/integration-tasks`. `filterByAreaGrant` appears only on DD routes (`3246, 3383, 3476, 3661, 3662`).
- GETs are not role-checked outside `/api/admin`, so any deal member reads the full RAID lane.

## Decision (user, 2026-08-02)

Build the disclosure the threat register promised. This closes T-04-21 **as written**
and makes the audience-widening a deliberate, informed operator choice rather than a
silent republish. Conversion is performed by an operator who **is** cleared for the
area, so informed consent is the appropriate control at this point in the flow.

The stronger option — clearance-filtering `/api/raid` and `/api/integration-tasks` for
DD-sourced entries — was explicitly considered and **deferred**: it is new scope beyond
Phase 4 and needs a design decision about who *should* see a converted finding, since
the entire purpose of converting is to move an item into the shared execution lane.
Log it for a later hardening phase; do NOT implement it here.

## Tasks

### Task 1 — Add the disclosure to the convert control

`public/js/due-diligence.js`, in the finding-row renderer's `convertRow` block
(currently ~lines 293-317, the `div.dd-finding-convert` holding the
"Create Day-1 task" and "Create RAID entry" buttons).

Append a note element to `convertRow` **after** both buttons and any existing
`dd-finding-linked` spans, built with the file's existing `el()` helper using the
`text:` property (which sets `textContent`) — **never** `innerHTML`:

```js
convertRow.appendChild(el('span', {
  className: 'dd-finding-convert-note',
  text: 'Visible to the whole deal team once created — not only members cleared for this area.',
}));
```

Constraints:
- **textContent only.** `grep -c innerHTML public/js/due-diligence.js` must stay `0`.
- The note must render for every finding row, regardless of `hasTask`/`hasRaid` — an
  operator deciding whether to convert needs it *before* converting, and an already
  converted finding still documents where its content went.
- Do not change conversion behaviour, button state, or `convertFinding()`.
- If a style rule is needed for legibility, add it to the page's existing scoped
  `<style>` block or `public/css/style.css` in the file's established manner. Keep it
  minimal — this is a disclosure, not a redesign.
